# MHWI Blender 模组制作

本 skill 是一条走到底的实作路线沉淀出来的：

- **通用手册**（本文件）= 流程、二进制格式、权重与材质配方、崩溃陷阱——前两次实战的产物，之后每次遇到新问题都会回填；
- **逐案记录**（`实战/`）= 第 4~17 次实战各自踩到的坑与判据，覆盖借壳移植、四部位权重对齐、mrl3/ctc/tex 就地打补丁、悬挂件物理链、材质观感与色彩空间、描边壳，以及"只有成品包、没有工程"时的反推。

贯穿全部实战的收获：**症状反复治不好时，先造一个能区分假设的测量**（射线穿模图、逐高度覆盖率表、贴图像素统计、改前改后逐字节 diff），远快于继续按"听起来合理"的猜测动手。第一次留下的"mrl3 不能写脚本直改"结论也已被推翻——格式完全反解后，就地打补丁是安全且高效的。

## 核心概念（先读这个）

1. **mod3 = 网格+骨架**，**mrl3 = 材质表**（材质名→贴图路径+渲染参数），**ctc/ccl = 物理**。四者配对使用。
2. **借壳策略**：找一个同体型的现成模组（同角色最佳），它的 mod3 里已经有游戏验证过的骨架、网格槽位、材质命名、LOD、物理链。你的工作只是"换皮"：删它的网格，放上你的网格，把权重从它的网格传给你的网格。
3. **四部位结构**：pl040_0000 下分 body/arm/wst/leg（+helm），**每部位一副独立骨架**（同一副游戏骨架的拷贝，骨骼名相同）。网格必须绑"所属部位"的骨架。基壳模组可能把奇怪的部件塞进奇怪部位（实测：外套在 arm、双马尾在 leg）。
4. **材质槽名即接口**：mod3 导出时写的是网格材质槽的**名字**，游戏拿这个名字去 mrl3 找材质。名字对不上 = 黑模。
5. **同名材质共享贴图**：两个网格用同一个材质名 = 游戏里只能用同一张贴图。需要独立贴图的网格要改到"闲置材质名"上（mrl3 里有几十个未使用的材质条目可挑）。
6. **伪发光渲染套路**：二次元模组普遍用 `BaseMapFactor≈0.3~0.4 + EmissiveFactor≈1.5~3.0（自发光贴图=底图）` 叠加出"不受光照影响"的赛璐璐感。**Emissive 指向错误贴图 = 整体被洗色**；关掉 Emissive 而不调 BaseFactor = 整体死黑；`Metalic=1.0` = 暗色镜面（手套花屏的元凶）。

## 完整流程

### 阶段 0：素材解包
- `.unitypackage` 本质是 **tar.gz**：每个资产一个 GUID 目录，含 `pathname`（原始路径）、`asset`（文件内容）、`asset.meta`（含 GUID）。
- 解包脚本：读 pathname 还原目录结构写 asset；用 asset.meta 里的 GUID 反查"材质槽→贴图文件"对应关系。
- 注意保留 `.meta` 或自建 GUID 映射表，否则反查不了。

### 阶段 1：基壳导入与对齐
1. MHW Mesh 面板导入基壳各部位 mod3（各自进入 `f_xxx040_0000.mod3` 集合）。
2. 基壳网格无贴图显示黑/白剪影 = 正常。
3. 把自己的模型（FBX）导入同一场景，**缩放对齐**：以骨盆高度对齐最准（G 缩放时锁轴，对比髋骨位置）。
4. ⚠️ 基壳骨架一根骨骼都不能删——游戏动画和 ctc 物理按骨骼名引用它们，没有权重的骨骼也可能是模拟链。

### 阶段 2：辨认基壳网格
- 网格名是 `Group_0_Sub_N__材质名` 无名氏。用"逐个放映"脚本（循环隐藏其他网格+镜头对准+大字标签）逐个辨认，记录"编号=部位"清单。
- 材质尾号（`__Mt__5` 等）可作为分组线索。

### 阶段 3：权重传递（核心工作量）
**对号表**：每个用户网格 ↔ 一个基壳供体网格。供体选择原则：
- 部位重叠的优先（袜←袜、鞋←鞋）
- 形状/覆盖范围差异大时，**改用身体皮肤（Body_base 类网格）当供体**——贴身衣物继承皮肤权重最正确（实例：原版供体是中筒袜，用户的过膝袜大腿段会拿到小腿骨权重；原版上衣只到胸部，紧身衣下摆会拿到裙摆骨权重）
- 垂坠装饰（项链/包/缎带）找同类垂坠件当供体

**传递流水线**（每个目标网格）：
1. 多用户网格先 `obj.data = obj.data.copy()`
2. 删除旧骨架修改器、清空旧顶点组（旧骨骼体系退役）
3. 清父级（CLEAR_KEEP_TRANSFORM）+ `transform_apply`（位置/旋转/缩放全应用）→ 网格数据=世界坐标
4. 加 Data Transfer 修改器：source=供体，顶点组权重，映射=最近面插值 → 应用
5. **补漏**：没拿到权重的顶点用 BVH 贴面插值从供体补（最近顶点法会在跨部位时涂抹权重）
6. 换绑部位骨架修改器
7. 把网格挪进供体所在集合（导出按集合走）

**物理链骨规则**（游戏实测教训）：
- 垂坠物（项链/包/头发/马尾/缎带）的链骨权重**保留**——游戏里布料模拟驱动，飘动是特性
- 贴腿/贴身部件（袜上段/腿环/紧身衣下摆）的链骨权重**必须改挂真骨**——Blender 姿态模式测不出来（运动学跟随），游戏里模拟一开就乱飘/后坠
- 判定方法：权重解剖脚本列出每组的"子骨数/后代数"，叶子骨成串出现=链骨

**最终修正用 Blender UI 手动做**（比脚本稳）：
- 编辑模式 + Alt+Z X 射线 + 框选/刷选顶点 → 顶点组"指定/移除"
- 裆部/下摆部件绑"骨盆级静态骨"（找叶子骨、位置在胯部、无网格绑定的那根）→ 抬腿不再拉宽
- 权重绘制模式（Ctrl+Tab）可视化检查
- 裆部皮肤左右甩：身体皮肤裆部中央窄条也改挂骨盆骨（两侧大腿内侧保留腿骨权重）

### 阶段 4：清理与导出前检查
- 删全部基壳供体网格、删自己的旧骨架（仅当无引用）
- 脚本清理：松散顶点（编辑模式 网格▸清理▸删除松散元素）、缺 UV（补空 UVMap）、多余 UV 层（mod3 只认一个）
- **材质名对齐**：把观感材质（BH_UV1 等）换成供体的官方材质名——**每次导出 mod3 前必须跑**；导完想看预览再跑"恢复预览材质"切回来
- 导出：文件 ▸ 导出 ▸ MHW Model Editor ▸ MHW MOD3，选目标集合。预检报错按提示修（松散顶点/缺UV 最常见）。"设置mod目录失败"日志无害，手动放文件即可。

### 阶段 5：贴图
1. **烘焙 alpha 细节**：作者贴图常把网纹/镂空/线条画在 alpha 通道（Blender 预览时预乘显示），游戏不透明渲染会丢失 → 用 PIL 把 RGB×alpha 预乘后存不透明版。检查方法：统计 alpha 半透明像素占比。
2. **合成叠层**：Unity 里靠材质叠层的贴图（如  补丁只有三个色块），游戏里需预先合成：PIL `Image.alpha_composite(base, overlay)`。
3. **texconv 转 DDS**：颜色 `-f BC7_UNORM -srgb`，法线 `-f BC5_UNORM`。注意新版本格式名要写全称。
4. **DDS → .tex**：把 .dds 拖进 Blender 3D 视图（4.1+ 支持），插件自动转 .tex（插件算子在后台模式会崩，自己按格式写更稳，见"二进制格式速查 / .tex"）。
5. .tex 放 `nativePC\<模组贴图目录>\`，文件名与 mrl3 里引用的路径对应。

### 阶段 6：mrl3 材质对接
两种方式：
- **插件面板改**（推荐）：导入 mrl3 → 侧边栏面板列出全部材质 → 贴图列表直接改路径字符串 → 导出 mrl3。纯 UI 操作无二进制风险。
- 属性清单（每个我们用到的材质）：
  - `AlbedoMap` = 自己的贴图路径；`EmissiveMap` = **与 Albedo 相同**（伪发光套路）
  - `BaseMapFactor` RGB ≈ 0.4；`EmissiveMapFactor` ≈ 1.5（真实光照则 1.0 / 0）
  - `ColorMaskMap` → `Assets\default_tex\null_black`（去掉调色染色）
  - `RMTMap` → `Assets\default_tex\null_RMT`
  - `Metalic` 保持 1.0（配合上述配方）——**单独把它改 0 而保留发光配方会变暗**
- 身体/脸等"空法线"部位 NormalMap 指回 `assets\NM`（空的法线贴图），别指向彩色图。

### 阶段 7：打包安装
`05_导出成品\nativePC\` 保持与基壳相同的相对路径结构（pl/f_equip/pl040_0000/{body,arm,wst,leg}/mod/... + 贴图目录），模组管理器/Fluffy 安装。

## 排错速查表

| 症状 | 原因 | 修法 |
|---|---|---|
| 模型整体粉/洗色 | Emissive 指向了别人的贴图 | EmissiveMap = 自己的 Albedo |
| 整体死黑 | 关了 Emissive 但 BaseFactor 还是 0.3 | Base=0.4 + EmiF=1.5，或 1.0/0 |
| 手套/金属件花屏 | Metalic=1.0 反射环境 | 按配方走（别单独改 Metalic） |
| 网袜纯白/镂空丢失 | 网纹画在 alpha 通道 | 预乘烘焙进 RGB |
| 部件游戏里乱飘/后坠 | 权重在物理链骨上 | 改挂真骨（Blender 里测不出来） |
| 部件不跟骨骼 | 供体覆盖范围不足拿错权重 | 换身体皮肤当供体重绑 |
| 下裆/裙摆被大腿拉宽 | 皮肤类权重分挂两条大腿 | 该区域改挂骨盆级静态叶子骨 |
| 黑模/隐身 | 材质槽名与 mrl3 对不上 | 材质名对齐 |
| 游戏加载崩溃 | mrl3 二进制损坏 | 恢复备份，用插件面板重改 |
| Blender 里白模 | 观感材质被换成导出占位材质 | 跑恢复预览材质脚本（导出前记得再切回） |

## 脚本制作方法

### 安全模式（每脚本必备）
```python
import bpy

try:
    bpy.ops.object.mode_set(mode="OBJECT")   # 任何模式下运行都安全
except RuntimeError:
    pass
```
1. **先切物体模式**：编辑/姿态模式下改顶点组 = Blender 秒崩。
2. **多用户网格先独占**：`if obj.data.users > 1: obj.data = obj.data.copy()`（否则改到共享数据块）。
3. **先收集后执行**：遍历顶点/顶点组时增删它们 = 崩溃。先建 `moves = {vert_index: weight}` 字典，再统一执行。
4. **幂等**：脚本重复运行结果一致（先清后建）。
5. **弹窗反馈**（用户不看控制台）：
```python
def draw(self, context):
    self.layout.label(text="完成 N 项", icon="CHECKMARK")
bpy.context.window_manager.popup_menu(draw, title="结果", icon="INFO")
```
6. 详细日志走 `print()` → 用户按 **Window ▸ Toggle System Console** 查看。
7. **跑脚本前 Ctrl+S**——崩溃/出错可回档。

### Blender 4.2 API 坑（实测踩过）
| 操作 | 正确写法 |
|---|---|
| Data Transfer 传权重 | `mod.use_vert_data = True; mod.data_types_verts = {"VGROUP_WEIGHTS"}`（不是 `data_type`） |
| 最近面插值 | `mod.vert_mapping = "POLYINTERP_NEAREST"`（UI 名 NEAREST_FACE_INTERPOLATED 不是 API 名） |
| 层选择 | 4.2 已移除 `layers_select_src/dst`，默认值即所需，**不要设置** |
| 修改器排序 | 没有 `move_to_index`；按添加顺序排即可 |
| KDTree | `from mathutils.kdtree import KDTree`（在子模块，不在 mathutils 顶层） |
| BVHTree | `from mathutils.bvhtree import BVHTree`；`FromPolygons(verts, polys)` |
| 约束 | 在 `pose.bones[i].constraints`，编辑骨 EditBone 没有 |
| 形态键材质 | `mat.blend_method` 有效但 `shadow_method` 已移除；alpha_threshold 在材质设置不在 BSDF |
| 编辑骨权重 | 静默操作无视觉反馈，用顶点组"选择"按钮验证 |

### 重活模式：供体重绑（BVH 贴面插值）

```python
tree = BVHTree.FromPolygons([v.co.copy() for v in dverts],
                            [tuple(p.vertices) for p in donor.data.polygons])
# 每顶点：世界坐标 → find_nearest → 所在面三顶点权重按重心坐标混合

```
要点：供体权重预取成 `[{组名:权重}, ...]` 列表；目标顶点世界坐标 `obj.matrix_world @ v.co`。

### 已知崩溃陷阱 ⚠️
1. **接力脚本崩溃**：一个脚本重建全部顶点组后，紧接着跑另一个改顶点组的脚本 = **Blender 秒崩**（内部数据结构失效）。对策：合并为单个原子脚本，或改用 **UI 手动操作**（编辑模式指定/移除永不崩）。
2. **`紧身衣重绑+髋骨修正.py` 已知必崩**（合并版也崩）——不要使用；替代方案：先跑重绑脚本，再用 **UI 手动**把下裆顶点从大腿组"移除"、指定到骨盆骨（MhBone_066 这类胯部叶子骨）。
3. **mrl3 二进制直改**：早期以为高危，第二次实战已把格式完全反解并逐字节验证 → **就地打补丁是安全高效的**（条目定长，文件大小不变），而且能顺手改 CB 里的渲染参数（插件面板改不了的部分）。三个前提：① 资源码必须从 `master_material_dict` 按资源名反查，**不能写死**；② 复用贴图槽位时要避开在用的槽；③ 每次从 `.bak` 原始备份重算，保证幂等。详见"二进制格式速查 / mrl3"。
4. 崩溃后：文件 ▸ 恢复 ▸ 上次会话；脚本幂等可重跑，但**跨脚本有顺序依赖**（见下）。

### 脚本顺序依赖（重要）
同一网格上的权重类脚本**互相覆盖**，只能按序执行一次：
```
腿部重绑（皮肤供体） → 紧身衣重绑（皮肤供体） → [髋骨/骨盆修正：UI 手动] → 材质名对齐 → 导出
```
后跑的会抹掉先跑的。导出前只需：材质名对齐 + 修复导出问题（松散顶点/UV）。

### 实用脚本模式
- **逐个放映辨认网格**：modal operator，方向键循环隐藏/显示+`view_selected`对焦+FONT 文字标签，ESC 恢复。
- **GUID 反查**：unitypackage 里 asset.meta 的 `guid:` 与材质 YAML 里的 `guid: xxx` 匹配 → 得到"材质槽→贴图路径"。
- **fbx 结构解析**：二进制 FBX 7400，节点头 13 字节（end_offset/num_props/prop_len/name_len 各 4+1），属性区首属性是 int64 ID，名字在字符串属性 `名字\x00\x01类型` 里。
- **选中即处理**：批量类脚本用 `bpy.context.selected_objects` 限定范围，防止误伤场景里其他模型。

## 二进制格式速查（第二次实战反解，全部逐字节验证过）

> 原则：**动手改二进制之前，先用"往返验证"证明你懂这个格式**——拿一个现成文件，按你的理解重建一遍，要求逐字节一致。做不到就别写。

### .tex（贴图容器）

```
结构 = 184 字节固定头 + (8 字节 × mip 级数) 偏移表 + DDS 负载
DDS 负载 = .dds 文件去掉它自己的文件头（128 字节，或带 DX10 头时 148 字节）
文件长度校验：184 + 8*mips + len(dds) - ddsHeaderLen  ← 必须完全相等
```

固定头字段（小端）：

| 偏移 | 值 | 含义 |
|---|---|---|
| 0 | `54 45 58 00` | magic `TEX\0` |
| 4 | 0x10 | 头尺寸标记 |
| 16 | 2 | 常数 |
| 20 | mip 级数 | 2048→12，4096→13，1024→11（完整 mip 链） |
| 24 / 28 | 宽 / 高 | |
| 32 | 1 | 常数 |
| 36 | 格式 | **22=BC1 24=BC4 26=BC5 30=BC7 7=R8G8B8A8** |
| 40 | 1 | 常数 |
| 44~119 | 标志位 | 与尺寸/格式**无关**（在 4096/2048/128 三种尺寸和 BC7/BC5 两种格式上验证过） |
| 120 | 宽（重复） | |

偏移表：从 184 开始，每级 mip 8 字节 = `(该级数据在文件里的绝对偏移 u32, 0 u32)`，依次累加各级大小。

- 颜色贴图 → `BC7_UNORM` + 完整 mip；法线 → `BC5U`
- PNG→DDS：`texconv.exe -f BC7_UNORM -y -o <outdir> <file.png>`（不加 `-m` 即全 mip 链）
- **实测对拍**：用这个结构重建 milfy 工程里 10 个现成 .tex（4096²/2048²/128²，BC7+BC5），全部逐字节一致。
- 也可以走插件：把 .dds 拖进 Blender 3D 视图自动转 .tex；**但插件那个 .tex 算子在后台模式会崩**（EXCEPTION_ACCESS_VIOLATION），自己写反而更稳。

### mrl3（材质表）

```
文件头 40 字节：magic 5001805@0, version 12@4, timestamp u64@8,
                materialCount@16, textureCount@20,
                textureOffset u64@24, materialOffset u64@32
贴图项 272 字节：路径字符串（ASCII，256 字节字段）在 +16
材质项  56 字节：typeID@0, nameHash@4, mmtrHash@8, shaderHash@12, blockSize@16,
                surfaceCoef(2B)@20, resourceCount(u16, 实际资源数=值÷2)@22,
                alphaCoef(4B)@24, ..., blockOffset u64@48
资源项  16 字节：resCode@0, resHash@4, resValue@8, unkn@12
```

- **材质名**：`various_hash_dict.json`（26 万条）用 nameHash 反查 → `Ch_Standard_Mt__1` 这种
- **资源名**：`master_material_dict[str(mmtrHash)]["resourceDict"][str(resHash>>12)]["name"]`
  → `tAlbedoMap__disclosure` / `tNormalMap__disclosure` / `tRMTMap__disclosure` / `tEmissiveMap__disclosure` / `tColorMaskMap__disclosure` / `CB*`
- **贴图资源**（名字以 `t` 开头）的 `resValue` = 贴图表里 **1-based** 索引 → 写 `槽位+1`
- **CB（常量缓冲）** 的 `resValue` = 该材质资源块内的字段起始偏移；字段名+类型来自 `property_dict.json[code]["fields"]`，按顺序读
- 定长条目 → **改路径/改数值都不改变文件大小**，可以就地打补丁
- 贴图槽位复用：把"没人用的槽"的路径字符串改写成自己的贴图名（256 字节定长字段），再让材质指过去

**关键 CB 参数**（PL_Mt 主材质）：

| 参数 | 含义 | 经验值 |
|---|---|---|
| `fBaseMapFactor__uiColor` | 底图倍率 | 1.0 过曝 → **0.4**（伪发光配方） |
| `fEmissiveMapFactor__uiColor` | 自发光倍率 | 1.5；**0 = 关掉发光** |
| `fSpecular__uiUNorm` | 镜面倍率 | 正常 1.0；`Ch_Pl_Standard_Mt__0X` 一族是 **0.0** |
| `fMetalic` / `fRoughness` | 金属/粗糙倍率 | 都保持 1.0（让 RMT 贴图说了算） |
| `fTranslucency` | 透光 | 0.3 |

### ctc（布料物理）

```
文件头 80：magic 4412483@0, version 28@4, unkn1@8, unkn2@12,
           chainCount@16, nodeCount@20, 24~79 全是常数
链头 80  ：nodeCount u32@0, colFlag u8@4, chaFlag u8@5, colAttr@8, colGroup@12,
           colType@16, gravity f32×3@32/36/40, ?@44, damping@48, transForce@52,
           spring@56, limit@60, friction@64, reflect@68, windRate@72,  0xCD 填充@76
节点 112 ：matrix 16×f32@0, isParent u16@66, colShape u16@70,
           BoneFunctionID u16@72, ?@76, colRadius f32@80, angLimit@84,
           widthRate@88, mass@92, elastic@96
```

**长度自检**：`80 + chainCount×80 + Σ(nodeCount)×112 == 文件长度`。对不上就是理解错了。

**节点矩阵约定（最难的一环，已反解）**：

- 矩阵**没有平移分量**（位置来自 mod3 骨骼表）
- **第 0 行 = 该段骨骼方向（游戏坐标）**
- 构造方式：把方向换算到游戏坐标 `v_game = R_x(-90) · v_blender`（游戏是 Y 上、Z 前），
  求「把局部 +X 转到该方向的最小旋转 R」（Rodrigues），**存 R 的转置**
- 验证：拿现成的 48 个节点当样本，30 个可判定节点误差 **0.0000**（其余 18 个是每条链的末节点，原作者工具在那里留了单位矩阵）
- 方向取的是**节点位置**（head[k+1] − head[k]），**不是** Blender 里骨骼的朝向——导入器把链骨骨骼统一成了固定朝向（全是 +Z、长度 0.05、`matrix_local` 完全相同），所以别指望从骨骼拿方向

**追加一条链**：重建整个文件 = 新文件头（chainCount+1、nodeCount+n）+ 原有链头 + 新链头 + 按序所有节点 + 新节点。做完必须复核"原有链头/节点逐字节一致 + 文件头 24~79 未动"。

### mod3（导出器行为，务必知道）

1. **导出的是 `obj.evaluated_get(dg)` 的网格**，不是 `mesh.vertices`
   （`blender_mod3.py` 里 `bpy.data.meshes.new_from_object(obj.evaluated_get(dg))`）
   → **带形态键的网格，改 `mesh.vertices` 会被静默丢弃**，导出的是形态键结果。
   实测：靴子有 3 个形态键，Basis 与 `mesh.vertices` 差最多 3cm，前面所有"把袜子外扩"的几何改动**全部没进游戏**。
   - 检测：比较 `mesh.vertices` 与 `shape_keys.key_blocks[0].data`；或比较静止姿态下"原始 vs evaluated"的位移
   - 修法：逐顶点算 delta 加到**所有**形态键上（保留各变体键的相对差异）；或直接删掉形态键
2. 材质表每条 128 字节、名字是 C 字符串；导出器固定插入一个 `InvisibleMantlesModEmiFix` 当第 0 个材质
3. 网格用**索引**引用材质，但游戏是按**名字 hash** 去 mrl3 找的 → mod3 的材质顺序不必和 mrl3 顺序一致
4. 骨骼名必须匹配 `^MhBone_\d{3}$`，`boneCount ≤ 255`

## 跨部位穿模：权重对齐（袜子/靴子案例）

**症状**：站着不动也能看到腿从袜子/靴口顶出来，改几何（外扩袜子）怎么改都没用。

**根因**：body/wst/arm/leg 是**四个独立 mod3**共用一副骨架。袜子在 leg、腿皮在 body，
两边**权重不一致**就会在动画里错开。实测靴子的小腿段几乎全绑在"脚骨"上，
它的"脚踝过渡带"被拉成 **18cm**，而腿皮只有 **2cm**：

| 高度 | 腿皮（小腿/脚） | 靴子（改前） |
|---|---|---|
| −0.90~−0.88 | 0.00 / 1.00 | 0.28 / 0.72 |
| −0.80~−0.78 | **1.00 / 0.00** | 0.63 / 0.37 |

脚踝一转，靴壁比腿皮慢半拍 ≈1cm，正好吃掉间隙。

**诊断**：逐高度统计两边"平均权重"，看过渡带位置/宽度是否一致（这就够了，不用猜）。

**修法**：对衣物每个顶点，取**同侧**最近 K 个皮肤顶点，按距离反比（K=3、幂次 3）混合它们的权重写到衣物上；
- ✅ **没被处理的顶点必须原样保留权重**——漏掉就失去蒙皮、整块留在原地，看起来像模型炸了
- 用 Z 淡入避免在过渡区外乱改（例如 −1.00~−0.96 线性淡入）

**验证必须摆姿势（关键）**：
- 检查哪些顶点**要在静止姿态下按位置选定**，再去各个姿态下判定是否露出。用变形后的坐标选点会选到别的部位（膝一弯，靴子跑走，你却在测大腿）
- 判定：从腿顶点沿法线向外打射线，**既没打到衣物、也没打到别的遮挡物（裙子）**，才算真穿模
- 成果：踝 +40° 从 122 个露点降到 0；膝 −45°踝 −25° 从 112 降到 26

## 贴身衣物的自适应间隙

统一间隙值一定出错：实测静止时间隙最小 1.6mm、中位 14.4mm，而摆姿势时靴壁相对腿最多往里挤 16mm（但只有几十个顶点挤得厉害）。

**做法（逐顶点）**：
1. **配对角点**：静止时给每个衣物顶点配一个最近的皮肤顶点，之后一直用这一对
2. 各姿态下量 `Δ = 点对距离(姿态) − 点对距离(静止)`，取最小值 → `need = −min(Δ) + 余量`
3. `目标 = max(need, 下限)`，沿皮肤法线把顶点收到目标间隙；只收不放（已经在里面的顶出来）

⚠️ **别用"到皮肤表面的有符号最近距离"当判据**：最近特征会跳（脚踝转到 55° 时最近点从小腿跳到脚掌），
会算出 −18mm 的假错位，逼你把间隙留到 18mm。点对法只有 −4.9mm，才敢收到 5mm。

## 给刚性挂件加物理（尾巴完整流程）

原状：尾巴 582 顶点 100% 焊在骨盆骨上 → 只会跟着腰硬转。三步：

1. **加骨骼**（`C21`）：PCA 求主轴 → 按长度切 N 段求中心线 → 建 `MhBone_xxx`（选**四个骨架都没占用**的号）
   - 骨骼号名字必须 `^MhBone_\d{3}$`；先扫一遍四个骨架取交集
   - **照抄现有链骨骨骼的形态**：走向 +Z、长度 0.05、roll 0 → `matrix_local` 与已验证能用的发链骨**完全一致**（差 0.000000）
2. **重绑权重**：按顶点在链条上的弧长参数 u 用帐篷函数平滑分配到各骨（每骨影响约 150~240 个顶点）
3. **追加物理链**（`C22`）：把链头和节点都拿现成链当模板复制，只改 nodeCount / gravity / damping / spring / BoneFunctionID / 节点矩阵

**静止形状和物理参数是两回事**：
- "站立时竖直垂下"改参数是治不好的——尾巴**网格本身**就朝后下方长（各段比水平线低 35°/83°/51°/50°/31°），重力一拉自然垂
- 想要"微微上翘"就**改静止形状**：绕根部渐进取直 `θ(u) = θmax · smoothstep(0, 0.35, u)`，前 35% 几乎不动保证根部还长在身上（实测只有 1 个顶点从"嵌入体内"变成露出，深度 0.5mm）
  → 角度 35/83/51/50/31 → **14/32/13/12/−7.5**（尖端微微上翘）
- 改完形状要**重跑第 1、2、3 步**（骨骼位置、权重、节点矩阵全部跟着新形状重算）
- 重力是**游戏坐标的向量**：① 发链用 `(0, −250, 0)`；挂件要悬垂感就得弱很多（尾巴 −90）
- 弹性（弹跳）→ 调 `spring`（低 = 不弹）；"跑动时不飘" → 调 `transForce`（学裙子的 0.35 更飘）

## 材质观感：亮度 / 发光 / 镜面

**权威依据**：用户自己的**套装预览 .blend** 里就写着"每个网格该配哪张贴图"（网格→材质→图片）。
比任何猜测都准，开一次 dump 出来即可。也能从源素材的 Unity prefab → `.mat` → `_guids.txt` 反查。

**伪发光配方**（二次元模组通用）：`BaseMapFactor=0.4 + EmissiveMap=Albedo + EmissiveMapFactor=1.5`

**两个反直觉的坑（都踩过）**：

| 症状 | 真相 |
|---|---|
| 蝴蝶结"发光严重" | **不是发光**。它的贴图平均 sRGB≈240，而军装藏青只有它的 1/17 → 阳光下当然晃眼。**无光照正常、只在光照下亮 = 不是自发光**（自发光在暗处也亮） |
| 换成黑贴图后**更亮** | 自发光是按**发光贴图的 alpha**取掩码的：`null_black` 是黑但 **alpha=1**（满掩码）；原来的白丝带 alpha 反而低。游戏专门有 `Assets\default_tex\null_black_alpha_BM`（黑且 alpha=0） |

**排查顺序**（从便宜到贵）：
1. **量贴图像素**：把贴图当图片读出来统计平均 RGB/alpha（Blender `bpy.data.images.load` 也行）。
   接近全白（>220）的贴图就是全模最亮的表面，要么换色、要么压 `fBaseMapFactor`
2. **看是不是发光**：暗处也亮 → 发光；只在亮处亮 → 漫反射/镜面
3. **查 `fSpecular`**：`Ch_Pl_Standard_Mt__0X` 一族是 **0.0**（高光项被乘 0，光能全落到漫反射），
   深色件看不出来，纯白件就过亮 → 改成 1.0 与其它部位对齐
4. **改色/换色**：作者素材通常自带多色版本（某头发素材 丝带就有 14 种色），直接换贴图最省事、也最贴合原作者设计
5. 关发光：发光贴图 → `Assets\default_tex\null_black_alpha_BM`，**同时**把 `EmissiveMapFactor` 写 0（两条路一起断，不依赖对掩码机制的猜测）

**亮度修正**（照抄用户上个工程已验证的）：`Base 0.3/0.2/1.0 → 0.4`；`EmissiveFactor 3.0/50.0 → 1.5`

## 验证方法论（比写脚本更重要）

1. **验成品，不验工作目录**：直接解 zip / 把成品 mod3 重新导入 Blender，确认"装进去的东西"对
   （期间就靠这一条发现"改了 blend 却根本没进游戏"）
2. **新写二进制格式前先做往返验证**：用你的理解把现成文件重建一遍，要求逐字节一致
3. **改前改后逐字节 diff**（以原始 `.bak` 为基准），把差异打印成表
4. **打补丁脚本必须幂等**：从 `.bak` 原始备份重算再写回（当补丁依赖"原始值"时尤其必要——
   例如把 `3.0` 改成 `0.0`，跑第二遍就在已改过的文件里找不到 `3.0` 了）
5. **每一步都把关键数字打进日志**：权重分布、间隙分布、长度自检、字节一致性——出问题时不用重新现场勘查
6. **搭一条一键流水线**（`C10_一键收尾.py` 那种）：13 步、全幂等、失败即停并打印上下文，
   一次迭代 30 秒。这是后面能快速试错的前提
7. 昂贵的贴图转换加 **mtime 跳过**；但注意 `Copy-Item`/`shutil.copy2` 会**保留原时间戳**，
   用"比源文件新就跳过"的逻辑时要意识到这点

## 贴图 alpha：脸/身体"斑驳暗影"的真正原因（第三次实战最大的坑）

**症状**：游戏里脸上（集中在嘴、鼻）出现斑驳的、像影子一样的暗块；**光照下明显、阴影里看不见**；
Blender 里看不出来（导入器把材质换成了黑色占位，只能靠游戏或另做渲染验证）。

**根因（每一条都是量出来的，不是推测）**：

1. 作者贴图的 alpha 是**覆盖蒙版**，不携带颜色：脸 4096² 里岛内 21.5% 的像素 `alpha<250`，
   其中 **`alpha=0` 的像素 RGB 100% 是纯白 (255,255,255)**（实测 253 万个像素无一例外）。
   岛内还有 14.4% 的面积是"整块被 UV 覆盖、整块全透明"的**成片**空白（不是抗锯齿细边）。
2. 脸的材质是"自发光为主"的画法（`fEmissiveMapFactor` 要调到 3.0 脸才不发黑），
   而**发光贴图就是 albedo 本身**——于是 alpha=0 的 texel 拿不到自发光、旁边的拿 3 倍，
   光照下就是一块块斑驳暗块，位置正好落在蒙版最密集的**嘴/鼻小岛**。这一条把"为什么只在嘴鼻、
   为什么只在光照下"全解释通了。
3. 图集空白（岛外 23%、身体 31%、头发 29%）在 mip 过滤时会渗进小岛：白渗=变亮；
   若材质按 RGB×alpha 取，就是白×0=**黑**——即"暗影"。

**正确处理：三条一起做，缺一不可**

| 步骤 | 做法 | 为什么不能省 |
|---|---|---|
| 蒙版拉平 | alpha 全置 255 | 不透明渲染用不上 alpha；留着会被挖洞/当掩码/相乘 |
| 空白填充 | 岛外 **和** 岛内 `alpha<250` 的像素，用**最近的岛内不透明像素**颜色填满（8 邻域生长，1/4 分辨率 96 轮 ≈ 全分辨率 384 像素射程） | 只置 alpha=1，空白区仍是白的；**只做预乘会变成黑的**（白×0=黑），比原来更糟 |
| 已画像素不动 | `alpha≥250` 的像素 RGB 原样保留 | 保住美术内容 |

- **别把"预乘 alpha"当万能药**：只有透明区的 RGB 本身承载颜色（"墨"画在 alpha 上）时预乘才对。
  本例透明区 RGB 是纯白＝没有内容 → 预乘只会把空白变黑。
  **先量一下 `alpha<0.5` 区域的 RGB 均值再决定用"填充"还是"预乘"**。
- **对照组价值极高**：用户上一个 mod（milfy）把 alpha 烘成了 1（源 0.7509 → 成品 1.0000），
  所以从没出现这个斑驳；我这次直接用原始 PNG 就中招。**做新 mod 时先看一眼参考 mod 的成品贴图
  与源贴图差在哪**，比凭空推理快得多。
- 顺带确认：容器格式没问题。把生成的 `.tex` 与**已经跑通过**的参考 `.tex` 做
  46 个头部 u32 + mip 偏移表 + 文件长度逐字段对拍，全部一致 → 嫌疑范围直接缩到图像内容。

**光栅化 UV 的坑（差点把贴图涂烂）**：UV 岛有镜像的，三角形绕序正负都有
（实测 blond 74%、Body_Base 26% 的三角形是负面积）。用固定符号做"点在三角形内"判定会**整片漏掉
镜像岛**，漏掉的区域会被当成空白涂抹——第一版烘焙就因此把头发 55%、身体 23% 的贴图糊掉了。
必须按**每个三角形自己的有符号面积**决定判定方向（覆盖率 12% → 67%）。

## 精简成品包：哪些贴图能删（活槽法）

不要按文件名猜，也不要只看"贴图槽里有没有这个名字"——**槽位存在 ≠ 有用**。判定链：

1. **mod3 实际用到的材质名**：mod3 里材质名是 ASCII 明文，正则
   `Ch_(?:Pl_)?Standard_Mt_[0-9_]*` + 结尾 `\0` 就能取出（`C0_替换成品包.py` 用的就是这招）
2. **材质名→哈希必须查游戏字典**（`various_hash_dict.json`）：MHW 的材质名哈希**不是 CRC32**。
   我按 CRC32 匹配时算出来的"活槽"数是 0
3. **每个部位的 mrl3 都带同一套 34 个材质**，但只有该部位 mod3 用到的才算"活"
   （用全局材质集合判断，会把别的部位的死槽当成活的，结果一张都删不掉）
4. 材质项 56B：`nameHash@4, mmtrHash@8, blockSize@16, resourceCount u16@22, blockOffset u64@48`
   → 资源项 16B：`type@0, hash@4, resValue@8`；`resValue` 落在 `1..贴图槽数` 时
   表示"第 resValue 个贴图槽"（1 起）。遍历条数用 `resourceCount // 2`
5. 资源名反查：`master_material_dict[str(mmtrHash)]["resourceDict"][str(resHash>>12)]["name"]`
   → 得到 `tAlbedoMap / tEmissiveMap / tNormalMap / tDetailNormalMap / tColorMaskMap / tFurMap /
   tFurVelocityMap / SSAlbedo …`

**落地效果**：只有活槽指到的文件才留。pl040_0010 实测 246 MB → 139 MB
（清掉 17 张共 107 MB 的遗留贴图），zip 95 MB → 47 MB。
理论依据：**mod3 没引用的材质，游戏根本不会实例化，它的贴图永远不会被加载**
（用户上一个 mod 的 mrl3 里本来就有一堆指向不存在文件的槽，照样正常运行）。

**两个反直觉的细节**：

- `.bak*` 备份**不要**移出 `nativePC`——C7/C11/C22/C25 的幂等重算要读它们。正确做法是留在原地，
  **打包时排除**；并且把打包逻辑集中到一个 `C33_打包zip.py`，不要再在流水线里内联一份
- 游戏自带贴图（`Assets\default_tex\null_black` 这类）**路径不能加模组文件夹前缀**，
  否则会指到 `nativePC\<模组目录>\Assets\...` 这种不存在的文件（这个洞是被反向验收脚本抓出来的）。
  而且要用捐体 mrl3 里**本来就出现过的名字**（`null_black`/`null_RMT`/`null_NM`），别自己编
  （我编的 `null_black_alpha_BM` 实测在捐体 mrl3 里出现 0 次）

## 打包前值得照抄的验收脚本

- **反向检查**：把"活槽 → 文件"的关系倒过来验一遍——每个活槽指到的文件必须同时存在于**磁盘和 zip**。
  这一条直接抓出了"游戏贴图路径被加了模组前缀"的洞
- **CRC 比对**：zip 里每个条目与磁盘文件 CRC32 一致（32/32 ✓）
- **从 zip 里解出贴图再验内容**：确认 zip 内 `Face_Base.tex` 的 mip0 载荷与 texconv 的产物逐字节一致
  —— 证明"修好的那张图"确实进了包，而不是只在工作目录里
- 每张贴图都打印"被哪些材质的哪个资源名指向"，出问题时一眼看出该删不该删

## 未解决问题：裙子与腿的碰撞

**现状**：这是唯一没能两全的地方，留给后来者。

- **开碰撞**（裙链 `colFlag=4` + 腿碰撞体半径放大到 3.5）：裙子被腿顶得大幅上翘乱飘，腿反而更容易穿出来
- **关碰撞**（`colFlag=0` + 腿碰撞体还原 2.0）：裙子垂坠自然，但腿会穿过裙子
- 已试过：统一裙链参数（重力/阻尼/弹簧）、腿碰撞体半径 2.0/3.5、彻底关碰撞
- **没试过的方向**（供参考）：
  1. **碰撞体半径取中间值**（2.0~3.5 之间逐节点调），别一把全改
  2. 调 `colGroup` / `colAttr`，只让大腿参与碰撞、小腿不参与
  3. 对比基壳**原始 ctc**里的值（备份还在 `f_wst040_0010.ctc.bak*`）——那套参数是给基壳自己的裙子调过的，是最好的起点
  4. 降低裙链的 `transForce` / 提高 `spring`，让裙子不那么容易被顶飞
  5. 检查裙子的内/外层顶点权重分配（内层跟腿、外层跟裙链？）
  6. 请教别的作者——这条最省时间，用户也是这么打算的

> 记录这一节的用意：**把"试过什么、为什么都不行"写清楚**，比留一堆看似可行但已证伪的方案更有价值。

## 贴图色彩空间：最容易误判成"材质错位"的一类回归

**症状**（用户原话）："袜子上部有一圈变成黑色，本来该都是白色"、"裙摆本来环绕下沿的白色条带上下错位"。
第一反应会去查 UV / 材质指向 / 图集填充 —— **实测全不是**：UV 没动、
mapping 907 条一条没变、军装贴图在它自己的 UV 区域内与他满意的版本**逐像素差 0.00**。

**真因**：同一张图案，**存 sRGB 原值**还是**sRGB→线性**，深色区差别巨大
（藏青 sRGB 60 → 线性 12；sRGB 168 → 线性 100）。白/深色边界在游戏里看起来就"移位"了，
原本淹没在深色里的暗纹也会显出来（＝袜子那圈黑、裙摆白条错位）。

**怎么定位（照抄这套流程）**：
1. 找到**用户说没问题的那一版 zip**，把里面同名 `.tex` 解成 PNG
2. 和「你的源图」「源图线性化」两版各比一次平均差，差小的那个就是它的色彩空间
   （实测：军装 54.05 vs **0.27**；毛皮 38.8 vs **5.0**；脸 12.99 vs 52.5）
3. **逐张判定，不要一刀切**：同一个包里 Body/Face/blond/ribbon 是原样、Hair/军装是线性化
   （素材来自不同作者、不同工具，历史上就是混的）
4. 用 46 个头部 u32 对拍确认容器没问题，把嫌疑锁定在**像素内容**上

**烘焙三条铁律**（`C31_贴图烘焙alpha.py` 已按此实现）：
- **只填 `alpha<250` 的空像素**（图集空白 + 岛内透明补洞 + 软边）；不透明像素一律原样保留。
  贪心地"凡 UV 岛外就填"会把作者自己画的图集空白涂掉 → mip 过滤时白条边界被推移，
  正是上面那个回归。（军装贴图 alpha 全 1，按这条规则＝一个像素都不动 ✓）
- **不做预乘**：实测透明区 RGB 100% 是纯白（不含颜色），预乘只会把已画好的像素压暗 ≤2%
- **UV 光栅化按每个三角形自己的有符号面积判定**（镜像岛实测占 26%~74%，
  用固定符号会整片漏掉镜像岛 → 覆盖面积算错 → 把有用的贴图画烂）
- **验收不变量**：改动像素必须**全部**来自 `alpha<250` —— 一句话证明"没画坏"

## 排查"斑驳阴影"这类主观问题：先做变量剥离，别连续换假设

我在脸上连试了 4~6 次都没解决，根源是一直换假设、没先把变量逐个摘掉。
正确顺序（每步都能本地复现，不必等用户装包）：
1. 解 `.tex` 确认成品里装的确实是修好的那张图（对拍 + CRC）
2. 渲染时**把贴图换成纯色**：还有斑驳 → 几何/法线/自遮挡；变干净 → 贴图
3. `light.use_shadow = False`：斑驳消失 → 阴影 acne
4. 只留主体连通分量（删补面/内壳）：消失 → 共面补面
5. 最后才怀疑 alpha / 色彩空间 / mip 过滤
**另外**：把"是不是跟着光线走"交给用户判断 —— 跟着光变＝着色/自遮挡；
死死贴在皮肤上＝贴图/几何。这一句能省掉一半假设。
**并且**：自己造的度量指标要能区分假设。我用"高通 std + 暗块占比"量了三次，
读数被脸本身画的线条和曲面明暗梯度主导，三组对照几乎一样 —— 等于没量。
指标必须先在一个**已知答案的对照**上标定过。

## 脸上的"斑驳阴影"：导入法线是坏的（实测根因）

**症状**：脸上（眼部周围最多）出现斑驳的、像遮挡阴影一样的暗块；正面光照下明明没有遮挡也有
阴影；头顶光下低头时会"融入"真实阴影；**把贴图换成纯色后依然存在**。

**定位顺序（前四条依次是否掉的，第五条才是答案）**：

| 假设 | 测法 | 结论 |
|---|---|---|
| alpha 蒙版 | 脸上 alpha 全去掉 + 透明区补肤色（改了 384 万像素） | 无变化 ✗ |
| 阴影 acne | 同机位 `light.use_shadow=False` 对比 | 无变化 ✗ |
| 共面补面 | 只留脸的主连通分量再渲 | 仅 -7% ✗ |
| 两层几何抢像素 | 自发光材质 + 每个连通分量一个纯色，看颜色是否互相咬合 | 洋红像素 93.5% 的邻域也是洋红（成片）= 正常露出的皮肤 ✗ |
| **着色法线** | `mesh.corner_normals` vs `mesh.vertex_normals` 的夹角 | **脸平均 29.15°，>90°（朝里）占 7.52%** ✓✓ |

同一套量法下身体/头发/丝带都只有 0.01~3° —— **只有脸是坏的**，正好对应"只有脸上有斑驳"。

**修法（最小改动，实测有效）**：只对脸执行
`bpy.ops.mesh.customdata_custom_splitnormals_clear()` → 平均夹角 29.15°→1.92°，
`>90°` 7.52%→**0.05%**，与正常部位齐平。

- **不要**顺手做 `normals_make_consistent`：它会**翻转面绕序**（D99 实测面索引哈希变了），
  对"正反两面都在同一个网格里"的薄壳脸皮是有风险的改动，而且并不需要
- **不要**为了修法线进出 EDIT 模式：进出编辑模式会动到网格数据（坐标哈希变了）
- 验收三件套：**坐标哈希不变 ✓、面索引(含绕序)哈希不变 ✓、`>90°` 占比降到 ~0 ✓**

**教训**：从 unitypackage / 别人的 mod 导入的网格经常带**损坏的 custom split normals**。
它不改变贴图、也不改变几何坐标，只让光滑表面出现斑驳明暗，而且**只在有光时看得出来** ——
极容易被误判成"阴影问题"而跑去改贴图、改几何、改碰撞。**做任何 mod 前先量一遍
`corner_normals vs vertex_normals`**，十分钟能省掉几天。
（顺带：`>90°` 那一栏才是硬证据 —— 法线朝里绝不可能是美术有意为之。）

## 最贵的一条教训：别改作者配好的形状（袜子穿模的完整复盘）

**症状**：袜子与小腿有明显间隙，且穿模出鞋子；用户说"很稳定，不管怎么动都穿"。

**我走过的弯路（按顺序，全是错的）**：
1. 用"最近鞋点法线点乘"判断里外 → 三版修法（全局腿轴径向收 / 沿鞋面法线塞 / 逐层内壁收）
   **都把计数改得更差** → 说明判据方向是反的（鞋内壁法线朝内）
2. 换"射线穿越奇偶"判据 → **鞋是开口壳，奇偶判据根本不成立**
3. 全部改动都在**静止姿势**下测量 → 但用户看到的是动态，我一度以为是权重问题
4. 最后用渲染图（袜子红/鞋蓝）出图给用户看 → 用户说"红色**细碎地**出现在蓝色里" ——
   **那其实是紫红(magenta)像素**（红蓝逐像素抢深度混出来的），我一直在数纯红/纯蓝 → 判据再次为空
5. 更致命：我把几何改了 5mm、41mm，**渲染图逐像素完全相同** —— 原来是移过去的点被鞋挡住了，
   我的"改动→复测"回路**从来没被标定过**，等于四版盲改

**真正的解法（用户一句话点破）**：
> "还原成最开始的样子，也就是没有放大袜子的时候"

把袜子按最早备份的坐标还原（只动袜子、同步形态键），**任何动作都不穿模了**，而且间隙也没有了。
根因是**我自己的流水线**：`C7 袜子几何外扩` + `C20 袜筒贴身化` 把作者按这套衣服/鞋配好的
原始形状改掉了，一改就破坏配合。实测数据（袜筒半径）：原始 r_med 0.0887 / r_max 0.1368，
被我改后 0.0893 / **0.1460**（最粗处 +9mm）。

**固化下来的规矩**：
- 形状是作者按整套服装配好的 → **不要为了别的毛病去改它**；有毛病先怀疑自己加的步骤
- 流水线里加了 `C44 袜子形状还原`（从原始备份读坐标写回，幂等）作为**兜底**，
  并**停用 C20**；停用理由写在 `C10_一键收尾.py` 的注释里
- 改几何的脚本一律：**限幅 + 同步所有形态键 + 改完用同一判据复核 + 没净改善就不保存**

**关于"重合面争抢"的判据（可复用）**：两个面几乎重合时，游戏/渲染里看到的不是"红的"或"蓝的"，
而是**两者混出的中间色**（红+蓝=紫红）。所以判断"有没有 z-fighting/穿插"要数**中间色像素**，
而且必须排除轮廓抗锯齿（只统计"周围 5x5 里亮像素占多数"的面内部）。基线：面内紫红 1.4~2.6%。

**关于度量的三条硬规矩（我用四轮代价换来的）**：
1. **先标定回路再改东西**：故意做一个必然可见的大改动（挪 10cm），确认渲染/度量**会变**。
   回路不通时，所有"改进"都是噪声
2. **判据要拿已知答案的点验证**：包围盒中心该判"里"、1 米外该判"外"。
   注意开口壳（鞋口没封）用射线奇偶会失效 —— 先看物体是不是闭合的
3. **指标测不出已知现象就是指标错**：用户说"能看见穿插"，我的指标读 0.000% → 错的必然是指标，
   不该继续改几何

> ★ **另一种 alpha 用法（第十二次实战）**：如果贴图的 **RGB 是常量（std ≈ 0）、图案 100% 画在 alpha 里**
> （渔网 / 蕾丝 / 镂空），那本节这套"只填 `alpha==0` + 拉平 alpha"的规则是**破坏性的** —— 会把图案抹平。
> 那一类要的是 **`RGB × alpha` 预乘后存不透明**，见 §十二 B。

## 2. ★★ 最容易抄错的一步：排除带的判据

**症状**：描边做完，某个"贴在别的件表面上"的小件（蝴蝶结、发绳、蕾丝贴片）**整块变黑**。

**原因**：它贴在 A 的表面外仅 0.09 mm，而 A 的壳在 1 mm 外 ⇒ **它被夹在 A 的表面与 A 的壳之间**
⇒ 从外面看到的是"包在它外面的那层黑壳"。

**第一版照抄的判据**（第1套 的写法）："壳顶点离该小件的距离 < 2 mm 的壳面丢掉"。
**它在 第4套 上失败了** —— 因为**相互贴着的两件会互相吃掉壳**：
内衣被吃 61%、内裤绳 78%、绷带整片被吃光（改前 4 个件各丢 17~78% 的面）。

**改对之后的判据**（一条就够）：
> 切掉壳面 **当且仅当** `d_别件 < min(d_本体, 2mm)`
> —— 即"**别的件夹在本体表面与壳之间**"。

| 情形 | d_别件 | d_本体 | 判定 |
|---|---|---|---|
| 蝴蝶结贴在头发卡片外 0.09mm | 0.91mm | 1.0mm | **切** ✓ |
| 内衣在裙子**里面** | 间隙+1mm | 1mm | **不切** ✓（本来就不是轮廓） |
| 内裤绳贴在绷带**外面** | 0.7mm | 1mm | **切** ✓（否则绳会把绷带糊黑） |

改完丢面量：裙 **0.25%**、臂 **0**、袜 0.2%；头发件仍丢 10~18%（**卡片互相叠压**，那些区域不是轮廓）。

**另一个更干净的做法**：壳**按"源件"整体建一个**，而不是按"按材质拆出来的子对象"各建。
本版每件都被拆成 cloth+gold 两块，两块**共面** ⇒ 按子对象各建会得到两层重合壳、金饰必糊黑。

## 3. 三个静默的坑

1. **丢面后留下孤立顶点** ⇒ 导出器预检直接报 `LooseVerticesOnSubMesh`。
   必须"只保留还有面的顶点 + 重映射下标"，并把位移/权重按映射补回去（带形态键的还要补到每个键块）。
2. **描边材质会被"从 `.bak` 重算材质指向"的那一步静默抹掉**。
   `第3套` 就是这样把 `Outline_Black` 丢掉的（四个 mrl3 里都没有该条目），
   于是用户看到的模型**完全没有描边**，而所有脚本都"成功"。
   ⇒ **流水线顺序铁律：材质指向脚本（`Y3`）→ 描边材质脚本（`O2`）**；`O2` 就地打补丁、幂等。
3. **取空贴图槽时要把"只被死材质引用"的槽也算上**：`body` 的 45 个槽全都被死材质引用，
   只认"从未被任何材质引用"的槽会取不满需要的 5 个（实测报"没有可用空槽"）。
   游戏不实例化死材质（skill 已验证）⇒ 改它引用的槽对观感无影响。

## 4. 要不要给某个件做壳？——按"它有没有轮廓"判断

* **做**：厚实件（衣服、袖子、裙、袜、鞋）、**头发卡片**（卡片自身的壳能出轮廓，实测有效）
* **可以不做**：贴在别的件上的小配饰（发绳、蝴蝶结）—— 它没有独立轮廓，
  被别件的壳"绕过去"不影响观感，但**要保证它不被别件的壳糊黑**（即上面 §2 的判据）。
* **代价**：每个壳约等于本体一倍的几何（本版 20 个壳让包从 56.6 → 61.2 MB）。

## 5. ★ 一条**数值**验收判据（第 15 次实战新增，10 秒可跑）

壳建完后，**量"壳顶点到本体表面的最近距离"**：中位/p95/max 都应当 ≈ **外扩量（1.0 mm）**，
容差 ±0.0002 mm。实测 `第13套` 的帽子壳：中位 **0.9998** / p95 **1.0000** / max **1.0001 mm** ✓。
* 偏大（例如 5 mm）⇒ 顶点法线被**坏绕序**或"共面叠层"带偏（`_vnorm` 是面积加权的，一层反向的面会稀释它）；
* 偏小或负 ⇒ 壳被建到了**里面**（本件绕序普遍朝内）⇒ 描边会看不见或糊在里面。
* ★ 这条判据比"**有符号体积**"可靠得多：体积对**开口 + 离原点远**的件会给出**假信号**
  （`第13套` 的手套实测 **85% 的三角朝外、绕序正确**，体积却报 `−57.7 cm³ ⇒ !! 需查`；
  开口壳的散度定理不成立、且数值依赖原点位置）。⇒ **判绕序请用"面法线与(面心−分量质心)点乘为正的比例"。**

# 附：链条的节点该放在哪（尾巴调飘的三条，都有实测数字）

> 场景：`第4套` 用户反馈"衣服尾巴飘不起来、很沉"。改完的结论按重要性排序如下。

## 1. ★★ 弯曲的链，节点必须落在**弧线中心线**上，不能落在"根→最远点"的弦上

原来 `MaidTail` 的节点由"根 → p95 最远点"的**直线弦**均分。实测尾巴的真实中心线
（12 个段组质心连成的折线）**弧长 0.6525（预览）**，而弦只有 0.5467 ⇒ **弧比弦长 19%**，
**中段偏离弦 0.112 预览单位 ≈ 15 cm** —— 而尾巴本体的粗细远小于 15cm
⇒ **关节飘在网格外面**，物理在"一条不存在的直线"上转，看起来就是硬、沉。

**做法**：`seg_nodes(srcname, segs, n_new)` —— 取该链所有段组的**加权质心折线**，
沿弧长均匀取 n_new 个点（并在根部外推半步，使首节点落在"接在身上"的位置）。
这套代码同时服务双马尾与尾巴（同一条路径 ⇒ 不会出现"两条并行的建链代码坐标系不一致"那类坑）。

**判据**：`弧长 / 弦长` 偏离 5% 以上就该用折线。**先量这个比值再决定**，不要凭"看起来是直的"。

## 2. ★★ 节点取 `k/n`，**不是** `k/(n-1)` —— 我把这条改反过一次

* `k/n`（n=5）：节点在弧长 **0 / 20 / 40 / 60 / 80%** ⇒ 末段 20% 的顶点（尾巴的蓬松尾尖，
  占 **80% 的顶点数**）是**绕 80% 处的关节转** ⇒ 会甩 ✓
* `k/(n-1)`：末节点落在**尾尖本身** ⇒ 尾尖的 80% 顶点**绕自己转 = 不动** ⇒ 更糟

我按"末段 20% 没节点"的直觉改成了后者，重建后才发现反了（"看着像修好、其实改反了"）。
**可移植的判据**：`u` 被 clip 到 1.0 的顶点比例高**本身不是问题** ——
要问的是**末节点的位置在不在"末段顶点之前"**。

## 3. ctc 参数：挂件不要套"头发档"，按参考包比例折算

原尾巴套用 `hair` 预设。skill 里记过参考包的取值：发链重力 `(0,−250,0)`、尾巴 `(0,−90,0)`
（比例 **0.36**）⇒ 本工程发链 −112.5 对应尾巴约 **−40**。改成：

| 参数 | hair 档 | **tail 档** | 方向 |
|---|---|---|---|
| `gravity` | (0, −112.5, 0) | **(0, −45, 0)** | 小 ⇒ 不往下坠 |
| `transForce` | 0.620 | **0.720** | 大 ⇒ 跟手/拖尾 |
| `damping` | 0.055 | **0.040** | 小 ⇒ 余摆长 |
| `spring` | 0.010 | 0.015 | 略加弹 |

**★ 观感无法离线验证** ⇒ 三个数做成命令行开关（`tailgrav=` / `tailtrans=` / `taildamp=`），
让用户一句话迭代，比助手猜三轮快。

## 4. 顺带的两个工程细节

* **链骨号按"链名"固定分配**，不要"按部位顺序发号"。否则开关（如"不出衣服尾巴"）改变链条数量时，
  其余链的号会整体漂移，而 `Y4`/`Y4b` 里是硬编码列表 ⇒ 号与链错配、且不报错。
  做法：`CHAIN_FNS = {"MaidTail": [144,145,146,147,148], ...}`，创建时按名字取并断言数量一致。
* **诊断脚本的分档边界**：`u` 会被 clip 到**恰好 1.0**，分档写成 `u < lo+0.25` 会把这一批整批漏掉
  （实测尾巴少报 **549/729** 个顶点，读数看着像"中间节点没权重"）。末档必须 `<=`。
