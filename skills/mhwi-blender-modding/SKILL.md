# MHWI Blender 模组制作

本 skill 总结自两次完整实战：

1. **第一次**（替换 pl040_0000）：VRChat 角色（某角色）+ 服装（某套装）+ 头发（TwinTail）从 Unity 素材移植为 MHWI 女猎人防具模组，全程借用现成模组做"基壳"。
2. **第二次**（替换 pl040_0010）：该角色 角色（含 身体贴图）+ 某套装 军装连衣裙 + 某头发素材 丝带双马尾，body/wst/arm/leg 四部位全套重做，并下沉到二进制格式层：反解 mrl3 / ctc / tex 结构并就地打补丁、跨部位权重对齐治穿模、给尾巴补骨骼+物理链、按作者原意重挂贴图。

第二次最大的收获：**症状反复治不好时，先造一个能区分假设的测量**（射线穿模图、逐高度覆盖率表、贴图像素统计、改前改后逐字节 diff），远快于继续按"听起来合理"的猜测动手。第一次留下的"mrl3 不能写脚本直改"结论也已被推翻——格式完全反解后，就地打补丁是安全且高效的。

## 核心概念（先读这个）

1. **mod3 = 网格+骨架**，**mrl3 = 材质表**（材质名→贴图路径+渲染参数），**ctc/ccl = 物理**。四者配对使用。
2. **借壳策略**：找一个同体型的现成模组（同角色最佳），它的 mod3 里已经有游戏验证过的骨架、网格槽位、材质命名、LOD、物理链。你的工作只是"换皮"：删它的网格，放上你的网格，把权重从它的网格传给你的网格。
3. **四部位结构**：pl040_0000 下分 body/arm/wst/leg（+helm），**每部位一副独立骨架**（同一副游戏骨架的拷贝，骨骼名相同）。网格必须绑"所属部位"的骨架。基壳模组可能把奇怪的部件塞进奇怪部位（实测：外套在 arm、双马尾在 leg）。
4. **材质槽名即接口**：mod3 导出时写的是网格材质槽的**名字**，游戏拿这个名字去 mrl3 找材质。名字对不上 = 黑模。
5. **同名材质共享贴图**：两个网格用同一个材质名 = 游戏里只能用同一张贴图。需要独立贴图的网格要改到"闲置材质名"上（mrl3 里有几十个未使用的材质条目可挑）。
6. **伪发光渲染套路**：二次元模组普遍用 `BaseMapFactor≈0.3~0.4 + EmissiveFactor≈1.5~3.0（自发光贴图=底图）` 叠加出"不受光照影响"的赛璐璐感。**Emissive 指向错误贴图 = 整体被洗色**；关掉 Emissive 而不调 BaseFactor = 整体死黑；`Metalic=1.0` = 暗色镜面（手套花屏的元凶）。

## 完整流程

### 阶段 0：素材解包
- `.unitypackage` 本质是 **tar.gz**：每个资产一个 GUID 目录，含 `pathname`（原始路径）、`asset`（文件内容）、`asset.meta`（含 GUID）。
- 解包脚本：读 pathname 还原目录结构写 asset；用 asset.meta 里的 GUID 反查"材质槽→贴图文件"对应关系。
- 注意保留 `.meta` 或自建 GUID 映射表，否则反查不了。

### 阶段 1：基壳导入与对齐
1. MHW Mesh 面板导入基壳各部位 mod3（各自进入 `f_xxx040_0000.mod3` 集合）。
2. 基壳网格无贴图显示黑/白剪影 = 正常。
3. 把自己的模型（FBX）导入同一场景，**缩放对齐**：以骨盆高度对齐最准（G 缩放时锁轴，对比髋骨位置）。
4. ⚠️ 基壳骨架一根骨骼都不能删——游戏动画和 ctc 物理按骨骼名引用它们，没有权重的骨骼也可能是模拟链。

### 阶段 2：辨认基壳网格
- 网格名是 `Group_0_Sub_N__材质名` 无名氏。用"逐个放映"脚本（循环隐藏其他网格+镜头对准+大字标签）逐个辨认，记录"编号=部位"清单。
- 材质尾号（`__Mt__5` 等）可作为分组线索。

### 阶段 3：权重传递（核心工作量）
**对号表**：每个用户网格 ↔ 一个基壳供体网格。供体选择原则：
- 部位重叠的优先（袜←袜、鞋←鞋）
- 形状/覆盖范围差异大时，**改用身体皮肤（Body_base 类网格）当供体**——贴身衣物继承皮肤权重最正确（实例：原版供体是中筒袜，用户的过膝袜大腿段会拿到小腿骨权重；原版上衣只到胸部，紧身衣下摆会拿到裙摆骨权重）
- 垂坠装饰（项链/包/缎带）找同类垂坠件当供体

**传递流水线**（每个目标网格）：
1. 多用户网格先 `obj.data = obj.data.copy()`
2. 删除旧骨架修改器、清空旧顶点组（旧骨骼体系退役）
3. 清父级（CLEAR_KEEP_TRANSFORM）+ `transform_apply`（位置/旋转/缩放全应用）→ 网格数据=世界坐标
4. 加 Data Transfer 修改器：source=供体，顶点组权重，映射=最近面插值 → 应用
5. **补漏**：没拿到权重的顶点用 BVH 贴面插值从供体补（最近顶点法会在跨部位时涂抹权重）
6. 换绑部位骨架修改器
7. 把网格挪进供体所在集合（导出按集合走）

**物理链骨规则**（游戏实测教训）：
- 垂坠物（项链/包/头发/马尾/缎带）的链骨权重**保留**——游戏里布料模拟驱动，飘动是特性
- 贴腿/贴身部件（袜上段/腿环/紧身衣下摆）的链骨权重**必须改挂真骨**——Blender 姿态模式测不出来（运动学跟随），游戏里模拟一开就乱飘/后坠
- 判定方法：权重解剖脚本列出每组的"子骨数/后代数"，叶子骨成串出现=链骨

**最终修正用 Blender UI 手动做**（比脚本稳）：
- 编辑模式 + Alt+Z X 射线 + 框选/刷选顶点 → 顶点组"指定/移除"
- 裆部/下摆部件绑"骨盆级静态骨"（找叶子骨、位置在胯部、无网格绑定的那根）→ 抬腿不再拉宽
- 权重绘制模式（Ctrl+Tab）可视化检查
- 裆部皮肤左右甩：身体皮肤裆部中央窄条也改挂骨盆骨（两侧大腿内侧保留腿骨权重）

### 阶段 4：清理与导出前检查
- 删全部基壳供体网格、删自己的旧骨架（仅当无引用）
- 脚本清理：松散顶点（编辑模式 网格▸清理▸删除松散元素）、缺 UV（补空 UVMap）、多余 UV 层（mod3 只认一个）
- **材质名对齐**：把观感材质（BH_UV1 等）换成供体的官方材质名——**每次导出 mod3 前必须跑**；导完想看预览再跑"恢复预览材质"切回来
- 导出：文件 ▸ 导出 ▸ MHW Model Editor ▸ MHW MOD3，选目标集合。预检报错按提示修（松散顶点/缺UV 最常见）。"设置mod目录失败"日志无害，手动放文件即可。

### 阶段 5：贴图
1. **烘焙 alpha 细节**：作者贴图常把网纹/镂空/线条画在 alpha 通道（Blender 预览时预乘显示），游戏不透明渲染会丢失 → 用 PIL 把 RGB×alpha 预乘后存不透明版。检查方法：统计 alpha 半透明像素占比。
2. **合成叠层**：Unity 里靠材质叠层的贴图（如  补丁只有三个色块），游戏里需预先合成：PIL `Image.alpha_composite(base, overlay)`。
3. **texconv 转 DDS**：颜色 `-f BC7_UNORM -srgb`，法线 `-f BC5_UNORM`。注意新版本格式名要写全称。
4. **DDS → .tex**：把 .dds 拖进 Blender 3D 视图（4.1+ 支持），插件自动转 .tex（插件算子在后台模式会崩，自己按格式写更稳，见"二进制格式速查 / .tex"）。
5. .tex 放 `nativePC\<模组贴图目录>\`，文件名与 mrl3 里引用的路径对应。

### 阶段 6：mrl3 材质对接
两种方式：
- **插件面板改**（推荐）：导入 mrl3 → 侧边栏面板列出全部材质 → 贴图列表直接改路径字符串 → 导出 mrl3。纯 UI 操作无二进制风险。
- 属性清单（每个我们用到的材质）：
  - `AlbedoMap` = 自己的贴图路径；`EmissiveMap` = **与 Albedo 相同**（伪发光套路）
  - `BaseMapFactor` RGB ≈ 0.4；`EmissiveMapFactor` ≈ 1.5（真实光照则 1.0 / 0）
  - `ColorMaskMap` → `Assets\default_tex\null_black`（去掉调色染色）
  - `RMTMap` → `Assets\default_tex\null_RMT`
  - `Metalic` 保持 1.0（配合上述配方）——**单独把它改 0 而保留发光配方会变暗**
- 身体/脸等"空法线"部位 NormalMap 指回 `assets\NM`（空的法线贴图），别指向彩色图。

### 阶段 7：打包安装
`05_导出成品\nativePC\` 保持与基壳相同的相对路径结构（pl/f_equip/pl040_0000/{body,arm,wst,leg}/mod/... + 贴图目录），模组管理器/Fluffy 安装。

## 排错速查表

| 症状 | 原因 | 修法 |
|---|---|---|
| 模型整体粉/洗色 | Emissive 指向了别人的贴图 | EmissiveMap = 自己的 Albedo |
| 整体死黑 | 关了 Emissive 但 BaseFactor 还是 0.3 | Base=0.4 + EmiF=1.5，或 1.0/0 |
| 手套/金属件花屏 | Metalic=1.0 反射环境 | 按配方走（别单独改 Metalic） |
| 网袜纯白/镂空丢失 | 网纹画在 alpha 通道 | 预乘烘焙进 RGB |
| 部件游戏里乱飘/后坠 | 权重在物理链骨上 | 改挂真骨（Blender 里测不出来） |
| 部件不跟骨骼 | 供体覆盖范围不足拿错权重 | 换身体皮肤当供体重绑 |
| 下裆/裙摆被大腿拉宽 | 皮肤类权重分挂两条大腿 | 该区域改挂骨盆级静态叶子骨 |
| 黑模/隐身 | 材质槽名与 mrl3 对不上 | 材质名对齐 |
| 游戏加载崩溃 | mrl3 二进制损坏 | 恢复备份，用插件面板重改 |
| Blender 里白模 | 观感材质被换成导出占位材质 | 跑恢复预览材质脚本（导出前记得再切回） |

## 脚本制作方法

### 安全模式（每脚本必备）
```python
import bpy

try:
    bpy.ops.object.mode_set(mode="OBJECT")   # 任何模式下运行都安全
except RuntimeError:
    pass
```
1. **先切物体模式**：编辑/姿态模式下改顶点组 = Blender 秒崩。
2. **多用户网格先独占**：`if obj.data.users > 1: obj.data = obj.data.copy()`（否则改到共享数据块）。
3. **先收集后执行**：遍历顶点/顶点组时增删它们 = 崩溃。先建 `moves = {vert_index: weight}` 字典，再统一执行。
4. **幂等**：脚本重复运行结果一致（先清后建）。
5. **弹窗反馈**（用户不看控制台）：
```python
def draw(self, context):
    self.layout.label(text="完成 N 项", icon="CHECKMARK")
bpy.context.window_manager.popup_menu(draw, title="结果", icon="INFO")
```
6. 详细日志走 `print()` → 用户按 **Window ▸ Toggle System Console** 查看。
7. **跑脚本前 Ctrl+S**——崩溃/出错可回档。

### Blender 4.2 API 坑（实测踩过）
| 操作 | 正确写法 |
|---|---|
| Data Transfer 传权重 | `mod.use_vert_data = True; mod.data_types_verts = {"VGROUP_WEIGHTS"}`（不是 `data_type`） |
| 最近面插值 | `mod.vert_mapping = "POLYINTERP_NEAREST"`（UI 名 NEAREST_FACE_INTERPOLATED 不是 API 名） |
| 层选择 | 4.2 已移除 `layers_select_src/dst`，默认值即所需，**不要设置** |
| 修改器排序 | 没有 `move_to_index`；按添加顺序排即可 |
| KDTree | `from mathutils.kdtree import KDTree`（在子模块，不在 mathutils 顶层） |
| BVHTree | `from mathutils.bvhtree import BVHTree`；`FromPolygons(verts, polys)` |
| 约束 | 在 `pose.bones[i].constraints`，编辑骨 EditBone 没有 |
| 形态键材质 | `mat.blend_method` 有效但 `shadow_method` 已移除；alpha_threshold 在材质设置不在 BSDF |
| 编辑骨权重 | 静默操作无视觉反馈，用顶点组"选择"按钮验证 |

### 重活模式：供体重绑（BVH 贴面插值）
```python
tree = BVHTree.FromPolygons([v.co.copy() for v in dverts],
                            [tuple(p.vertices) for p in donor.data.polygons])
# 每顶点：世界坐标 → find_nearest → 所在面三顶点权重按重心坐标混合
# 腿骨权重归髋骨：混合后把腿骨组权重累加进骨盆组
```
要点：供体权重预取成 `[{组名:权重}, ...]` 列表；目标顶点世界坐标 `obj.matrix_world @ v.co`。

### 已知崩溃陷阱 ⚠️
1. **接力脚本崩溃**：一个脚本重建全部顶点组后，紧接着跑另一个改顶点组的脚本 = **Blender 秒崩**（内部数据结构失效）。对策：合并为单个原子脚本，或改用 **UI 手动操作**（编辑模式指定/移除永不崩）。
2. **`紧身衣重绑+髋骨修正.py` 已知必崩**（合并版也崩）——不要使用；替代方案：先跑重绑脚本，再用 **UI 手动**把下裆顶点从大腿组"移除"、指定到骨盆骨（MhBone_066 这类胯部叶子骨）。
3. **mrl3 二进制直改**：早期以为高危，第二次实战已把格式完全反解并逐字节验证 → **就地打补丁是安全高效的**（条目定长，文件大小不变），而且能顺手改 CB 里的渲染参数（插件面板改不了的部分）。三个前提：① 资源码必须从 `master_material_dict` 按资源名反查，**不能写死**；② 复用贴图槽位时要避开在用的槽；③ 每次从 `.bak` 原始备份重算，保证幂等。详见"二进制格式速查 / mrl3"。
4. 崩溃后：文件 ▸ 恢复 ▸ 上次会话；脚本幂等可重跑，但**跨脚本有顺序依赖**（见下）。

### 脚本顺序依赖（重要）
同一网格上的权重类脚本**互相覆盖**，只能按序执行一次：
```
腿部重绑（皮肤供体） → 紧身衣重绑（皮肤供体） → [髋骨/骨盆修正：UI 手动] → 材质名对齐 → 导出
```
后跑的会抹掉先跑的。导出前只需：材质名对齐 + 修复导出问题（松散顶点/UV）。

### 实用脚本模式
- **逐个放映辨认网格**：modal operator，方向键循环隐藏/显示+`view_selected`对焦+FONT 文字标签，ESC 恢复。
- **GUID 反查**：unitypackage 里 asset.meta 的 `guid:` 与材质 YAML 里的 `guid: xxx` 匹配 → 得到"材质槽→贴图路径"。
- **fbx 结构解析**：二进制 FBX 7400，节点头 13 字节（end_offset/num_props/prop_len/name_len 各 4+1），属性区首属性是 int64 ID，名字在字符串属性 `名字\x00\x01类型` 里。
- **选中即处理**：批量类脚本用 `bpy.context.selected_objects` 限定范围，防止误伤场景里其他模型。

## 二进制格式速查（第二次实战反解，全部逐字节验证过）

> 原则：**动手改二进制之前，先用"往返验证"证明你懂这个格式**——拿一个现成文件，按你的理解重建一遍，要求逐字节一致。做不到就别写。

### .tex（贴图容器）

```
结构 = 184 字节固定头 + (8 字节 × mip 级数) 偏移表 + DDS 负载
DDS 负载 = .dds 文件去掉它自己的文件头（128 字节，或带 DX10 头时 148 字节）
文件长度校验：184 + 8*mips + len(dds) - ddsHeaderLen  ← 必须完全相等
```

固定头字段（小端）：

| 偏移 | 值 | 含义 |
|---|---|---|
| 0 | `54 45 58 00` | magic `TEX\0` |
| 4 | 0x10 | 头尺寸标记 |
| 16 | 2 | 常数 |
| 20 | mip 级数 | 2048→12，4096→13，1024→11（完整 mip 链） |
| 24 / 28 | 宽 / 高 | |
| 32 | 1 | 常数 |
| 36 | 格式 | **22=BC1 24=BC4 26=BC5 30=BC7 7=R8G8B8A8** |
| 40 | 1 | 常数 |
| 44~119 | 标志位 | 与尺寸/格式**无关**（在 4096/2048/128 三种尺寸和 BC7/BC5 两种格式上验证过） |
| 120 | 宽（重复） | |

偏移表：从 184 开始，每级 mip 8 字节 = `(该级数据在文件里的绝对偏移 u32, 0 u32)`，依次累加各级大小。

- 颜色贴图 → `BC7_UNORM` + 完整 mip；法线 → `BC5U`
- PNG→DDS：`texconv.exe -f BC7_UNORM -y -o <outdir> <file.png>`（不加 `-m` 即全 mip 链）
- **实测对拍**：用这个结构重建 milfy 工程里 10 个现成 .tex（4096²/2048²/128²，BC7+BC5），全部逐字节一致。
- 也可以走插件：把 .dds 拖进 Blender 3D 视图自动转 .tex；**但插件那个 .tex 算子在后台模式会崩**（EXCEPTION_ACCESS_VIOLATION），自己写反而更稳。

### mrl3（材质表）

```
文件头 40 字节：magic 5001805@0, version 12@4, timestamp u64@8,
                materialCount@16, textureCount@20,
                textureOffset u64@24, materialOffset u64@32
贴图项 272 字节：路径字符串（ASCII，256 字节字段）在 +16
材质项  56 字节：typeID@0, nameHash@4, mmtrHash@8, shaderHash@12, blockSize@16,
                surfaceCoef(2B)@20, resourceCount(u16, 实际资源数=值÷2)@22,
                alphaCoef(4B)@24, ..., blockOffset u64@48
资源项  16 字节：resCode@0, resHash@4, resValue@8, unkn@12
```

- **材质名**：`various_hash_dict.json`（26 万条）用 nameHash 反查 → `Ch_Standard_Mt__1` 这种
- **资源名**：`master_material_dict[str(mmtrHash)]["resourceDict"][str(resHash>>12)]["name"]`
  → `tAlbedoMap__disclosure` / `tNormalMap__disclosure` / `tRMTMap__disclosure` / `tEmissiveMap__disclosure` / `tColorMaskMap__disclosure` / `CB*`
- **贴图资源**（名字以 `t` 开头）的 `resValue` = 贴图表里 **1-based** 索引 → 写 `槽位+1`
- **CB（常量缓冲）** 的 `resValue` = 该材质资源块内的字段起始偏移；字段名+类型来自 `property_dict.json[code]["fields"]`，按顺序读
- 定长条目 → **改路径/改数值都不改变文件大小**，可以就地打补丁
- 贴图槽位复用：把"没人用的槽"的路径字符串改写成自己的贴图名（256 字节定长字段），再让材质指过去

**关键 CB 参数**（PL_Mt 主材质）：

| 参数 | 含义 | 经验值 |
|---|---|---|
| `fBaseMapFactor__uiColor` | 底图倍率 | 1.0 过曝 → **0.4**（伪发光配方） |
| `fEmissiveMapFactor__uiColor` | 自发光倍率 | 1.5；**0 = 关掉发光** |
| `fSpecular__uiUNorm` | 镜面倍率 | 正常 1.0；`Ch_Pl_Standard_Mt__0X` 一族是 **0.0** |
| `fMetalic` / `fRoughness` | 金属/粗糙倍率 | 都保持 1.0（让 RMT 贴图说了算） |
| `fTranslucency` | 透光 | 0.3 |

### ctc（布料物理）

```
文件头 80：magic 4412483@0, version 28@4, unkn1@8, unkn2@12,
           chainCount@16, nodeCount@20, 24~79 全是常数
链头 80  ：nodeCount u32@0, colFlag u8@4, chaFlag u8@5, colAttr@8, colGroup@12,
           colType@16, gravity f32×3@32/36/40, ?@44, damping@48, transForce@52,
           spring@56, limit@60, friction@64, reflect@68, windRate@72,  0xCD 填充@76
节点 112 ：matrix 16×f32@0, isParent u16@66, colShape u16@70,
           BoneFunctionID u16@72, ?@76, colRadius f32@80, angLimit@84,
           widthRate@88, mass@92, elastic@96
```

**长度自检**：`80 + chainCount×80 + Σ(nodeCount)×112 == 文件长度`。对不上就是理解错了。

**节点矩阵约定（最难的一环，已反解）**：

- 矩阵**没有平移分量**（位置来自 mod3 骨骼表）
- **第 0 行 = 该段骨骼方向（游戏坐标）**
- 构造方式：把方向换算到游戏坐标 `v_game = R_x(-90) · v_blender`（游戏是 Y 上、Z 前），
  求「把局部 +X 转到该方向的最小旋转 R」（Rodrigues），**存 R 的转置**
- 验证：拿现成的 48 个节点当样本，30 个可判定节点误差 **0.0000**（其余 18 个是每条链的末节点，原作者工具在那里留了单位矩阵）
- 方向取的是**节点位置**（head[k+1] − head[k]），**不是** Blender 里骨骼的朝向——导入器把链骨骨骼统一成了固定朝向（全是 +Z、长度 0.05、`matrix_local` 完全相同），所以别指望从骨骼拿方向

**追加一条链**：重建整个文件 = 新文件头（chainCount+1、nodeCount+n）+ 原有链头 + 新链头 + 按序所有节点 + 新节点。做完必须复核"原有链头/节点逐字节一致 + 文件头 24~79 未动"。

### mod3（导出器行为，务必知道）

1. **导出的是 `obj.evaluated_get(dg)` 的网格**，不是 `mesh.vertices`
   （`blender_mod3.py` 里 `bpy.data.meshes.new_from_object(obj.evaluated_get(dg))`）
   → **带形态键的网格，改 `mesh.vertices` 会被静默丢弃**，导出的是形态键结果。
   实测：靴子有 3 个形态键，Basis 与 `mesh.vertices` 差最多 3cm，前面所有"把袜子外扩"的几何改动**全部没进游戏**。
   - 检测：比较 `mesh.vertices` 与 `shape_keys.key_blocks[0].data`；或比较静止姿态下"原始 vs evaluated"的位移
   - 修法：逐顶点算 delta 加到**所有**形态键上（保留各变体键的相对差异）；或直接删掉形态键
2. 材质表每条 128 字节、名字是 C 字符串；导出器固定插入一个 `InvisibleMantlesModEmiFix` 当第 0 个材质
3. 网格用**索引**引用材质，但游戏是按**名字 hash** 去 mrl3 找的 → mod3 的材质顺序不必和 mrl3 顺序一致
4. 骨骼名必须匹配 `^MhBone_\d{3}$`，`boneCount ≤ 255`

## 跨部位穿模：权重对齐（袜子/靴子案例）

**症状**：站着不动也能看到腿从袜子/靴口顶出来，改几何（外扩袜子）怎么改都没用。

**根因**：body/wst/arm/leg 是**四个独立 mod3**共用一副骨架。袜子在 leg、腿皮在 body，
两边**权重不一致**就会在动画里错开。实测靴子的小腿段几乎全绑在"脚骨"上，
它的"脚踝过渡带"被拉成 **18cm**，而腿皮只有 **2cm**：

| 高度 | 腿皮（小腿/脚） | 靴子（改前） |
|---|---|---|
| −0.90~−0.88 | 0.00 / 1.00 | 0.28 / 0.72 |
| −0.80~−0.78 | **1.00 / 0.00** | 0.63 / 0.37 |

脚踝一转，靴壁比腿皮慢半拍 ≈1cm，正好吃掉间隙。

**诊断**：逐高度统计两边"平均权重"，看过渡带位置/宽度是否一致（这就够了，不用猜）。

**修法**：对衣物每个顶点，取**同侧**最近 K 个皮肤顶点，按距离反比（K=3、幂次 3）混合它们的权重写到衣物上；
- ✅ **没被处理的顶点必须原样保留权重**——漏掉就失去蒙皮、整块留在原地，看起来像模型炸了
- 用 Z 淡入避免在过渡区外乱改（例如 −1.00~−0.96 线性淡入）

**验证必须摆姿势（关键）**：
- 检查哪些顶点**要在静止姿态下按位置选定**，再去各个姿态下判定是否露出。用变形后的坐标选点会选到别的部位（膝一弯，靴子跑走，你却在测大腿）
- 判定：从腿顶点沿法线向外打射线，**既没打到衣物、也没打到别的遮挡物（裙子）**，才算真穿模
- 成果：踝 +40° 从 122 个露点降到 0；膝 −45°踝 −25° 从 112 降到 26

## 贴身衣物的自适应间隙

统一间隙值一定出错：实测静止时间隙最小 1.6mm、中位 14.4mm，而摆姿势时靴壁相对腿最多往里挤 16mm（但只有几十个顶点挤得厉害）。

**做法（逐顶点）**：
1. **配对角点**：静止时给每个衣物顶点配一个最近的皮肤顶点，之后一直用这一对
2. 各姿态下量 `Δ = 点对距离(姿态) − 点对距离(静止)`，取最小值 → `need = −min(Δ) + 余量`
3. `目标 = max(need, 下限)`，沿皮肤法线把顶点收到目标间隙；只收不放（已经在里面的顶出来）

⚠️ **别用"到皮肤表面的有符号最近距离"当判据**：最近特征会跳（脚踝转到 55° 时最近点从小腿跳到脚掌），
会算出 −18mm 的假错位，逼你把间隙留到 18mm。点对法只有 −4.9mm，才敢收到 5mm。

## 给刚性挂件加物理（尾巴完整流程）

原状：尾巴 582 顶点 100% 焊在骨盆骨上 → 只会跟着腰硬转。三步：

1. **加骨骼**（`C21`）：PCA 求主轴 → 按长度切 N 段求中心线 → 建 `MhBone_xxx`（选**四个骨架都没占用**的号）
   - 骨骼号名字必须 `^MhBone_\d{3}$`；先扫一遍四个骨架取交集
   - **照抄现有链骨骨骼的形态**：走向 +Z、长度 0.05、roll 0 → `matrix_local` 与已验证能用的发链骨**完全一致**（差 0.000000）
2. **重绑权重**：按顶点在链条上的弧长参数 u 用帐篷函数平滑分配到各骨（每骨影响约 150~240 个顶点）
3. **追加物理链**（`C22`）：把链头和节点都拿现成链当模板复制，只改 nodeCount / gravity / damping / spring / BoneFunctionID / 节点矩阵

**静止形状和物理参数是两回事**：
- "站立时竖直垂下"改参数是治不好的——尾巴**网格本身**就朝后下方长（各段比水平线低 35°/83°/51°/50°/31°），重力一拉自然垂
- 想要"微微上翘"就**改静止形状**：绕根部渐进取直 `θ(u) = θmax · smoothstep(0, 0.35, u)`，前 35% 几乎不动保证根部还长在身上（实测只有 1 个顶点从"嵌入体内"变成露出，深度 0.5mm）
  → 角度 35/83/51/50/31 → **14/32/13/12/−7.5**（尖端微微上翘）
- 改完形状要**重跑第 1、2、3 步**（骨骼位置、权重、节点矩阵全部跟着新形状重算）
- 重力是**游戏坐标的向量**：① 发链用 `(0, −250, 0)`；挂件要悬垂感就得弱很多（尾巴 −90）
- 弹性（弹跳）→ 调 `spring`（低 = 不弹）；"跑动时不飘" → 调 `transForce`（学裙子的 0.35 更飘）

## 材质观感：亮度 / 发光 / 镜面

**权威依据**：用户自己的**套装预览 .blend** 里就写着"每个网格该配哪张贴图"（网格→材质→图片）。
比任何猜测都准，开一次 dump 出来即可。也能从源素材的 Unity prefab → `.mat` → `_guids.txt` 反查。

**伪发光配方**（二次元模组通用）：`BaseMapFactor=0.4 + EmissiveMap=Albedo + EmissiveMapFactor=1.5`

**两个反直觉的坑（都踩过）**：

| 症状 | 真相 |
|---|---|
| 蝴蝶结"发光严重" | **不是发光**。它的贴图平均 sRGB≈240，而军装藏青只有它的 1/17 → 阳光下当然晃眼。**无光照正常、只在光照下亮 = 不是自发光**（自发光在暗处也亮） |
| 换成黑贴图后**更亮** | 自发光是按**发光贴图的 alpha**取掩码的：`null_black` 是黑但 **alpha=1**（满掩码）；原来的白丝带 alpha 反而低。游戏专门有 `Assets\default_tex\null_black_alpha_BM`（黑且 alpha=0） |

**排查顺序**（从便宜到贵）：
1. **量贴图像素**：把贴图当图片读出来统计平均 RGB/alpha（Blender `bpy.data.images.load` 也行）。
   接近全白（>220）的贴图就是全模最亮的表面，要么换色、要么压 `fBaseMapFactor`
2. **看是不是发光**：暗处也亮 → 发光；只在亮处亮 → 漫反射/镜面
3. **查 `fSpecular`**：`Ch_Pl_Standard_Mt__0X` 一族是 **0.0**（高光项被乘 0，光能全落到漫反射），
   深色件看不出来，纯白件就过亮 → 改成 1.0 与其它部位对齐
4. **改色/换色**：作者素材通常自带多色版本（某头发素材 丝带就有 14 种色），直接换贴图最省事、也最贴合原作者设计
5. 关发光：发光贴图 → `Assets\default_tex\null_black_alpha_BM`，**同时**把 `EmissiveMapFactor` 写 0（两条路一起断，不依赖对掩码机制的猜测）

**亮度修正**（照抄用户上个工程已验证的）：`Base 0.3/0.2/1.0 → 0.4`；`EmissiveFactor 3.0/50.0 → 1.5`

## 验证方法论（比写脚本更重要）

1. **验成品，不验工作目录**：直接解 zip / 把成品 mod3 重新导入 Blender，确认"装进去的东西"对
   （期间就靠这一条发现"改了 blend 却根本没进游戏"）
2. **新写二进制格式前先做往返验证**：用你的理解把现成文件重建一遍，要求逐字节一致
3. **改前改后逐字节 diff**（以原始 `.bak` 为基准），把差异打印成表
4. **打补丁脚本必须幂等**：从 `.bak` 原始备份重算再写回（当补丁依赖"原始值"时尤其必要——
   例如把 `3.0` 改成 `0.0`，跑第二遍就在已改过的文件里找不到 `3.0` 了）
5. **每一步都把关键数字打进日志**：权重分布、间隙分布、长度自检、字节一致性——出问题时不用重新现场勘查
6. **搭一条一键流水线**（`C10_一键收尾.py` 那种）：13 步、全幂等、失败即停并打印上下文，
   一次迭代 30 秒。这是后面能快速试错的前提
7. 昂贵的贴图转换加 **mtime 跳过**；但注意 `Copy-Item`/`shutil.copy2` 会**保留原时间戳**，
   用"比源文件新就跳过"的逻辑时要意识到这点

## 贴图 alpha：脸/身体"斑驳暗影"的真正原因（第三次实战最大的坑）

**症状**：游戏里脸上（集中在嘴、鼻）出现斑驳的、像影子一样的暗块；**光照下明显、阴影里看不见**；
Blender 里看不出来（导入器把材质换成了黑色占位，只能靠游戏或另做渲染验证）。

**根因（每一条都是量出来的，不是推测）**：

1. 作者贴图的 alpha 是**覆盖蒙版**，不携带颜色：脸 4096² 里岛内 21.5% 的像素 `alpha<250`，
   其中 **`alpha=0` 的像素 RGB 100% 是纯白 (255,255,255)**（实测 253 万个像素无一例外）。
   岛内还有 14.4% 的面积是"整块被 UV 覆盖、整块全透明"的**成片**空白（不是抗锯齿细边）。
2. 脸的材质是"自发光为主"的画法（`fEmissiveMapFactor` 要调到 3.0 脸才不发黑），
   而**发光贴图就是 albedo 本身**——于是 alpha=0 的 texel 拿不到自发光、旁边的拿 3 倍，
   光照下就是一块块斑驳暗块，位置正好落在蒙版最密集的**嘴/鼻小岛**。这一条把"为什么只在嘴鼻、
   为什么只在光照下"全解释通了。
3. 图集空白（岛外 23%、身体 31%、头发 29%）在 mip 过滤时会渗进小岛：白渗=变亮；
   若材质按 RGB×alpha 取，就是白×0=**黑**——即"暗影"。

**正确处理：三条一起做，缺一不可**

| 步骤 | 做法 | 为什么不能省 |
|---|---|---|
| 蒙版拉平 | alpha 全置 255 | 不透明渲染用不上 alpha；留着会被挖洞/当掩码/相乘 |
| 空白填充 | 岛外 **和** 岛内 `alpha<250` 的像素，用**最近的岛内不透明像素**颜色填满（8 邻域生长，1/4 分辨率 96 轮 ≈ 全分辨率 384 像素射程） | 只置 alpha=1，空白区仍是白的；**只做预乘会变成黑的**（白×0=黑），比原来更糟 |
| 已画像素不动 | `alpha≥250` 的像素 RGB 原样保留 | 保住美术内容 |

- **别把"预乘 alpha"当万能药**：只有透明区的 RGB 本身承载颜色（"墨"画在 alpha 上）时预乘才对。
  本例透明区 RGB 是纯白＝没有内容 → 预乘只会把空白变黑。
  **先量一下 `alpha<0.5` 区域的 RGB 均值再决定用"填充"还是"预乘"**。
- **对照组价值极高**：用户上一个 mod（milfy）把 alpha 烘成了 1（源 0.7509 → 成品 1.0000），
  所以从没出现这个斑驳；我这次直接用原始 PNG 就中招。**做新 mod 时先看一眼参考 mod 的成品贴图
  与源贴图差在哪**，比凭空推理快得多。
- 顺带确认：容器格式没问题。把生成的 `.tex` 与**已经跑通过**的参考 `.tex` 做
  46 个头部 u32 + mip 偏移表 + 文件长度逐字段对拍，全部一致 → 嫌疑范围直接缩到图像内容。

**光栅化 UV 的坑（差点把贴图涂烂）**：UV 岛有镜像的，三角形绕序正负都有
（实测 blond 74%、Body_Base 26% 的三角形是负面积）。用固定符号做"点在三角形内"判定会**整片漏掉
镜像岛**，漏掉的区域会被当成空白涂抹——第一版烘焙就因此把头发 55%、身体 23% 的贴图糊掉了。
必须按**每个三角形自己的有符号面积**决定判定方向（覆盖率 12% → 67%）。

## 精简成品包：哪些贴图能删（活槽法）

不要按文件名猜，也不要只看"贴图槽里有没有这个名字"——**槽位存在 ≠ 有用**。判定链：

1. **mod3 实际用到的材质名**：mod3 里材质名是 ASCII 明文，正则
   `Ch_(?:Pl_)?Standard_Mt_[0-9_]*` + 结尾 `\0` 就能取出（`C0_替换成品包.py` 用的就是这招）
2. **材质名→哈希必须查游戏字典**（`various_hash_dict.json`）：MHW 的材质名哈希**不是 CRC32**。
   我按 CRC32 匹配时算出来的"活槽"数是 0
3. **每个部位的 mrl3 都带同一套 34 个材质**，但只有该部位 mod3 用到的才算"活"
   （用全局材质集合判断，会把别的部位的死槽当成活的，结果一张都删不掉）
4. 材质项 56B：`nameHash@4, mmtrHash@8, blockSize@16, resourceCount u16@22, blockOffset u64@48`
   → 资源项 16B：`type@0, hash@4, resValue@8`；`resValue` 落在 `1..贴图槽数` 时
   表示"第 resValue 个贴图槽"（1 起）。遍历条数用 `resourceCount // 2`
5. 资源名反查：`master_material_dict[str(mmtrHash)]["resourceDict"][str(resHash>>12)]["name"]`
   → 得到 `tAlbedoMap / tEmissiveMap / tNormalMap / tDetailNormalMap / tColorMaskMap / tFurMap /
   tFurVelocityMap / SSAlbedo …`

**落地效果**：只有活槽指到的文件才留。pl040_0010 实测 246 MB → 139 MB
（清掉 17 张共 107 MB 的遗留贴图），zip 95 MB → 47 MB。
理论依据：**mod3 没引用的材质，游戏根本不会实例化，它的贴图永远不会被加载**
（用户上一个 mod 的 mrl3 里本来就有一堆指向不存在文件的槽，照样正常运行）。

**两个反直觉的细节**：

- `.bak*` 备份**不要**移出 `nativePC`——C7/C11/C22/C25 的幂等重算要读它们。正确做法是留在原地，
  **打包时排除**；并且把打包逻辑集中到一个 `C33_打包zip.py`，不要再在流水线里内联一份
- 游戏自带贴图（`Assets\default_tex\null_black` 这类）**路径不能加模组文件夹前缀**，
  否则会指到 `nativePC\<模组目录>\Assets\...` 这种不存在的文件（这个洞是被反向验收脚本抓出来的）。
  而且要用捐体 mrl3 里**本来就出现过的名字**（`null_black`/`null_RMT`/`null_NM`），别自己编
  （我编的 `null_black_alpha_BM` 实测在捐体 mrl3 里出现 0 次）

## 打包前值得照抄的验收脚本

- **反向检查**：把"活槽 → 文件"的关系倒过来验一遍——每个活槽指到的文件必须同时存在于**磁盘和 zip**。
  这一条直接抓出了"游戏贴图路径被加了模组前缀"的洞
- **CRC 比对**：zip 里每个条目与磁盘文件 CRC32 一致（32/32 ✓）
- **从 zip 里解出贴图再验内容**：确认 zip 内 `Face_Base.tex` 的 mip0 载荷与 texconv 的产物逐字节一致
  —— 证明"修好的那张图"确实进了包，而不是只在工作目录里
- 每张贴图都打印"被哪些材质的哪个资源名指向"，出问题时一眼看出该删不该删

## 未解决问题：裙子与腿的碰撞

**现状**：这是唯一没能两全的地方，留给后来者。

- **开碰撞**（裙链 `colFlag=4` + 腿碰撞体半径放大到 3.5）：裙子被腿顶得大幅上翘乱飘，腿反而更容易穿出来
- **关碰撞**（`colFlag=0` + 腿碰撞体还原 2.0）：裙子垂坠自然，但腿会穿过裙子
- 已试过：统一裙链参数（重力/阻尼/弹簧）、腿碰撞体半径 2.0/3.5、彻底关碰撞
- **没试过的方向**（供参考）：
  1. **碰撞体半径取中间值**（2.0~3.5 之间逐节点调），别一把全改
  2. 调 `colGroup` / `colAttr`，只让大腿参与碰撞、小腿不参与
  3. 对比基壳**原始 ctc**里的值（备份还在 `f_wst040_0010.ctc.bak*`）——那套参数是给基壳自己的裙子调过的，是最好的起点
  4. 降低裙链的 `transForce` / 提高 `spring`，让裙子不那么容易被顶飞
  5. 检查裙子的内/外层顶点权重分配（内层跟腿、外层跟裙链？）
  6. 请教别的作者——这条最省时间，用户也是这么打算的

> 记录这一节的用意：**把"试过什么、为什么都不行"写清楚**，比留一堆看似可行但已证伪的方案更有价值。

## 贴图色彩空间：最容易误判成"材质错位"的一类回归

**症状**（用户原话）："袜子上部有一圈变成黑色，本来该都是白色"、"裙摆本来环绕下沿的白色条带上下错位"。
第一反应会去查 UV / 材质指向 / 图集填充 —— **实测全不是**：UV 没动、
mapping 907 条一条没变、军装贴图在它自己的 UV 区域内与他满意的版本**逐像素差 0.00**。

**真因**：同一张图案，**存 sRGB 原值**还是**sRGB→线性**，深色区差别巨大
（藏青 sRGB 60 → 线性 12；sRGB 168 → 线性 100）。白/深色边界在游戏里看起来就"移位"了，
原本淹没在深色里的暗纹也会显出来（＝袜子那圈黑、裙摆白条错位）。

**怎么定位（照抄这套流程）**：
1. 找到**用户说没问题的那一版 zip**，把里面同名 `.tex` 解成 PNG
2. 和「你的源图」「源图线性化」两版各比一次平均差，差小的那个就是它的色彩空间
   （实测：军装 54.05 vs **0.27**；毛皮 38.8 vs **5.0**；脸 12.99 vs 52.5）
3. **逐张判定，不要一刀切**：同一个包里 Body/Face/blond/ribbon 是原样、Hair/军装是线性化
   （素材来自不同作者、不同工具，历史上就是混的）
4. 用 46 个头部 u32 对拍确认容器没问题，把嫌疑锁定在**像素内容**上

**烘焙三条铁律**（`C31_贴图烘焙alpha.py` 已按此实现）：
- **只填 `alpha<250` 的空像素**（图集空白 + 岛内透明补洞 + 软边）；不透明像素一律原样保留。
  贪心地"凡 UV 岛外就填"会把作者自己画的图集空白涂掉 → mip 过滤时白条边界被推移，
  正是上面那个回归。（军装贴图 alpha 全 1，按这条规则＝一个像素都不动 ✓）
- **不做预乘**：实测透明区 RGB 100% 是纯白（不含颜色），预乘只会把已画好的像素压暗 ≤2%
- **UV 光栅化按每个三角形自己的有符号面积判定**（镜像岛实测占 26%~74%，
  用固定符号会整片漏掉镜像岛 → 覆盖面积算错 → 把有用的贴图画烂）
- **验收不变量**：改动像素必须**全部**来自 `alpha<250` —— 一句话证明"没画坏"

## 排查"斑驳阴影"这类主观问题：先做变量剥离，别连续换假设

我在脸上连试了 4~6 次都没解决，根源是一直换假设、没先把变量逐个摘掉。
正确顺序（每步都能本地复现，不必等用户装包）：
1. 解 `.tex` 确认成品里装的确实是修好的那张图（对拍 + CRC）
2. 渲染时**把贴图换成纯色**：还有斑驳 → 几何/法线/自遮挡；变干净 → 贴图
3. `light.use_shadow = False`：斑驳消失 → 阴影 acne
4. 只留主体连通分量（删补面/内壳）：消失 → 共面补面
5. 最后才怀疑 alpha / 色彩空间 / mip 过滤
**另外**：把"是不是跟着光线走"交给用户判断 —— 跟着光变＝着色/自遮挡；
死死贴在皮肤上＝贴图/几何。这一句能省掉一半假设。
**并且**：自己造的度量指标要能区分假设。我用"高通 std + 暗块占比"量了三次，
读数被脸本身画的线条和曲面明暗梯度主导，三组对照几乎一样 —— 等于没量。
指标必须先在一个**已知答案的对照**上标定过。

## 脸上的"斑驳阴影"：导入法线是坏的（实测根因）

**症状**：脸上（眼部周围最多）出现斑驳的、像遮挡阴影一样的暗块；正面光照下明明没有遮挡也有
阴影；头顶光下低头时会"融入"真实阴影；**把贴图换成纯色后依然存在**。

**定位顺序（前四条依次是否掉的，第五条才是答案）**：

| 假设 | 测法 | 结论 |
|---|---|---|
| alpha 蒙版 | 脸上 alpha 全去掉 + 透明区补肤色（改了 384 万像素） | 无变化 ✗ |
| 阴影 acne | 同机位 `light.use_shadow=False` 对比 | 无变化 ✗ |
| 共面补面 | 只留脸的主连通分量再渲 | 仅 -7% ✗ |
| 两层几何抢像素 | 自发光材质 + 每个连通分量一个纯色，看颜色是否互相咬合 | 洋红像素 93.5% 的邻域也是洋红（成片）= 正常露出的皮肤 ✗ |
| **着色法线** | `mesh.corner_normals` vs `mesh.vertex_normals` 的夹角 | **脸平均 29.15°，>90°（朝里）占 7.52%** ✓✓ |

同一套量法下身体/头发/丝带都只有 0.01~3° —— **只有脸是坏的**，正好对应"只有脸上有斑驳"。

**修法（最小改动，实测有效）**：只对脸执行
`bpy.ops.mesh.customdata_custom_splitnormals_clear()` → 平均夹角 29.15°→1.92°，
`>90°` 7.52%→**0.05%**，与正常部位齐平。

- **不要**顺手做 `normals_make_consistent`：它会**翻转面绕序**（D99 实测面索引哈希变了），
  对"正反两面都在同一个网格里"的薄壳脸皮是有风险的改动，而且并不需要
- **不要**为了修法线进出 EDIT 模式：进出编辑模式会动到网格数据（坐标哈希变了）
- 验收三件套：**坐标哈希不变 ✓、面索引(含绕序)哈希不变 ✓、`>90°` 占比降到 ~0 ✓**

**教训**：从 unitypackage / 别人的 mod 导入的网格经常带**损坏的 custom split normals**。
它不改变贴图、也不改变几何坐标，只让光滑表面出现斑驳明暗，而且**只在有光时看得出来** ——
极容易被误判成"阴影问题"而跑去改贴图、改几何、改碰撞。**做任何 mod 前先量一遍
`corner_normals vs vertex_normals`**，十分钟能省掉几天。
（顺带：`>90°` 那一栏才是硬证据 —— 法线朝里绝不可能是美术有意为之。）

## 最贵的一条教训：别改作者配好的形状（袜子穿模的完整复盘）

**症状**：袜子与小腿有明显间隙，且穿模出鞋子；用户说"很稳定，不管怎么动都穿"。

**我走过的弯路（按顺序，全是错的）**：
1. 用"最近鞋点法线点乘"判断里外 → 三版修法（全局腿轴径向收 / 沿鞋面法线塞 / 逐层内壁收）
   **都把计数改得更差** → 说明判据方向是反的（鞋内壁法线朝内）
2. 换"射线穿越奇偶"判据 → **鞋是开口壳，奇偶判据根本不成立**
3. 全部改动都在**静止姿势**下测量 → 但用户看到的是动态，我一度以为是权重问题
4. 最后用渲染图（袜子红/鞋蓝）出图给用户看 → 用户说"红色**细碎地**出现在蓝色里" ——
   **那其实是紫红(magenta)像素**（红蓝逐像素抢深度混出来的），我一直在数纯红/纯蓝 → 判据再次为空
5. 更致命：我把几何改了 5mm、41mm，**渲染图逐像素完全相同** —— 原来是移过去的点被鞋挡住了，
   我的"改动→复测"回路**从来没被标定过**，等于四版盲改

**真正的解法（用户一句话点破）**：
> "还原成最开始的样子，也就是没有放大袜子的时候"

把袜子按最早备份的坐标还原（只动袜子、同步形态键），**任何动作都不穿模了**，而且间隙也没有了。
根因是**我自己的流水线**：`C7 袜子几何外扩` + `C20 袜筒贴身化` 把作者按这套衣服/鞋配好的
原始形状改掉了，一改就破坏配合。实测数据（袜筒半径）：原始 r_med 0.0887 / r_max 0.1368，
被我改后 0.0893 / **0.1460**（最粗处 +9mm）。

**固化下来的规矩**：
- 形状是作者按整套服装配好的 → **不要为了别的毛病去改它**；有毛病先怀疑自己加的步骤
- 流水线里加了 `C44 袜子形状还原`（从原始备份读坐标写回，幂等）作为**兜底**，
  并**停用 C20**；停用理由写在 `C10_一键收尾.py` 的注释里
- 改几何的脚本一律：**限幅 + 同步所有形态键 + 改完用同一判据复核 + 没净改善就不保存**

**关于"重合面争抢"的判据（可复用）**：两个面几乎重合时，游戏/渲染里看到的不是"红的"或"蓝的"，
而是**两者混出的中间色**（红+蓝=紫红）。所以判断"有没有 z-fighting/穿插"要数**中间色像素**，
而且必须排除轮廓抗锯齿（只统计"周围 5x5 里亮像素占多数"的面内部）。基线：面内紫红 1.4~2.6%。

**关于度量的三条硬规矩（我用四轮代价换来的）**：
1. **先标定回路再改东西**：故意做一个必然可见的大改动（挪 10cm），确认渲染/度量**会变**。
   回路不通时，所有"改进"都是噪声
2. **判据要拿已知答案的点验证**：包围盒中心该判"里"、1 米外该判"外"。
   注意开口壳（鞋口没封）用射线奇偶会失效 —— 先看物体是不是闭合的
3. **指标测不出已知现象就是指标错**：用户说"能看见穿插"，我的指标读 0.000% → 错的必然是指标，
   不该继续改几何

> ★ **另一种 alpha 用法（第十二次实战）**：如果贴图的 **RGB 是常量（std ≈ 0）、图案 100% 画在 alpha 里**
> （渔网 / 蕾丝 / 镂空），那本节这套"只填 `alpha==0` + 拉平 alpha"的规则是**破坏性的** —— 会把图案抹平。
> 那一类要的是 **`RGB × alpha` 预乘后存不透明**，见 §十二 B。

# 第四次实战：某套装 花瓣裙 + 某头发素材 双马尾（工程 `第2版`，测试号 01~17）

> 本轮在 `第1版`（军装 某套装）的基础上换装。**约定：一套衣服一个工程目录、测试号各自新开。**
> 下面只记"上一版没有、或少走一步就会踩"的东西。

## A. mod3 导出器的两条硬事实（都会静默出错，不报错）

1. **每个网格只能有一个材质**：导出器对每个 mesh 写**一个** `materialID`，取的是该对象**材质槽 0**。
   一个对象上用两种材质 ⇒ 整个网格被套上第一种材质的贴图。
   **现象**：`acc` 配饰 52% 的面本该用 `Accessories.png`，游戏里却显示成头发贴图。
   **修法**：按材质**把对象拆成多个**（顶点/面/UV/权重一起切），各自一个材质槽。
   实测形状：`TD_acc` 1440 三角 + `TD_acc_StandardMt5` 1568 三角。
2. **材质名来源**：优先 `obj.name.split("__",1)[1].split(".")[0]`，拆不出来才回退到材质槽 0 的名字。
   所以**对象名里不要出现 `__`**（我的命名 `TD_Bun`/`RPD_Cloth_Inner` 都靠回退路径工作 ✓）。

## B. mrl3 的两个必踩坑

1. **材质名哈希不是 CRC32** —— 必须查 `various_hash_dict.json`。
   症状是**静默的**：`plan_ref`（活槽保护集合）算成空集 ⇒ 槽位复用会把**在用贴图槽覆盖掉**
   （实测：皮肤/脸/耳尾的贴图全串了，且脚本一路"成功"）。
   C25 的框架里就有这个 bug，我照抄时又踩了一次。
2. `resourceCount`（材质项 +22 u16）是**条数×2**，遍历必须 `rc//2`；按 `rc` 遍历会越界读到后面
   的块（有时不报错、有时 `struct.error`）。
3. CB 值**可以是标量**（`fSpecular__uiUNorm` 等），写回要区分 list / 标量（`len(pval)` 会 TypeError）。

## C. ★ 布料碰撞：四要素 + 那个决定性的字段 `colShape`

**判定清单（缺一个就整条路静默失效）**：

| 要素 | 正确值（照抄 `该角色_初恋吸血鬼`＝同角色可用包） | 我们踩的坑 |
|---|---|---|
| 布链 `colFlag`(+4) | **4** | 捐体旧链抄成 6 |
| `colAttr`(+8) | **0xFFFFFFFF** | 抄成旧值 |
| `colGroup`(+12) | **1** | 抄成旧值 ⇒ 与碰撞体不同组 |
| `colType`(+16) | **1** | 同上 |
| **节点 `colShape`(+70)** | **257** | **我们是 258** ← **决定性字段** |
| 节点 `colRadius`(+80) | 2.0 | 3.5 偏大 |

* **`colShape` 不对 = 完全零反应**（不是"弱碰撞"，是"没碰撞"）。三轮回溯才定位到它。
* **碰撞体不在 ctc 里，在 `.ccl`**：参考包 ctc 不加额外碰撞链，ccl 里放 2~18 条即可。
  我前两版往 ctc 里塞了 2~4 条"胶囊链"，即使参数对也不生效（多余）。
* **`.ccl` 结构（本轮反解）**：`u32@0` magic `CCL\0`、`u32@4` 版本、`u32@8` 条目数、`u32@12` 条目数×64、
  条目从 **+16** 开始、**每条 64 字节**；条目 `u32@4` = `(hi<<16)|lo` = **骨对（线段两个端点）**，
  半径等参数在 +20/+24 附近（我们的 4 条腿部碰撞体就是 `(15,14)` 与 `(19,18)` 各两条，半径 2.0）。
* **对拍法（最快）**：解 2~3 个"裙子可用"的同角色包，把 `ctc` 的链字段与 `ccl` 条目打成一张表并排看
  （`Z28_对拍裙子物理.py`）。**同角色的包价值最高**（同一副骨架、同一套身体）。

## D. 配方定标：用"等效发光"而不是系数本身

**等效发光 = 系数 × 贴图"面料区"亮度**。注意是**面料区**、不是全图均值 ——
图集空白（我们那张 25% 是纯黑）会把均值拖低，算出来会误判。

本轮定标（三个"用户已确认"的数据点）：

| 版本 | 系数 | 面料亮度 | 等效 | 用户评价 |
|---|---|---|---|---|
| v1 军装 | 4.0 | 0.52 | **2.08** | 正常 |
| 实测61 | 4.0 | 0.93 | 3.72 | 太亮、花纹看不清 |
| 实测05 | 0.90 | 0.93 | 0.84 | 非常灰暗 |

⇒ 目标 2.08 ⇒ **Base 0.30 / EmiF 2.35**（正好与"用户确认合理"的头发同档，全角色统一）。

**另一个独立判据（花纹被乘法压平）**：统计贴图面料区的分位。若面料集中在 234~250 的**亮窄带**，
则**任何 >1 的系数都会过曝成纯白** ⇒ 花纹消失（实测：乘 4.5 过曝 57.6%、乘 1.4 仍 48%、乘 1.0 才 0%）。
反过来说，深色布料（如藏青军装）用大系数没问题 —— **系数必须连贴图数据一起抄**。

**观感与光照响应**：`自发光占比 = EmiF/(Base+EmiF)`。89%（头发）几乎不随光照变；60%（裙子）
会出现"阴暗偏暗 / 直射纯白 / 非直射正常"三连症状 —— 这个症状组合可以直接判"自发光占比太低"。

## E. 流水线顺序（本轮最贵的两个 bug，都是顺序）

1. **"从别的网格转移权重"的步骤，必须在所有改那张网格权重的步骤之后**。
   实测：内裤（转移自身体）跑在"臀部权重修复"**之前** ⇒ 内裤还跟腿、身体屁股已跟骨盆 ⇒
   动画里两者错开，看起来"屁股凹进去一块"。**正确顺序：改身体 → 再转移**。
2. **重建型脚本会覆盖只在成品包里的修复**。
   我从主 blend 重建 body ⇒ 上一版只打在成品包 `body.mod3` 里的**手指拉伸修复**被抹掉，
   用户实机反馈"手指又开始拉长"。**修法**：把实测验收过的目标态（`.npy`）绝对写回，
   并把它固化成流水线的一步（本例在导出前）。
   **判据**：拿到"只在成品包里的修复"时，先查它的来源 blend 是否还在；不在就写绝对权重。
3. **改权重的作用域不要用"直角边界"**（`y>0.02`、`|x|<0.20` 这种）。改过的顶点与紧邻未改顶点在动画
   下错开 ⇒ 折痕/凹坑。做法：把"改动的量"沿网格 **Laplacian 平滑 8 轮（α=0.5）**再施加。
   同时作用域要**避开语义相邻但方向相反的区域**（我 `y>0.02` 收屁股时把**裆部下缘**也圈进去了
   ⇒ 大腿正面顶穿内裤）。

## F. 验证方法（本轮新增）

1. **摆姿势必须摆"该网格所属部位"的骨架副本**，而且**跨部位相关的两副一起摆**。
   `f_body040_0010`/`f_wst040_0010`/`f_arm040_0010` 是**三副独立副本**，游戏里吃同一套动画；
   只摆 body ⇒ 裙子不动 ⇒ 量不到跟腿效果（我第一版就量错了）。
2. **每出一版就把该版的 `mod3/ctc/mrl3` 快照到 `_snap_<版本>/`**。
   否则成品树被下一版覆盖后，**旧包无法再做逐字节复核**（只能给结构级验收）。
3. **验证脚本要拿"本版快照"比对**，不要拿"当前树"（那会给出假的"不一致"）。
4. **Blender 脚本抛异常时退出码仍是 0** ⇒ 驱动脚本必须用**哨兵**（查报告里有没有 `SAVED`）判断成败。
5. **贴图解码链（本机可用）**：`.tex` → 手搓一张单级 `.dds`（148 字节 DX10 头，dxgiFormat
   BC7=98/BC7S=99/BC5=83/BC1=71）→ `texconv -f R8G8B8A8_UNORM` 解成 RGBA8 DDS → 直接读字节。
   **输入输出必须放不同目录**（同名会被判成"覆盖自己"）。
6. **隐形载体**（要"某部位不出几何"时）：实测 **885 个第三方 mod3 里 `meshCount=0` 的一个都没有**
   ⇒ 不能发空 mod3，也不能删 mod3（会回落原版）。做法：把身体对应部位的一小块**绕区域中心缩到 0.9 倍**
   （严格藏在自身内部）+ 同下标复制权重 ⇒ 导出一个"有效但不可见"的网格。
7. **"悬空引用无害"有个前提**：链驱动**不存在的骨**无害（v1 的 leg.ctc 就是，实机正常）；
   但**骨存在、却被旧形状的链驱动**就致命（武器/衣服形状全错）—— 所以 ctc 过滤规则要写成
   "节点号落在新 mod3 骨表里、且不在白名单里 ⇒ 必删"。

## G. 解剖参考包的顺序（省钱）

1. 先看**同角色**的包（同骨架、同身体，字段可直接抄）。
2. `ctc` 打表：链数/节点数/`colFlag`/`colAttr`/`colGroup`/`colType`/重力/阻尼/平移/弹簧/`colShape`/`colRadius`。
3. `ccl` 打表：条目数 + 每条的骨对。
4. 材质 CB 打表：`Base`/`EmiF`/`fSpecular`/`fMetalic`/`fRoughness`/`fTranslucency`/`bUseCMM`/`bBaseColorEmissive`
   + 各 `t*` 指向（看清它法线/RMT 是不是都用**游戏空图** `Assets\default_tex\null_*`、`assets\NM`）。
5. 贴图亮度：一定要量（`E.` 那条"系数不能脱离贴图抄"）。

## H. ★ UV 必须"逐面角(per-loop)"保留，不能压成"每顶点一个"（本轮最隐蔽的 bug）

**症状**：两根马尾"材质全乱"，其余头发"零散地有怪材质"，但**贴图指向、UV 层、材质名、材质分配全部实测正常**。

**根因**：我从预览 JSON 里拿到的 UV 是 **per-loop**（每个面角一组），但我写回时压成了
`uv0[顶点] = 它第一个 loop 的 UV`，再按顶点写进 UV 层。
**UV 缝合边上的同一个顶点在不同 UV 岛里必须用不同的 UV** —— 压成一个值就把另一侧的面
拉去采样别的岛 ⇒ 贴图乱。头发是碎岛最多的资产（马尾最碎）⇒ 症状最重。

**修法（两条一起）**：
1. 建网格时按**源面的面角顺序**把 UV 写进 UV 层（`suvl.data[loi].uv = 源面第 k 个面角的 UV`）；
2. **先写 UV，再三角化** —— bmesh 的 `triangulate` 会正确插值/保留 UV 层；
   反过来（先三角化再按顶点写 UV）就会前功尽弃。

**验收判据（很好用）**：修好后 `.mod3` **会变大**（本例 body 2,583,944 → **2,645,960 B，+62 KB**），
因为导出器必须在 UV 缝合处**拆点**（mod3 的 UV 是随顶点走的，所以缝合处必须有重复顶点）。
"文件变大 + 网格顶点数上升"正是修对的指纹。

## A. ★ ctc 的 `nodeCount` 最小是 **2** —— 决定骨号预算的硬约束

想给每个"链组"做物理链时，**链节点数不能是 1**：实测**参考包（该角色初吻 4 个部位）与我方 4 个 ctc 的
nodeCount 分布里最小值都是 2**（`{3:16, 4:2}`/`{2:3,7:2}`/`{3:6,4:7}`/`{3:10,8:2}`），
所以"一条链 = 2 个节点"⇒ **每根链要 2 根骨**（root + tip）。`Y4b` 里末节点的方向会退化成
`pts[k]-pts[k-1]`，1 节点则连方向都没有。

**骨号预算（pl040_0010 实测）**：`200` 与 `206~246` 在四个部位**全部空闲**（共 41 个）；
`150~193` 是上一版的链骨区间、`194~199` 胸骨、`201~205` 尾巴、`247~254` 原版。
⇒ 41 个号 = 最多 20 条 2 节点链。本轮被迫把 12 组"次要组"改成固定骨才能塞下：
`HeadDress_L/R/M_1`→Head、`WristCloth_A/B/C{L,R}_1`→Hand、`BreastCurtain_L/R_1`→胸骨、
`ShoulderRibbon_L/R_1`→Upper_arm、`Elbow_support.L/R`→前臂。
**下次开工前先把"哪些组值得做链"按权重排一遍**（Σw 占比），别平均分。

## B. ★ 链的方向与长度**必须从几何实测**，不能抄原骨架的骨 `tail`

原骨架（预览里的 Armature.004）的骨 tail 是**导入器的显示朝向**，不可靠：
实测 `Skirt_AL` 的 tail 朝下、**`Skirt_AR` 的 tail 朝上**（同一对链、方向相反）。

做法（本版 `Y1_构建.py` 的 `chain_tip`）：
1. 收该链所有段组的顶点，**只收"该组是主导组"的顶点** —— 同一组名会同时出现在好几个网格里
   （`Skirt_AL_1` 在 Belt/SkirFlaps/Skirt/SkirtArmor 都有），全收进来质心会被拉偏
   （实测链方向因此**越过中线**）；
2. 以 `head → 最远点(p95 距离)` 定方向与链长（不能只用质心方向，长条布片会偏）。

## C. ★ 单段组链要"逐点 u"才有沿链渐变（否则布片是硬转的）

原网格常常**只把整片布绑在链根骨上**（作者的链是"根骨+一个 tip 传感器"，布片不会弯）。
照抄"按段组算 u"就会得到：`n_new=2` 且 `u=0.5` ⇒ 整片 50/50 分给两个节点（弧度怪）、
或全给根骨（完全不弯）。
**做法**：`u = clamp( (顶点 - head)·(tip-head) / |tip-head|² , 0, 1 )` 逐顶点算。
验收（`Y8c_链骨权重体检.py`）：`SkirtAL` u 0~0.25 → root 占比 **1.000**、u 0.75~1 → tip **0.822**，
且 u 单调 ✓。判据写成"root 占比按 u 分档必须单调递减"。

## D. ★★ 从别的工程目录整体拷贝时，`*.bak_*` 备份是**陈旧陷阱**

`.bak_y4`/`.bak_z5`/`.bak_c25` 这类备份**不属于 .bak 本身保护的内容**，它们记录的是**别的工程**的中间态。
本轮 `Z29_裙链碰撞修正.py` 从陈旧的 `wst.ctc.bak_z5`（= 上一版工程的 RPD 链）重算，
把 `Y4b` 刚产出的新链**整份覆盖掉** —— 症状是"改动：2 条布链"而应当是 11 条。
**判据**：脚本报的"改动条数"与规格不符时，第一件事就是**查它的 `.bak_*` 是谁的**。
**修法**：驱动脚本里在会读备份的那一步之前 `rm -f <那个 .bak>`（前提是该步幂等、能从更上游重算）。

## E. `bmesh.ops.bisect_plane` 会把三角面变成四边形

用它"沿平面切掉一部分"（丝袜切脚）之后，**必须补一次 `bmesh.ops.triangulate`**，
否则导出器预检报 `N 个非三角面 (NonTriangulatedFace)` 直接中止导出。
（切完 `bm.to_mesh()` 前判一次 `any(len(f.verts)!=3 …)` 即可，代价近零。）

## F. ★ 配色/亮度："等效发光"**不能跨贴图迁移**，而且要先量"用哪套配色"

本套源包自带 **9 套配色**（`A_Black&White` … `I_White&Yellow`），亮度差**一个数量级**：

| 配色 | Tex_Upper 覆盖区均值 | Tex_Under |
|---|---|---|
| A_Black&White（预览里用的） | 0.400 | 0.004 |
| F_White / G / H / I | **0.87~1.00** | 0.97~1.00 |

同一档配方（`Base 0.30 / EmiF 2.35`）在 A 上的等效发光只有 **0.94**、在 F 上是 **2.1**（≈上一版花瓣裙的 2.19）。
⇒ **交付时必须把"这套配色会是暗的"当成一条待判定项写给用户，并把换配色写成一条命令**
（贴图差分：只换 `.tex`、不改材质名、不改几何）。别自己去"调系数补偿"。

**量"面料区亮度"的正确口径**：把每个网格的 UV 三角形**光栅化到 1024² 掩码**、取并集，
再在掩码内统计 —— 比"全图均值"（图集空白拉低）和"非黑像素"（黑底贴图会误判）都准。
本套是**黑底银饰**（全图均值只有 3~65），用"非黑像素"口径会把内裤/丝袜判成"只有 1~5% 画过"。
辅以"覆盖区内 alpha 分档"判"内容到底在不在 UV 里"（本轮 `Tex_Socks` 覆盖区 72.7% 但
alpha≥250 只占 6.9%、软边占 92.9% ⇒ 内容在软边区，烘焙规则"只填 alpha==0"正好不动它）。

## G. 色彩空间"raw vs sRGB→线性"要**按工程重新量**，别继承上一版的结论

v1（第1版 军装）的 `MiliCuteNavy` 是**线性化后存**的；而 第2版 的 `某套装`（用户认可）是 **raw**。
本轮从**用户认可的 zip**里解出贴图再与源 PNG 比对（`X9_色彩空间判据.py`）：
`某套装` 原样差 **0.105** vs 线性化差 17.414 ⇒ **raw**。新贴图按 raw 存。
**链路**：`.tex` 的 mip0 载荷 + **texconv 自己产的单级 BC7 DDS 头**拼成合法 DDS
（别手搓 DDS 头 —— 字段顺序极易错，本轮第一版就错在 `dwCaps` 偏移上）→ `texconv -f R8G8B8A8_UNORM` → 读字节。
注意"输入输出放不同目录"（同名会被判成覆盖自己）。

## H. 高跟鞋丝袜：先量"脚底法线"，别只看整体主轴

`Socks` 脚区（最低 16 cm）主轴与竖直成 **54.2°**，看起来像"斜 45°"。但更细的量测：
* **最低 1.2 cm 层**的 PCA 最小轴 = 鞋底法线，**与竖直只差 0.3°**（脚底是平的）；
* 膝盖以上的小腿段与身体**只差 0.3~0.4 mm**（贴合极好）；
⇒ 真正的形变是"**整只脚相对身体下移 2.5~4 cm**"，不是"脚背绷直 36°"。
**ICP 定量**（绕踝绕 X 轴 + 平移搜索）：最优 **−14.75°** 仍留下 **p99 12.7 mm** 残差
⇒ 会在脚上局部鼓/塌。**改为"按 z 切掉脚部"**：切后穿入 **0** 个、切面处袜-身体半径差仅 0.4 mm
（袜口正好贴在皮肤上），再沿身体法线外推到 +2.5 mm ⇒ 复核 0 穿入、最小间隙 +1.5 mm。
**判据**："转平"要 `中位<5 mm 且 p99<10 mm` 才算贴身；做不到就切，并报出切口环的半径与身体截面差。

## I. 复用上一版流水线时，**材质名清单要重新核对"在不在用"**

`Y3_材质指向` 写的是材质名 → 新贴图。改名前必须知道"这个名字当前有没有被网格用"：
本轮实测 body 在用 `{__1,__2,__3,__5,__7,Outline_Black}`、arm `{__6}`、wst `{__5}`、leg `{Ch_Pl_Standard_Mt__01}`，
所以 `__8` 在 body/wst 都空闲 ⇒ 安全改指向。
**两个必查**：① mod3 里材质名是 ASCII 明文，`re.findall(rb"Ch_(?:Pl_)?Standard_Mt_[0-9_]*\x00", mod3)` 就能拿到；
② 注意 `bpy.data.materials[name]` 在**没被任何网格用过**时不存在，`Y1` 里要"缺就复制一份改名"
（本轮 `Ch_Standard_Mt__8` 就触发了 `KeyError`）。

## J. 摆姿势穿模的指标要"能区分假设"，否则只能报原始读数

本轮按 skill 的老办法做了"身体顶点沿法线打射线、打不到任何衣物就算露出"，
在 40° 抬腿下读数从 11.15% 跳到 55.69% —— 但它**同时**把两件正常事算进去了：
① 过膝袜口到胯之间那 4.5 cm 大腿**本来就露**；② 裙是 8 片独立裙片、片间本来有缝。
⇒ 这个数**不能当"穿模计数"读**。教训与 skill 里那条一致：
**先问"这个指标能不能把'正常'与'缺陷'分开"**；分不开就只报原始读数 + 说明它的构成，
把判定交给实机。**别把它包装成"改进/恶化"。**

## K. ★★ 判据陷阱：镜像网格上的"均值相等"是**几何必然**，不是证据

第二轮修"裆部被两条大腿拉成方形"时，我按这个判据圈作用域：
`腿总和>0.35 且 min(左腿,右腿)/max(左腿,右腿) > 0.5`（"两条腿都在拉"）——
**筛出来 0 个顶点**。原因：
* 我上一份报告里写的 `|x| 0.01~0.04 → 左腿 0.486 / 右腿 0.486` 是**分档均值**；
* **镜像对称的网格上"左腿均值 == 右腿均值"必然成立**（左右互为镜像），
  它**不携带任何"每个顶点都被两腿共享"的信息**；
* **逐顶点**看，同区域两腿比均值只有 **0.084** —— 大量顶点是"非左即右的单侧"。

⇒ **规矩**：要判"这个顶点是否被两条腿同时拉"，必须在**逐顶点**上算（`min/max` 逐点），
不能用分档均值。**任何"两边对称的均值"都要先问一句：它是不是被对称性保证的？**
（与 skill 里"对合变换下的不变统计量是空判据"是同一条家族。）

**改对之后的判据**：只按 `|x|` 圈中缝（`|x|<0.045` 全额、`0.075` 淡出）+
z 范围 + Laplacian 平滑 —— 418 个顶点被改，中缝腿权重 0.97~1.00 → **0.26~0.44**（骨盆 0.55~0.72）。

## L. ★ 链的权重参数 `u` 写错 = "整片刚性"而不是"不明显"

`t = u × n_new − 0.5` 这个公式对 `u` 很敏感：**`u` 一律取 0.5、而 `n_new` 是奇数（如 5）时，
`t` 恰好是整数 ⇒ 全部权重落到"中间那一根链骨"**，网格变成**刚性片**（不会弯）。
症状不是"弯得少"，而是"**整块水平硬片被物理甩到头顶**"（本轮用户实测）。
* 修法：`u` 必须**按段组在链里的次序**给：`u = (段组序号 + 0.5) / 段组总数`；
* **最快的验收判据**：`Y1` 报告里该网格的**"用骨"数** —— 修前 `TD_Tail` = **3**、修后 = **11**。
  一个"5 节链"的网格用骨数只有 3（=2 条链各 1 根 + 1 根真身骨）就是中招了。

## M. 挂链/挂辅骨要看**权重所在的位置**，不是骨的名字

`ShoulderGuard`（肩甲，z 0.976~1.034 在肩膀上）的顶点组里有
`Elbow_support.L/R`（各 6.85%）。我按"骨的原位在肘"把它挂到**前臂** `Lower_arm`
⇒ 小臂一摆肩甲跟着扭 ⇒ 穿模。**正确做法看权重的位置**：那些顶点物理上在肩上 ⇒
挂 `Upper_arm`（= `Elbow_support` 的父骨）。
⇒ 规矩：**辅骨（accessory bone）的映射，按"它带的顶点在哪"决定，不按骨头的名字/原位。**

## N. 贴身衣物的权重：**从腿皮转移**永远优于"照抄原骨架的权重"

用户第二轮反馈"站立不穿模、走动时膝盖前后袜子穿模、皮肤漏出"。逐高度量平均权重
（skill 里治袜子穿模的标准口径）发现：**袜子的"小腿→大腿"过渡带比腿皮高 6 cm**
（z −0.46~−0.40：袜 0.891/0.109 vs 腿皮 0.621/0.379）。
袜子用的是**源素材自己的权重**（作者的另一套骨架），和我们的身体不是一套。
⇒ 修法（`Z28_袜子权重对齐腿皮.py`）：给身体建 BVH → 每个衣物顶点取**最近面**、
按重心坐标混合该面 3 顶点的权重 → **逐点替换**。
读数：大腿通道逐层平均绝对差 **0.0789 → 0.0248（−69%）**；踝部也修好（0.322/0.678 → 0.121/0.879）。
**铁律**：这一步必须在**所有改身体权重的步骤之后**（本轮顺序：Y11 手指 → Z26 臀部 → Z27 裆部 → Z28 袜子）。

## O. "改作者形状"与"报残差"之间的取舍：先问用户

高跟鞋丝袜的脚部，我第一轮选了"切掉"（因为没有离线方案能同时做到贴身与不穿模）。
用户明确要"转平贴合" ⇒ 这一轮改成 `−14.75°` 刚体旋转 + 沿法线外推，
并**把固有残差直接报出来**（p99 12.7 mm ⇒ 袜脚局部松/紧），同时保留"切脚版"作为退路。
⇒ 形状是作者按整套服装配好的（skill 那条最贵的教训），**但它也是用户的观感偏好** ——
两条冲突时，把"两个版本 + 各自代价"都给出来让用户选，比替他决定好。
另外记一条工程细节：旋转后**丝袜脚底会落到身体脚底下方 ~12 mm**（鞋楦比脚大），
要按"身体脚底 − 2 mm"抬回来，否则角色像站在一层鞋垫上。

## P. ★★ 两条并行的建链代码，只要一条忘了统一坐标，症状就出在"那一半"

本轮"头发飘在头顶、整体水平"的真根因：`Y1_构建.py` 里链骨位置有两条路 ——
* 新衣服的链：在计算时就过了一次坐标变换 `xf()`（预览→工作）；
* **某头发素材 双马尾的链（质心法）：算出的是预览坐标，我却直接当工作坐标用了**（漏了 `xf`）。

后果：5 根链骨被放到**头顶上方 0.61 m**，整片马尾被拉过去。
**读数**：首节点 `(0.0889,0.0640,1.0832)` vs 正常值 `(0.1227,0.1125,0.4682)`；
而 `xf(前者) == 后者` **逐位相同** —— 一眼定案。

**最省时间的定位法：跟一个"已知正常"的产物逐字段对拍。**
用户说"参考 第2版，那里是同一套头发且没问题" ⇒ 直接比两边的**链骨首节点坐标**，
一次就出结论。（上一轮我靠推理绕了一圈、只修了权重分布，位置错没修，所以还是飘。）

**通用判据**：任何"从别的代码路径抄过来"的几何量（骨位置、链节点、贴图路径），
都要先问一句"**这个量在哪个坐标系里？两条路一致吗？**"

## Q. ★★ 判据事故：对照组"看起来有效"不等于对照组**代表**了争议区域

为判"袜脚面片有没有折叠"，我先用了"袜子面法线 vs 该处**身体**法线的夹角 >90°"，读数 **7.66%**，
于是花好几轮去消折叠（去掉全量投影、给位移加 Laplacian 平滑），**结果穿入从 42 涨到 356**。

事后做对了两步才收敛：
1. **对照标定**：拿"完全没改动过的袜筒段"比 —— 对照组 0% ⇒ 判据"看起来"有效；
2. **换一个不依赖身体的判据**：面法线 vs **它自己三个顶点的顶点法线** ⇒ 真折面只有 **0.45%**。

⇒ 7.66% 是**假阳性**：身体脚在**脚趾**处曲率极高（906 顶点挤在 3.1cm 内、54% 在 2mm 内互为邻居、
27% 法线朝下），"最近点的法线"在那里指向完全不同的方向，**与折叠无关**。
对照组之所以通过，是因为袜筒是低曲率、紧贴的区域 ——
**对照组的"代表性"本身就是一个必须先验证的假设。**

**三条可移植的规矩**：
* 判"网格自身是否自交/翻折"要用**自洽**判据（面法线 vs 自身顶点法线 / 面 vs 邻面），
  **不要**用"与另一个物体的法线比"—— 后者度量的是"两个形状像不像"，不是"网格坏没坏"；
* 对照组要选**与争议区域同性质**的（高曲率对高曲率），否则标定通过也是假的；
* 当"修 A 反而让 B 变差"时（本轮：消折叠 → 穿入涨 8 倍），先怀疑**判据**，别再改几何。

## R. 贴合衣物"要贴上去"时的可用手法与代价（本轮实测总结）

把一件"作者为高跟鞋做的袜脚"贴到"平放的脚"上，试过并按代价排序：

| 手法 | 效果 | 代价 |
|---|---|---|
| 刚体旋转（绕踝 −14.75°，实测最优角） | 姿态对了 | 残差 p99 12.7mm（形状不同） |
| **按数据做尺寸对齐**（把袜脚 y 跨度映射到脚 y 跨度 + 余量、脚底降到脚底下方 2mm） | 脚底跨度从"短 1cm/端"变成**盖满脚印** | 无（仿射，不会折叠） |
| 踝下**细分一级** | 面片塌陷量降到 ~1/4（袜脚顶点数只有脚的一半） | 顶点数 ×4（317k→383k 的 leg.mod3） |
| **单调外推**（只把贴进身体的顶点沿法线推到 3.5mm，从不内移） | 穿入 1244 → 42（最深 2.9mm） | 无（单调 ⇒ 不会折叠） |
| 全量投影（每个顶点投到"身体面+3.5mm"） | 覆盖最好 | **会让 ~10% 面片自我覆盖/翻折**（拓扑不匹配时）⇒ 放弃 |
| 对位移做 Laplacian 平滑 | 理论上防折 | **实测穿入涨 8 倍**、折面不变 ⇒ 放弃 |

**一句话**：**"仿射对齐 + 单调外推"是安全组合**（都不会引入折叠）；
"全量投影"和"位移平滑"看着高级，在拓扑不匹配时反而更糟。
**并且**：如果目标面的曲率远高于源网格（脚趾 vs 光滑鞋楦），**任何变形都盖不住** ——
这时正确的做法是**重做那一段几何**（按目标面做一层等距壳），而不是继续调变形。

## S. ★★★ 目标面曲率远高于源网格时：**别调变形，替换那一段几何**

本轮最硬的一课。"把作者给高跟鞋做的袜脚贴到平放的脚上"，试遍了所有变形手法：

| 做法 | 脚尖裸露 |
|---|---|
| 绕踝转平 + 尺寸对齐 + 单调外推 | 50.2%（最深 14.0mm） |
| 再加**径向投影**（从脚内部点射向袜顶点、落到"脚面+1mm"；星形区域一对一、不折叠） | **78.8%** ← 更差 |
| **删掉原脚部 + 复制脚面外扩 0.6mm 做新壳** | **0.0%** |

**为什么变形注定失败**：袜子原厂脚部共 1716 顶点（给光滑鞋楦用的），
而脚趾区身体有 **906 顶点**、54% 在 2mm 内互为邻居 —— **源的密度不够表现目标的高曲率**。
投影后落在脚尖 y 区间的袜子顶点只剩 **96 个**。⇒ 二选一：要么穿模、要么折面。

**替换几何的完整配方（本轮实测，可直接照抄）**：
1. **删**掉源网格出问题的那一段（本轮：袜子预览 z<0.100 以下全删）；
2. **复制目标面**：取目标物体该区域的全部顶点与面，每个顶点沿**自身法线**外扩一个薄量
   （本轮 0.6mm）⇒ 新对象；法线必须来自目标物体、逐顶点，别用面法线（否则硬边）；
3. **权重直接复制目标同一批顶点的权重** —— 壳的顶点就是目标的顶点，
   ⇒ **天生与目标逐位一致**，比任何"最近面/最近点对齐"都准（本轮用骨 7、兜底 0 个）；
4. **UV 平铺**一个"源面料中央"的 UV（源该段是纯色布时最稳；要花纹就得真做 UV 重映射）；
5. **把缝藏在源网格里**：新壳的顶边伸进源网格**内部**（本轮壳顶边预览 z 0.145、
   源切到 0.100，重叠 4.5cm，壳在外 0.2mm）⇒ 切口被盖住、外面看不到缝；
6. **兜底**：源网格剩余部分沿目标法线轻量外推（阈值要比壳的偏移小，否则刚贴好的又被吹起来）。

**验收判据这次变得极简**：逐顶点"壳 − 目标"的有符号距离中位 = **−0.6mm**（就是设计的外扩量），
配合"身体顶点沿自身法线向外打射线、打不到壳"的比例 = **0.0%**。**不再需要解释**。

## T. ★ 同一类错误我犯了两次：在"高曲率、密集、两表面差异大"的区域用间接判据

* 第一次：用"袜子面法线 vs 身体法线夹角 >90°"判折叠 ⇒ 7.66% **假阳性**（真值 0.45%）；
* 第二次：把同一区域的"裸露"读数当噪声 ⇒ **误判成"脚尖没问题"**，实机一看 5 根脚趾全在外面。

两次根因相同：**那个区域的间接判据读不出结论**。
**规矩**：当判据在某个区域**读不出确定结论**时，正确表述是
**"这个判据在这里无效，我无法声称它没问题"** —— 而不是"所以它没问题"。
（前一条是"指标测不出已知现象就是指标错"的加强版：**指标测不出时，结论只能是"未知"**。）

**并且**：脱离困境最快的办法往往不是换更好的判据，而是**换掉问题本身**
（本轮：从"让两个形状互相逼近"改成"复制目标面"，判据随之变成一个直接差值）。

2. 原 `readme.txt`（**必读**）：本轮它写明套装带披肩、更新记录里有「内裤穿透 Tops 隐藏网格」的修复条目

## B. ★ 关键有利条件：先看"零件用的是哪条材质"

本轮内裤与披肩的材质都是 **`某套装OnePiece.001`** = **与军装同一个材质/同一套贴图**
⇒ **不需要新贴图**、mrl3 **一字不改**、包内贴图条目 **15 不变**。
**如果零件自带独立贴图，就得走贴图与槽位那条流程，成本完全不同 —— 所以这一步必须先看。**

## C. 权重的正确来源：从"我们自己的身体"转移；外挂件必须**限定骨集合**

* 原零件的顶点组属于**原作者的骨架**（本轮 VRChat 命名，内裤只有 6 个组）⇒ **一律不用**。
* **贴身衣物（内裤）**：从**我们自己的身体网格**按最近点转移 ⇒ 必然与身体同步（本轮内裤用 5 骨，
  转移距离中位 10.6 mm）。
* **外挂件（披肩）**：同样从身体转移，但**必须限定骨集合为躯干/肩/颈，排除手臂/前臂/手与腿**
  —— 否则披肩会被手臂扯开。本轮做法="按该骨加权顶点质心做几何分类"⇒ **保留 16 骨、排除臂/手 34 骨 + 腿 6 骨**，
  实际用到 14 骨、**无任何臂/手/腿骨**。
  这是**"限定骨集合"，不是"加权重规则"**。
* 收尾：**≤4 影响 + 归一化**（本轮影响数 max=4、行和 min=max=1.000000）。

## D. 变体怎么出：靠"集合成员关系"控制导出 + 极干净的验收口径

每个部位的导出内容由该部位的**集合**决定 ⇒ **同一个工作副本、同一套权重，只切换"零件是否进集合"，
各导出一次**；然后各自替换进基包（基包 = 已验收的那一版）。

**验收口径（本轮实测）**：每个变体应满足
* 条目级：**只有 `wst.mod3` 一个条目不同**，`body`/`arm`/`leg` 的 mod3 与基包**逐字节相同**，
  `mrl3` 全部**逐字节相同**，包内**没有新贴图**；
* 成品 mod3 内部：`meshCount` +1/+2，`vertexCount`/`faceCount` 的增量**严格可加**
  （本轮 `+10 746 = 3×3582`、`+28 476 = 3×9492`、两件 `+39 222 = 3×13 074`），**`boneCount` 不变**；
* 已验收项**不许退化**（本轮核对 `body.mod3` 逐字节相同 ⇒ 展掌拉伸必然不变；`leg.mrl3@36376 = 0x0d` 雪地修正保持）。

> 一个便宜的指纹：作废版与修好版的 mod3 **字节数完全相同但 sha 不同** ⇒ "只改了坐标、拓扑未动"，
> 这正是"修穿模"应有的形态。

## E. 修穿模的最小手法（只动那一个网格）

把穿入顶点沿**身体表面法线**外推，目标间隙 **+0.5 mm**；外推量**先按穿透深度加权**、
**向 1~2 环扩散（衰减 0.6）**、再 **Laplacian 平滑 4 轮（α=0.6）**，迭代到达标。
读数：穿入 **46 → 22 → 4 → 0**（第 3 次迭代达标），随后继续推到 min = +0.50 mm。

**尖刺体检三件套**（改完必量，证明"没有把网格推坏"）：

| 量 | 本轮实测 | 判读 |
|---|---|---|
| 顶点位移 | max **5.16 mm**、均值 0.15 mm（>0.5mm 的 154 个） | 幅度可控 |
| 边长相对变化 | max **16.61%**、均值 0.176% | 最大值落在**原穿模最深那一处** ⇒ 是把折进去的一块摊平 |
| **面法线转角** | max **4.53°**、均值 0.141° | **无方向性尖刺** ✓ |

## F. ★★ 判据陷阱："对衣服的有符号距离"**不是**穿入判据

本轮为了看"内裤有没有穿出其它衣服"，一开始算了对衣服的**有符号**距离，得到 Belt **−9.3 cm**、
Shoes **−14.4 cm** 这类数 —— **全是假信号**：那些点的**最近衣服顶点在十几厘米外**，
"沿它的法线投影"在几何上没有意义。

**规矩**：
* **有符号距离只对"贴身/邻近表面"（如身体）有效**；
* 对**其它衣服**只报**无符号最小距离（是否相交）** —— 本轮内裤到 `Skirt` 最近 12.1 mm ⇒ 未相交 ✓
* 这与 skill 里"对照组要同性质""间接判据在高曲率处失效"是同一条家族：
  **先问"这个量在这个位置有没有意义"，再拿它下结论。**

# 第七次实战：借别的 该角色 套装换袜子（工程 `第3版` 后续，试验10~18）

> 场景：自家这套衣服的袜子"是为高跟鞋做的鞋楦"，怎么改都不合用 ⇒ **从同角色的别的套装借袜子**。

## A. ★★ 先看骨架：同源的话，**配准与权重转移都省掉**

三件候选（冬鹿乃 某袜素材 / 连体丝袜 / 丝狐）的 FBX 骨架 **`Hips` 世界 head 全都与 该角色 身体逐位相同**
（`-0.0000, -0.0165, +0.7596`）⇒ 同一世界空间、**不需要配准**；而且它们的顶点组**直接就是**
`Upper_leg / Lower_leg / Foot / Toe`（长袜件再加 `Hips/Spine/Butt`）
⇒ **权重按名字映射就能用，一行都不用转移**。

**开工清单**（比动手快得多）：`bpy.ops.import_scene.fbx()` 各导一次，只打印
骨架 Hips 世界坐标 + 每个网格的 顶点/包围盒/材质/顶点组/形态键 ⇒ 5 分钟定案。
判据：**Hips 逐位相同 = 同源**；差几毫米还可以靠 `xf` 对齐；差一个量级就是另一套身体。

## B. ★ 借来的袜子要做的三件事（顺序固定）

1. **裁长**：按目标袜的**顶边**用 `bisect_plane` 切、只留下方（切完**必须补三角化**，
   否则导出预检报非三角面）。读数：连体 6939→4110、丝狐 4927→3408；
   本来就短的（冬鹿乃）**不要动**。
2. **袜底对齐**：借来的袜子"鞋底"厚薄不一（实测丝狐袜底比身体脚底低 **22.6mm** ⇒ 像站在厚垫子上）。
   做法：**只在底部一段（脚底往上 20mm 内）做平滑压缩**，把最低点抬到"脚底 −2mm"，
   **上面完全不动** —— 整体上移会让袜筒错位。读数：丝狐抬 20.6mm（1512 顶点）、连体 0.7mm。
3. **权重对齐**：见 D（这一条最贵）。

## C. ★★★ "运动时穿模"：先把三个几何假设都量掉，再怀疑权重

用户报"运动时脚踝处穿模"。三轮量测（`K30_量脚踝.py`）的读数：
* 间隙：袜子**均匀在外 5mm**、**0 穿入** ⇒ 不是间隙；
* 网格：自洽折面判据 **0.06%** ⇒ 不是外推推折的；
* 权重：袜子的"脚→小腿"过渡**比腿皮低 2cm** ⇒ **是它**。

**可移植的顺序**：`间隙 → 网格质量 → 权重`。前两项都能用现成判据一次量掉
（有符号距离 / 自洽折面），别一上来就调几何或加余量。

## D. ★★★ 权重对齐的三条口径都会栽在同一个地方，根因在**身体侧**

| 口径 | 栽在哪 |
|---|---|
| ① 最近面重心插值（原始 `Z28`） | **脚踝前面是凹面** ⇒ 袜子在踝前"跨"过去时，最近皮肤点跳到小腿或脚背 |
| ② 按 z 分箱建权重表 | 身体腿部网格是**稀疏环状**的（实测 z∈[−0.89,−0.867] **一个顶点都没有**）⇒ 空箱被邻近箱填成**阶梯函数** |
| ③ 同侧 z±窗口 KNN | 窗口再大也只够着"最近的那一环"，拿不到环间插值 |

**三轮结果几乎一样 —— 这就是"问题不在袜子"的信号。** 于是做**顶点级三方对拍**
（袜子顶点 / 我算出的表项 / 最近的皮肤顶点，并排打印）：

```
袜 #438 z=-0.8801  实际(小腿0.337 脚0.663)  表(小腿0.000 脚1.000)
皮 #620 z=-0.8657 x=0.0552 -> 小腿1.000 脚0.000
皮 #623 z=-0.8667 x=0.0744 -> 小腿0.000 脚1.000   ← 同一圈里权重是"混"的！
```

**根因：身体自己在脚踝那一圈的权重就是乱的**（30 个顶点里 26 个"小腿 1.0"、4 个"脚 1.0"）
—— 上一版从供体转移权重留下的噪声。身体自己的脚踝形变就错，**袜子怎么对齐都错**。

**修法（`Z31_修脚踝权重.py`，身体侧）**：**腿是圆柱面 ⇒ 权重应当只随高度变化**。
按 z 分 1cm 箱取平均 → **沿 z 滑动平均 2 轮**抹平混圈 → 每个顶点按自己的高度取插值剖面写回
（只做腿部 z∈(−1.02,−0.20)，**不碰裆部**）。修完剖面单调光滑：**脚 0.995 → 0.73 → 0.18 → 0**；
袜子跟着对齐后整段与腿皮的差从 **0.75 降到 ≤0.033**（只剩 1cm 档 0.38，
那是身体环距 3.5cm 的采样差，要重做身体踝部网格密度才能消）。

**可移植的两条**：
* **"贴身衣物怎么对齐都不对" ⇒ 先量身体的权重场一致性**（同一圈内的权重方差）；
  圆柱部位（腿/臂）的权重**本就该只随高度变化**，用"按高度取剖面 + 沿高度平滑"一把修干净；
* **"这个网格的权重噪声"会同时坑所有借来的衣服** —— 修在身体侧一次，所有变体都受益。

## E. ★ 借来几何 + 换自家材质（"UV 搬过去"）——**两次都失败，别再试**

想让借来的袜子用自家袜的贴图：按**最近顶点**把自家袜的 UV 搬到借来的袜子上
（KD 树，2 万个面角全部搬到、0 漏）⇒ 用户两次反馈"贴图和建模配合得很怪"（`试验13`/`试验14`）。
原因：**拓扑不同的网格之间，最近顶点的 UV 对应关系不是连续映射** ⇒ 纹理被撕碎/错位。
⇒ **要"自家材质 + 借来几何"就得真做 UV 重映射（按柱面参数化重展 UV），别指望搬最近点。**

## F. 预览检视工程：几条"看起来没贴图/显示不出来"的真原因

给用户"自己打开 Blender 看"的检视工程时，这几条每次都中招：

| 症状 | 真因 |
|---|---|
| "没有贴图"（Solid 模式） | Solid 模式默认**不显示贴图** ⇒ 必须把视口设成 `shading.type='MATERIAL'` 且 `color_type='TEXTURE'` |
| 贴图挂上了但发灰/发白 | FBX 从 Unity 转进来的 Principled 带**自发光/镜面**项 ⇒ 把 `Emission Color` 涂黑、`Emission Strength=0`、`Metallic=0`、`Roughness≈0.85`，让贴图说话 |
| 材质名对不上（大写/小写、`Stocking` vs `stocking`） | 必须**大小写不敏感 + 前缀匹配**地查映射表；否则静默漏挂 |
| "某个集合无法显示" | 用了 `collection.hide_viewport`（大纲里那个**小复选框**）⇒ 用户点**眼睛**没反应。要用 `bpy.context.view_layer.layer_collection.children[name].hide_viewport`（**眼睛**）；`LayerCollection` **没有** `hide_render` |
| 全白 | 灯光过曝（sun 3.0 + Standard view transform）⇒ 降到 ~1.0，或换 AgX |

## G. 解 `.unitypackage`：**按 GUID 目录成对取 pathname/asset**

`.unitypackage` 是 tar.gz，每个资产一个 GUID 目录，内含 `pathname`（原始路径）/`asset`/`asset.meta`。
**必须先把成员按第一层目录（GUID）分组，再取该组的 pathname 与 asset 配对** ——
按 tar 顺序"读到 pathname 就配下一个 asset"会**张冠李戴**：本轮的 `.fbx` 一度被写成了
**别人的 prefab YAML**（症状：Blender 报 `ASCII FBX文件不被支持`，而文件头是 `%YAML 1.1`）。
另外：`pathname` 是**相对路径**（`Assets/...`），必须接到"该包的解包根目录"上才能落到真实文件。
**Blender 4.2 的 FBX 导入器不支持 ASCII FBX** —— 但先把解包配对修好，往往就不是 ASCII 了。

## H. 骨号/材质名/贴图的"逐包核对"要**从 zip 里读**，不要读当前树

每出一版，成品树会被覆盖 ⇒ 想核对"某一版里 leg 的材质指向哪张贴图"，
必须**从那个 zip 里解出 mrl3 再解析**（本轮四份变体就是这样确认 `Sock某袜素材/SockBody/Sock某袜素材/SilverSocks`
各自指对的）。读当前树只能确认最后一版。

## B. ★★ `U_socks` 不是"高跟鞋姿态" —— 同一个部位，两版的答案可以完全相反

提示词里（依据经验）预判本版 `U_socks` 大概又是"为高跟鞋做的鞋楦"，需要旋转/切脚/复制脚面做壳。
**实测三条把它否掉了**：

| 量法 | 读数 | 含义 |
|---|---|---|
| 形态键 `Foot_highheels` 的**键值** | **0.0** | 预览用的是平放姿态 |
| 袜「最低 1.2 cm 层」的 PCA **最小轴**（= 鞋底法线） | **与竖直差 0.1°** | 脚底是平的 |
| 袜底最低 z（工作）vs 身体脚底 | −1.0068 vs −1.0054 ⇒ 只在脚底下 **1.4 mm** | 正常袜子厚度 |
| 袜脚区对身体的**有符号**距离 | 中位 **+1.4 mm（在外侧）**、99.75% 在外 | 不是"陷在里面" |

⇒ **只需 1.0 mm 单调外推兜底**（只把贴进皮肤的顶点推出去、从不内移）：作用 42 个顶点、复核穿入 0、最小 +0.7 mm。
**没有改作者配好的形状**（skill 那条最贵的教训）。

**可移植的两条**：
* **"袜子/贴身件要不要手术"必须每版重量三件**（主轴角度 / 形态键值 / 有符号距离），
  不能继承上一版的处置 —— 同一个角色、同一个部位，两版的答案可以完全相反。
* **符号约定别抄错**：`find_nearest` 返回的 `(loc, nrm)`，`dot(q−loc, nrm) > 0` 是**在外侧**。
  本轮 `X1` 里写成 `sgn = −dot` 并把读数标成"陷入"，于是"99.75% 陷入"其实是"99.75% 在外"，
  差点按错误的结论动手。**判据的符号必须在"已知答案的点"上标定一次**（skill 的老规矩）。

## C. ★ "纯均匀 ×100"怎么确认、以及它省掉了什么

素材 的骨架 `Armature.1`（261 骨）与 该角色 的 `Armature`（222 骨）**有 33 个同名骨**，
逐骨对拍 **head 距离 max = 0.000000 m** ⇒ 就是 该角色 骨架 ×100（无旋转、无偏移）。
**做法**：X1 采集时把该集合的对象 `world` 整体 ×0.01（骨架的骨 head 也一起 ×0.01），
于是 `Y1` 的相似变换 `xf()` 一行都不用改（`xf` 仍由 `Body_base` 的预览 local vs 工作 local 解出，
实测仍是 `s=1.379583 t=(0,+0.0242,−1.026176)`，与 第2版·第3版 逐位相同）。
**一旦"×0.01"是在采集端做的，所有消费 `world` 的量（链根、几何 tip、权重 u 的投影轴）就天然一致**
—— 这正是把 skill 里那条"两条并行的建链代码要统一坐标系"的坑堵在源头上。

## D. ★ 链：`nodeCount` 最小 2 的预算该按"几何/方位"分配，不是平均分

**裙 16 片 → 12 条链**：素材 的裙子有 16 条侧链（每侧 8 片 `PB_skirt_1..8_L/R`，绕腰一圈，
方位角 11.9°~172.3°）+ 正前 + 正后。每片一条要 36 骨，塞不下 41 的池子。
**做法**：把每侧**方位间距最小的 3 对**并起来（实测 `(7,8)=15.1°` `(2,3)=19.2°` `(5,6)=26.6°`，
比 `(3,4)=27.2°` `(4,5)=30.2°` 小）⇒ 每侧 5 条 + 正前 + 正后 = 12 条（24 骨）；
body 再放 5 条（头饰飘带 2 + 尾巴 1×3 节点 + 双马尾 2×5）= 17 骨。**41 骨刚好用满池子**。

**链根位置用"源骨架骨 head"、链长/方向用"几何 p95"** —— 与 第3版 同一口径（本轮已证同名骨 head 逐位相同）。
**★ 一条新踩的坑在 E 节。**

## E. ★★ "只收主导组"的几何口径会漏掉某些链组，然后**静默退回假值**

`Y1` 建 `_grp_pts` 时只收"该组是顶点主导组"的点（为避免同组跨多网格把质心拉偏）。
但 `head_dress_Fril_master_L/R(.001)` **从来不是任何顶点的主导组**（那片的顶点主导组是
权重 1.0 的 `head_dress` / `headdress_L.005`）⇒ 收到 0 个点 ⇒ `chain_tip` 返回 `None`
⇒ **静默退回骨架骨 tail**，链长变成 **0.0297 m**（= 导入器的显示骨长，假值）。

**修法**：对"主导组为空、但该组权重>0 的点够多"的组，改用量重>0 口径。
读数：链长 0.0297 → **0.0947 m**（1412 个点）。
**判据（很好用）**：**链长为 0、或恰好等于骨长时，先怀疑"这个组有没有主导顶点"**。
（这与 skill 里"指标测不出时结论只能是未知"同族 —— 这里的表现是"指标给了个假值而不是空值"，更难发现。）

## F. ★★ UV 光栅化：绕序要按每三角形自己的有符号面积，而且**边函数与鞋带公式符号相反**

skill 已有"镜像岛要用每三角形自己的符号"这条，本轮又踩一次、而且踩出了一个**符号陷阱**：

* 第一版用固定符号 `d > 0` ⇒ `__8/__5/__10/__7/__6`（正绕序）能量，
  `__11/__12/__9`（镜像岛，Gold/U_贴片件）**全部量成"掩码为空"**；
* 改成 `(d > 0) if s2 > 0 else (d < 0)` ⇒ **全空**（符号又反了一次）；
* 正确写法：**`inside = (d * s2) < 0`**。

**为什么**：边函数写成 `Σ (P−a)×(b−a)` 时，它与鞋带公式 `Σ (a×b)` **符号相反**，
所以"内部"是**异号**（乘积 < 0），不是同号。
**可移植的一句**：**任何"用有符号面积判内外"的代码，先在一个已知形状（正绕序三角形 + 一个点）
上标定符号**，别靠推理。

## G. ★ "删掉没用的贴图"不能只看名字 —— 反向验收就是专门抓这个的

上一版遗留的 `MiliCuteNavy.tex`（21MB）、`ribbon_black.tex`（1.3MB）看着是死文件，

# 第九次实战：一份工程出 N 份特征变体（开关矩阵 + 命名口径，工程 `第4版`）

> 场景：同一个模型，用户要"有/无内裤、有/无原版尾巴、有/无丝袜、有/无描边"的各种组合。

## A. 开关矩阵与命名口径

**开关全部走命令行**（`bash Z9_出一版.sh <包名> <开关...>`），每个开关只做一件可判定的事：

| 开关 | 含义 | 实现要点 |
|---|---|---|
| `nounderwear` | 不出内裤（+ 内裤下那张创可贴） | 从 `NEW` 的"跳过表"里过滤 |
| `nosock` | 不出丝袜（leg 改放"隐形脚部载体"） | 载体 = 身体脚部缩到 0.9，藏在自己内部 |
| `nooutline` | 不做描边 | 跳过建壳 + **跳过描边材质脚本** |
| `origtail` / `origear` | 保留**原版**尾巴 / 耳朵（默认删） | 只改"删除清单" |
| `nomtail` | 不出**衣服的**尾巴 | 与 `origtail` 配对用 |
| `tailgrav=` `tailtrans=` `taildamp=` | 尾巴手感（观感类参数） | 让用户一句话迭代，别让助手猜 |

**命名口径**：`<主体>_<维度1>_<维度2>_... .zip`，每个维度写**取值**而不是写测试号 ——
如 `女仆装_有内裤_衣服尾巴_有丝袜_有描边.zip`、`女仆装_有内裤_原版尾巴_有丝袜_无描边.zip`。
（用户明确要求"用**简体字** + **其中包含的特征**命名"。维度取值要么"有X/无X"，要么"X=取值"。）

**好处**：用户看一眼文件名就知道里面是什么；旧测试号包一律挪到 `_旧测试号\`（连 `_snap_*` 一起），
避免"拿错包"这类最贵的错误。

## B. ★ 删一件时，要顺着看它的"邻居"（用户事后才发现的那种）

本轮删了内裤，**用户随后发现内裤下面还贴着一张创可贴**（`U_bansoukou_under`，117 顶点）——
没有内裤时它露在外面很怪。

⇒ 把创可贴**并进 `nounderwear` 开关**。
**可移植的做法**：每引入一个"隐藏某个件"的开关时，**先列出"它盖住的 / 盖住它的"邻居件**
（用最近距离或层级关系扫一遍），一起决定它们的去留；否则用户会在实机里一个一个发现。

## C. ★ 关掉一个特性时，要一并删掉**依赖它的历史遗留对象**

本轮加"无描边"开关时发现：上一版留下的 **`Animal_Ear__Outline_Black` / `Tail__Outline_Black`
是描边壳对象**，如果只是"不新建壳"，这两个**旧壳仍会被导出、但它们要用的 `Outline_Black` 材质不存在**
（因为跳过描边材质脚本）⇒ "有网格无材质"。

**规矩**：任何"关掉某特性"的开关，都要问一遍——**有没有历史遗留的对象/材质/链是依赖这个特性的？**
有就一并删。判据很好验：`Z14` 的反向检查（活材质→贴图都在包里）会抓"材质缺失"这一类。

## D. ★★ 同一个量在两处用**不同口径**定义 ⇒ 诊断读数会误导你

本轮给尾巴换节点时，"权重铺得均不均匀"有两个 `u`：

* **建件脚本（Y1）里的 `u`** = 顶点在**折线中心线上的弧长参数**（权重就是按它分配的）；
* **体检脚本（Y8c）里的 `u`** = 顶点在**"首骨 head → 末骨 tail"这条弦**上的投影。

尾巴是**弧线**，两者差很多 ⇒ 用 Y8c 的读数看，会得出"中间节点没有权重"的结论 ——
而按 Y1 的口径它其实铺得挺好。

**规矩**：把"权重是按什么参数分配的"写进体检脚本的注释里；两个口径不一致时，
**要么统一，要么在报告里明确写"这里量的是弦投影，不是分配用的 u"**。
（同族：skill 里"指标要能区分假设"、"对照组要同性质"。）

## E. 顺带：链骨号"按链名固定分配"

开关会增删链条（如 `nomtail` 少一条 5 节点链）。如果号是"按部位顺序发"的，链条数量一变，
**其余链的号会整体漂移**，而 `Y4`/`Y4b` 里是硬编码列表 ⇒ 号与链错配且**不报错**。
做法：`CHAIN_FNS = {"MaidTail": [144,145,146,147,148], ...}`，按名字取并断言数量一致。
（详见本 skill 的「链条的节点该放在哪」§4。）

   **★ 顺序**：必须在所有改身体权重的步骤之后 —— `Y11 → Z26 → Z27 → Z31 → Z33 → Z28 → Z32`。
2. **硬的环/带类 ⇒ 查"面片弦切"**：`足リング` 的权重与皮肤完全一致（L1 0.000），

## F. ★★ 身体侧的"提胯拉扯 / 裆底敞开"：分界高度是**曲线** + 平滑带
用户反馈：待机"左右切换重心、提胯"时另一条腿的**大腿上部被明显拉扯**；直立时**裆底最下面被拉向两侧敞开**；
且"**上一个模组就有、本模组完全一致**"⇒ 从基壳继承的**身体侧**问题（不是衣物/素材）。

实测（纯 python 跑预览 JSON 即可，不需要渲染）：
* 先排除"被两条腿同时拉"：全网格 `Upper_leg.L` 与 `Upper_leg.R` 同时 >0.2 的顶点 **= 0** ⇒ 左右分派干净。
* **大腿上部**：同一条腿、同一 2cm 高度环内 `Hips` 的 **sd = 0.354、极差 0.96**（z≈0.69）⇒ 圈内错开 = 撕扯。
* **裆底**：中线有一条 **2mm 的硬边界**（`z=0.639` 处 `Hips=0.46`、`z=0.641` 处 **`Hips=1.00`**）。

修法（新增 `Z33_修胯与裆部权重.py`）：取 `pool = Hips + Upper_leg.L + Upper_leg.R`，
按 `t = smoothstep((z − (zc(|x|) − HW)) / (2·HW))` 重分配（`Hips = pool·t`、腿 = `pool·(1−t)`，腿内按原比例）。
**其余骨骼（`Butt.L/R` 臀部抖动、`Lower_leg`、`Spine`）一个都不动**；pool 守恒 ⇒ 总权重不变
⇒ 对"腿权重本来就小"的顶点是**恒等变换**（第5版 只改 889~1567 / 16517 个顶点）。

**★★ 分界高度 `zc` 是随 |x| 变化的曲线，不能按高度一刀切。** 骨盆下缘本身就是曲线 ——
**中线最低（裆底 ≈0.655）、两侧最高（髋 ≈0.705）**。照"只随高度"平铺会把**本该跟骨盆的会阴**拉到腿上
（我第一版就犯了这个，改动顶点 1507 反而更糟）。参数：`ZC_MID=0.655 / ZC_SIDE=0.705 / ZC_W=0.05 / HW=0.035`。

**验收**（都能纯 python 从预览 JSON 算）：
① 同一侧 + 同一高度环内的权重 **sd**（圆柱部位本就该只随高度变化）；
② 沿 z 扫描找**硬跳**（相邻 1~2mm 的圈之间权重突变）。
读数：带内 sd 中位 **0.151 → 0.065**；两侧 **0.354 → 0.127**；裆底剖面从 2mm 硬跳 → **70mm 平滑上升**；
`body.mod3` 尺寸**不变**（影响数没变 ⇒ 没引入新风险）。

## G. ★★ 光照异常先做 **CB 44 字段对拍**，别猜系数
用户反馈"阴凉 / 阳光未直射时亮度正常，但**阳光直射时变成一团白光**"。
把我们的材质与**用户满意的基壳材质**（body `__1` 身体）**逐字段对拍 CB 的 44 个字段**：
**只有两个字段不同** —— `fBaseMapFactor` 0.30 vs 0.40、`fEmissiveMapFactor` 2.35 vs 2.00；
其余 42 个（含 `fSpecular`、`fEmissiveBlendColor`=0 且 blend=0、`fAddColor*` alpha=0、雪参数）**全同**。
**选旋钮的判据 = "这个字段只影响被光照到的那部分吗"**：
* `fBaseMapFactor` / `fSpecular` ⇒ 只在被直射时起作用 ⇒ "只有直射过曝"就该动这两个
  （`Base 0.30→0.10`、`Spec 1.0→0.30`；自发光占比 88.7%→96%，**阴凉处差 <1%**）

## A. ★★ 交接材料里"已探明"的数据**本身可能就是错的** —— 三条都被实测否证

上一版（第十次实战 A）的教训是"交接材料里的**坑**要实测"；这一轮更进一步：**"已探明"的读数也要复核**。

| 交接材料说 | 实测 | 后果 |
|---|---|---|
| §2.2 表格 `A_Collar` 用 `A/Metal/Jewel` | **整列错位一行** —— 那三个材质是 `A_Top_Ribbon` 的；`A_Collar` 在预览里**根本没有材质槽** | 按表建件会拿到错的贴图 |
| （同上）`Tail.001` 材质"见报告" | 也**没有材质槽**；源里真正的归属在 `_extracted\resolved_mats.json` 的 **`slotmap_prefab`**（对象名→材质名）：`A_Collar→A_White`、`Tail→fur` | 漏掉一个材质（`fur` = **无贴图的平涂色**），布类实际是 **9 个**不是 8 个 |
| §2.5 丝袜"绕踝 6.2°" | 最小二乘拟合鞋底剖面得 **9.20°**；且 6.2° 的残差带 10.3mm、9.2° 只有 4.8mm | 按 6.2° 转会**转不够**，脚尖仍翘／鞋底仍斜 |

**做法（可移植）**：
1. **"某件没材质/材质可疑" ⇒ 先查源包的 `resolved_mats.json → slotmap_prefab`**（对象名→材质名 + 贴图），
   它比预览工程权威；预览工程里**没有材质槽**的对象在导入时就会静默变成"无材质"。
2. **角度/长度这类几何量一律自己拟合**（这里用"沿脚长分箱取最低 z + 最小二乘"，再对比两种角度的残差带），
   别信交接材料里"atan(Δz/Δy)"式的算术 —— 它假设了鞋底是平面，而实测那只袜子是
   **rocker（脚尖 9cm 平垫 + 后跟翘）**，不是平面。

## B. ★★ 穿模外推会把网格**推坏**，刚体旋转**不会**

用户："脚尖的袜子形成了**不规则的尖刺**"。判据用 **面法线 vs 它自己三个顶点的顶点法线**的转角
（**自洽**判据；skill 第七次实战 Q 已说过"判网格坏没坏不要跟别的物体比法线"）：

| 状态 | max 转角 | >30° 的三角 | >60° 的三角 |
|---|---|---|---|
| 源几何（预览里原样） | 69.75° | 152 | 22 |
| **只做绕踝刚体旋转** | **69.75°** | **152** | **22** ← **逐项相同 ⇒ 旋转零副作用** |
| 旋转 + 迭代外推（沿身体法线，4 轮） | **164.67°** | 236 | 50 ← **尖刺就是这一步造的** |
| 旋转 + `proj`（投到体表+余量）2mm 限幅 | 109.54° | 165 | 72 |

**三条可移植的规矩**：
1. **交付前对每个改过几何的件都跑一次这个判据，并与"源几何基线"比**（翻倍 = 有尖刺，别只看绝对值）。
   把基线数字写进报告（`第6版` 是 max 69.75° / 152 / 22）。
2. 高曲率区（**脚趾、指尖**）**宁可留穿入也不要推**：那里"最近特征会跳变"，沿法线推会做出
   "每根脚趾一个包"。残余穿入如果**被脚底/脚踝挡住看不见**（`第6版` 是 556 顶点 / 最深 11.5mm）
   就留着；要真收干净只有一条路 —— **"复制目标面外扩 0.6mm 做壳"**（第七次实战 S）。
3. **外推限幅要"累积"**（相对 P0 的总位移），不是"每轮" —— 后者 4 轮可累积 4 倍
   （实测 43.76mm 的失控位移）。而且要**按件给上限**：粗环/足弓这种"天生悬空 12.8mm"的地方要单独放大。

## C. ★★★ 修一个症状会造出另一个症状 ⇒ **两个判据一起看，而且要分带**

用户第一轮："扭腰时裆部被扭变形 + 裆部紧身衣拉长到腿部" ⇒ 我加了 `Z34_修裆部拉伸.py`（身体侧，
把裆的腿权重让给骨盆）。用户第二轮："**裆部确实不怎么扭了，但是大腿的扭曲非常严重**"
⇒ 第一版修过头了。

> ★★★ **别跳过：两条纪律**（本线最贵的一课；也正是**同一个 bug 在 `第5版` 上同样存在**的原因 ——
> 基壳身体在"裆 / 大腿内侧"的 `Hips ↔ 腿` 分配不一致，而 **Z33 只治了噪声与硬跳、
> 没治"中线附近本该更跟骨盆"**）
>
> 1. **必须两个判据一起看**：① 摆姿势下的边长拉伸率（= **症状**）＋
>    ② 同一高度环内 `w_leg` 的 sd（= **副作用**）。
>    只盯 ① 就会造出"大腿扭曲"，而 **② 当时就在报警 —— 我用"这个判据在这里不适用"把它忽略了**，
>    那正是这次的病。**指标报了警，不能因为"解释不通"就无视它。**
> 2. **判据② 必须分带**：**大腿段（预览 z 0.44~0.62）基线 sd max `0.0118` ＝ 护栏**
>    （那里任何 `|x|` 依赖都是凹痕 ⇒ **不许变差**）；**髋部带（0.63~0.70）的 `0.217` 只作参考**
>    （Z33 自己就管这里、实测过且用户认可）。
>
> **★ 回植到其它版本（已回植 `第5版`，2026-09-24）**：只改脚本里的**工程路径一处**，
> 再插进 `Z9` 的 **`Z33 之后 / `Z28`·`Z32` 之前**（带 `nocrotchstretch` 开关），**其余一字不改**；
> 然后对"**已交付的每一份包**"用**原开关**重跑 + `Z14` 验收。
> **⛔ 不要动**：`Z32` 的对齐表、`Z34` 与 `Z32` 的先后顺序、以及**材质配方** ——
> `第5版` 的贴图是**深色**，照抄本轮的 `Base 0.40 / EmiF 2.00` 会让它**变暗**

**判据设计**（这一节是本轮最贵的教训）：

| 判据 | 量什么 | 只看它的后果 |
|---|---|---|
| ① **摆姿势下的边长拉伸率** `\|L/L0−1\|`（抬腿 25° / 扭腰 20°，近似 LBS = 绕骨 head 转、按权重加权） | 裆部被扯得多狠（**症状**） | 看不到"大腿上部不再跟腿" |
| ② ★★ **同一高度环内 `w_leg` 的 sd**（Z33 的老口径） | 圆柱部位（腿）本该只随高度变化（**副作用**） | 看不到裆部拉扯 |

第一版**只盯①**：影响区做成**矩形**（`|x|<0.14`，一路管到裆底以下 10cm）
⇒ 同一高度上"内侧跟骨盆、外侧跟腿" ⇒ ①变好、**②从 0.148 涨到 0.256** ⇒ 实机"大腿扭曲严重"。
**判据②当时就在报警，我用"这个判据在这里不适用"把它忽略了 —— 那正是这次的病。**

**两条做法**：
1. **影响区用"以关键点为中心的椭圆"，不要用矩形**：`t = K·(1 − smoothstep(0.55, 1.0, sqrt((x/XR)² + ((z−ZC)/ZR)²)))`。
   椭圆的 |x| 半宽随"离关键点越远"自动收窄 ⇒ 腿段天然不受影响。定稿 `ZC=0.648 / XR=0.040 / ZR=0.035 / K=0.60`
   （预览坐标；裆底 = 0.648）。
2. **判据②必须分带**（把"合理的曲线"与"不该有的凹痕"分开）：

   | 带 | 预览 z | 基线 sd | 处理 |
   |---|---|---|---|
   | **大腿段** | 0.44~0.62 | **0.0118** | **护栏**：任何 \|x\| 依赖都是凹痕 ⇒ 不许变差 |
   | 髋部带 | 0.63~0.70 | 0.000~0.06 | 只作参考（Z33 实测 max **0.217** 且用户认可，同量级即可）|

**定稿读数**（真实流水线；`第6版\project\_Z34_裆部拉伸_*.txt`）：
```
判据①  max 2.920→1.109（−62%）｜p95 0.513→0.461｜p99 1.519→0.638（−58%）｜>10% 的边 299→281
判据②  大腿段 sd max 0.0102→0.0102（**分毫未动**）｜髋带 0.062→0.241
改动顶点 467（2.8% 全网格；第一版是 1581 / 9.6%）
```
★ 参数扫描表（`_Z34_扫4.txt`）：`XR=0.040 ZR=0.025~0.035 K=0.6` 腿段 sd = 0.0118（安全）；
`ZR=0.048` 起腿段开始超（0.026）；`XR=0.052 ZR=0.070 K=0.9` 是"大腿扭曲"那一版（0.19~0.41）。
**想更狠就必须复核腿段 sd —— 超了就是拿大腿换裆部。**

## D. ★★ 预览 JSON 的权重场 ≠ 工作 blend 的权重场

同一个区域（裆/大腿内侧），**预览 `_X3_preview.json`** 里 `Hips` 均值 **0.616**、
**工作 blend 的 `Body_base`** 里是 **0.279**（后者已经过 第1版 的权重传递 + Z26/Z27/Z31/Z33）。
我拿预览离线（纯 python）调出来的裆部参数（`X_HALF=0.10/K=0.8`）落到工作 blend 后，
`>10%` 的边数反而**涨了 77%**；最后是在**真实权重场**上扫参数才找到最优。

**做法**：纯 python 离线试参数只用来**定方向与公式**；**幅度与边界必须在目标文件上扫**。
给脚本加一个 `dry=1` 模式（**只扫不写盘**、打印判据对照表）—— 一次 1 分钟，比"改—导出—进游戏"快两个数量级。

## E. "衣服灰暗 / 没有反光"：先做 **CB 资源对拍**，再动系数

**不要**先怀疑色彩空间或贴图。做法（`第6版\project\_cb_full.py`）：把我们的材质与**用户满意的基壳材质**
（`Ch_Standard_Mt__1` 身体）逐项并排打 —— **11 个贴图资源 + 44 个 CB 字段**。

实测结论：`第6版` 的材质与 **第4版、第5版（用户都认可）** 的
`ColorMaskMap / FxMap / FurMap / PanoramaMap` **逐项相同** ⇒ **不是资源指向的问题**；
唯一动过的是 第5版 末期为了治"阳光直射变成一团白光"压下去的两个数：
`fBaseMapFactor` 0.30→**0.10**、`fSpecular` 1.0→**0.30**。

**机理**：白贴图（alpha≥250 区均值 255）+ 自发光占比 96% ⇒ 只剩一片**平的发光**：
没有明暗、没有高光 ⇒ 看着就是"灰暗、没反光"。
**改法**：改回**用户一直满意的身体材质那一档** —— `Base 0.40 / EmiF 2.00 / fSpecular 1.00`
（对白贴图算 等效发光 = 2.00 × 1.00 = **2.00**，正好落在用户认可过的 2.08 / 2.19 上）。

★★ **并且把这三个数做成命令行开关**（`第6版\project\Z10_只改配方.sh <包名> base=.. emi=.. spec=..`，
约 20 秒一次）—— 观感类参数**永远不要让用户等我改代码**：

| 症状 | 怎么调 |
|---|---|
| 偏暗/发闷 | `base` 抬到 0.5、`emi` 抬到 2.4 |
| 阳光直射过曝 | `emi` 降到 1.6；再不行 `spec` 降到 0.6 |
| 还是"没有反光" | `spec` 已 1.0（标准值）⇒ 问题只在 `assets\RMT` 那张 RMT 图，或者该部位本来就该亮 |

⚠ **这套数字不能跨贴图搬**（skill 第十次实战 §5.3）：第5版 的贴图是**深色**，
`Base 0.40/EmiF 2.00` 会让它变**暗**（等效发光 2.00×0.3 = 0.6）⇒ **同一个 bug 在深色套装上要另定标**。

## F. ★★ 链清单做成"单一数据源"（根治"开关改了、ctc 没跟上"）

`Y1_构建.py` 建完链，把**实际链清单**（链名 / 骨号 / preset）写进 `_Y1_链清单.json`；

另外 `Y1` 的 `DEL_RANGE` 要**同时删旧链骨的两个号段**（`140~193` **与** `206~246`），否则

## G. `FORCE_CHAIN`：整件**没有任何顶点组**的件 ⇒ 按"链投影"白送权重

实测：衣服自带的兔尾 `Tail.001`（86 顶点 / 168 三角）**0 个顶点组**、无材质槽 ⇒ 不处理的话
所有顶点会落到"部位兜底骨"上 = **焊死**。做法：`FORCE_CHAIN[对象名] = 链名`，
逐顶点按 `u = 投影到链轴` 用帐篷函数把权重分给该链的节点（与链权重同一套公式）。
★ 兜底骨也要**按件**给：头发/耳朵的落单顶点必须挂 `Head(4)`，不能按部位兜到 `Chest(2)`
（实测 `TD_Main` 有 160/2405 个顶点没有任何顶点组，挂 Chest 会被胸口拽着动）。

## H. 折线链只在"真是一条弯链"时用（判据：弧长/跨距比）

`第6版` 的肩褶是**三片散开的小片**（空间上前后外各一），我把它们塞进一条折线 ⇒
`order_segs_geo` 排出**往复折线**：**弧长 0.1495 而几何只跨 0.044** ⇒ 节点飘在 15cm 外。
比基尼飘带同理（往复 1.3cm、总弧长 2cm）。
**规矩**：先量 `弧长/跨距`，偏离 5% 以上才用折线；散了的小片走 `chain_tip`（根 = 源骨 head、
尖 = 几何 p95）的**直线轴**。可对照：双马尾的弧长/弦长 = 1.028（只有 2.8% 偏离）⇒ 该用折线。

## I. 死贴图清理：判据就是 `Z14` 的反向检查

## 2. ★★ 最容易抄错的一步：排除带的判据

**症状**：描边做完，某个"贴在别的件表面上"的小件（蝴蝶结、发绳、蕾丝贴片）**整块变黑**。

**原因**：它贴在 A 的表面外仅 0.09 mm，而 A 的壳在 1 mm 外 ⇒ **它被夹在 A 的表面与 A 的壳之间**
⇒ 从外面看到的是"包在它外面的那层黑壳"。

**第一版照抄的判据**（第1版 的写法）："壳顶点离该小件的距离 < 2 mm 的壳面丢掉"。
**它在 第4版 上失败了** —— 因为**相互贴着的两件会互相吃掉壳**：
内衣被吃 61%、内裤绳 78%、绷带整片被吃光（改前 4 个件各丢 17~78% 的面）。

**改对之后的判据**（一条就够）：
> 切掉壳面 **当且仅当** `d_别件 < min(d_本体, 2mm)`
> —— 即"**别的件夹在本体表面与壳之间**"。

| 情形 | d_别件 | d_本体 | 判定 |
|---|---|---|---|
| 蝴蝶结贴在头发卡片外 0.09mm | 0.91mm | 1.0mm | **切** ✓ |
| 内衣在裙子**里面** | 间隙+1mm | 1mm | **不切** ✓（本来就不是轮廓） |
| 内裤绳贴在绷带**外面** | 0.7mm | 1mm | **切** ✓（否则绳会把绷带糊黑） |

改完丢面量：裙 **0.25%**、臂 **0**、袜 0.2%；头发件仍丢 10~18%（**卡片互相叠压**，那些区域不是轮廓）。

**另一个更干净的做法**：壳**按"源件"整体建一个**，而不是按"按材质拆出来的子对象"各建。
本版每件都被拆成 cloth+gold 两块，两块**共面** ⇒ 按子对象各建会得到两层重合壳、金饰必糊黑。

## 3. 三个静默的坑

1. **丢面后留下孤立顶点** ⇒ 导出器预检直接报 `LooseVerticesOnSubMesh`。
   必须"只保留还有面的顶点 + 重映射下标"，并把位移/权重按映射补回去（带形态键的还要补到每个键块）。
2. **描边材质会被"从 `.bak` 重算材质指向"的那一步静默抹掉**。
   `第3版` 就是这样把 `Outline_Black` 丢掉的（四个 mrl3 里都没有该条目），
   于是用户看到的模型**完全没有描边**，而所有脚本都"成功"。
   ⇒ **流水线顺序铁律：材质指向脚本（`Y3`）→ 描边材质脚本（`O2`）**；`O2` 就地打补丁、幂等。
3. **取空贴图槽时要把"只被死材质引用"的槽也算上**：`body` 的 45 个槽全都被死材质引用，
   只认"从未被任何材质引用"的槽会取不满需要的 5 个（实测报"没有可用空槽"）。
   游戏不实例化死材质（skill 已验证）⇒ 改它引用的槽对观感无影响。

## 4. 要不要给某个件做壳？——按"它有没有轮廓"判断

* **做**：厚实件（衣服、袖子、裙、袜、鞋）、**头发卡片**（卡片自身的壳能出轮廓，实测有效）
* **可以不做**：贴在别的件上的小配饰（发绳、蝴蝶结）—— 它没有独立轮廓，
  被别件的壳"绕过去"不影响观感，但**要保证它不被别件的壳糊黑**（即上面 §2 的判据）。
* **代价**：每个壳约等于本体一倍的几何（本版 20 个壳让包从 56.6 → 61.2 MB）。

# 附：链条的节点该放在哪（尾巴调飘的三条，都有实测数字）

> 场景：`第4版` 用户反馈"衣服尾巴飘不起来、很沉"。改完的结论按重要性排序如下。

## 1. ★★ 弯曲的链，节点必须落在**弧线中心线**上，不能落在"根→最远点"的弦上

原来 `MaidTail` 的节点由"根 → p95 最远点"的**直线弦**均分。实测尾巴的真实中心线
（12 个段组质心连成的折线）**弧长 0.6525（预览）**，而弦只有 0.5467 ⇒ **弧比弦长 19%**，
**中段偏离弦 0.112 预览单位 ≈ 15 cm** —— 而尾巴本体的粗细远小于 15cm
⇒ **关节飘在网格外面**，物理在"一条不存在的直线"上转，看起来就是硬、沉。

**做法**：`seg_nodes(srcname, segs, n_new)` —— 取该链所有段组的**加权质心折线**，
沿弧长均匀取 n_new 个点（并在根部外推半步，使首节点落在"接在身上"的位置）。
这套代码同时服务双马尾与尾巴（同一条路径 ⇒ 不会出现"两条并行的建链代码坐标系不一致"那类坑）。

**判据**：`弧长 / 弦长` 偏离 5% 以上就该用折线。**先量这个比值再决定**，不要凭"看起来是直的"。

## 2. ★★ 节点取 `k/n`，**不是** `k/(n-1)` —— 我把这条改反过一次

* `k/n`（n=5）：节点在弧长 **0 / 20 / 40 / 60 / 80%** ⇒ 末段 20% 的顶点（尾巴的蓬松尾尖，
  占 **80% 的顶点数**）是**绕 80% 处的关节转** ⇒ 会甩 ✓
* `k/(n-1)`：末节点落在**尾尖本身** ⇒ 尾尖的 80% 顶点**绕自己转 = 不动** ⇒ 更糟

我按"末段 20% 没节点"的直觉改成了后者，重建后才发现反了（"看着像修好、其实改反了"）。
**可移植的判据**：`u` 被 clip 到 1.0 的顶点比例高**本身不是问题** ——
要问的是**末节点的位置在不在"末段顶点之前"**。

## 3. ctc 参数：挂件不要套"头发档"，按参考包比例折算

原尾巴套用 `hair` 预设。skill 里记过参考包的取值：发链重力 `(0,−250,0)`、尾巴 `(0,−90,0)`
（比例 **0.36**）⇒ 本工程发链 −112.5 对应尾巴约 **−40**。改成：

| 参数 | hair 档 | **tail 档** | 方向 |
|---|---|---|---|
| `gravity` | (0, −112.5, 0) | **(0, −45, 0)** | 小 ⇒ 不往下坠 |
| `transForce` | 0.620 | **0.720** | 大 ⇒ 跟手/拖尾 |
| `damping` | 0.055 | **0.040** | 小 ⇒ 余摆长 |
| `spring` | 0.010 | 0.015 | 略加弹 |

**★ 观感无法离线验证** ⇒ 三个数做成命令行开关（`tailgrav=` / `tailtrans=` / `taildamp=`），
让用户一句话迭代，比助手猜三轮快。

## 4. 顺带的两个工程细节

* **链骨号按"链名"固定分配**，不要"按部位顺序发号"。否则开关（如"不出衣服尾巴"）改变链条数量时，
  其余链的号会整体漂移，而 `Y4`/`Y4b` 里是硬编码列表 ⇒ 号与链错配、且不报错。
  做法：`CHAIN_FNS = {"MaidTail": [144,145,146,147,148], ...}`，创建时按名字取并断言数量一致。
* **诊断脚本的分档边界**：`u` 会被 clip 到**恰好 1.0**，分档写成 `u < lo+0.25` 会把这一批整批漏掉
  （实测尾巴少报 **549/729** 个顶点，读数看着像"中间节点没权重"）。末档必须 `<=`。

   （"几乎全是 bug"），它的 albedo 用了 **format 30**，而 skill 的普查早已把"albedo 用 30"列为**错误**
   （99.2% 的 albedo 是 31；且"albedo=30"的去重样本里 **15/20 张正是我们自己那个包**，见 §2.6 / §8.2）。
   ⇒ **组合 = 它的预乘 + 我们的 format 31**。
3. 定案后**把"逐字节相同"当验收**：`我们的 .tex` 与 `参照 .tex` 整条 mip 链一致、只差一个格式字节
   —— 这种验收比任何"看起来对不对"都硬。

## B. ★★ 图案画在 **alpha 通道**里的贴图（渔网 / 蕾丝 / 镂空）：四种处置与各自的失败模式

素材：`Stockings.png` 是 **RGB 全白（std = 0.0）、图案 100% 在 alpha 里**
（`alpha==0` 占 62.60% = 菱形网眼；alpha 1→255 是抗锯齿的网线；另有右侧一条实心带）。

| 处置 | 结果 |
|---|---|
| `Y2` 的通用规则"**填满 alpha==0 + alpha 拉平到 255**"（为治脸上的斑驳暗影而设） | **渔网被抹成一个白筒** ← 实机第一轮 |
| **保留 alpha**（想让网眼真透） | 实机是**一片彩色抖动杂色**（`0<a<250` 的抗锯齿边被逐像素裁切，露出底下带颜色细节的身体贴图；mip 链上"直通 alpha"还会让 RGB 与 alpha 不同步） |
| `lerp(皮肤色, 网线色, 原始 alpha)` | 网线被**低值软边稀释成浅灰** ⇒ 腿"整体变白" |
| **★ 预乘 `RGB' = RGB源 × (alpha/255)`，然后 alpha 全置 255** | **正解**（= 作者原意 = 参照工程的做法） |

**三条可移植的规矩**：
1. **换素材先量一句"`alpha==0` 占比 + RGB 是不是常量"**：RGB 是常量（std 0）就说明**图案在 alpha 里**，
   绝不能走"填洞"那条路。
2. **再看 alpha 直方图**：本图 `alpha>=1` 占 **37.40%**、但 `>=250` 只 **5.13%**（从 1 平滑衰减）
   —— "低值软边占大头"的掩码**直接当 lerp 权重会把线条稀释成浅灰**。要它变实，得先"陡化"
   （`a' = clip((a/255−0.10)/(0.50−0.10),0,1)`），但**预乘路线根本不需要这一步**。
3. **验收 = 解码成品 `.tex` 的 mip0**，不是看文件大小。可复制的解码链：
   ```
   .tex 前 184 字节头 + mip 表 → 取 mip0 载荷
   用 texconv 自产的单级 BC7 DDS 头当模板（dwMipMapCount 改成 1）
   → texconv -f R8G8B8A8_UNORM -m 1 → 读字节 → reshape(H, W, 4)
   （★ 别手搓 DDS 头；字段顺序极易错，用"能跑的同款 DDS 的头"最稳）
   ```

## C. **首次导入"裸 FBX"**：对象名/骨架名/材质名都会被导入器改，一律按"对象引用"与"前后差集"判

素材从来没进过预览工程 ⇒ `X1` 里自己 `bpy.ops.import_scene.fbx()`。**三个坑**：

| 坑 | 实测 |
|---|---|
| **对象名会被重名改写** | 素材里的 `Tail` 在预览工程里已有 `Tail`(身体) 与 `Tail.002`(头发) ⇒ 导入后变成 **`Tail.003`** |
| **骨架对象名是导入器给的** | 叫 **`Armature.007`**（预览里已占用 `.001~.006` 与 `.1`） |
| **材质名会被重名改写** | 素材里的 `Metal` 变成了 **`Metal.001`**（写错名字会静默漏挂材质） |

**做法**：① 导入前后取 `set(bpy.data.objects)` 的**差集**拿到"新导入的那批"；
② 用"去掉尾部 `.NNN`"的**基准名**建索引（只吃纯数字后缀，`NO.1` 不受影响）；
③ 骨架**按对象引用**取，绝不按名字；④ 把 `pre["cloth_arm"]` / `pre["hair_arm"]` 写进采集 JSON，
下游（`Y1`）读它 —— 换素材时一行都不用改。

## D. "逐槽定材质"常常是**伪命题**：同一件的各材质槽**共享同一套 UV** ⇒ 按件归组

素材每件有 2~5 个材质槽，名字是通用的 `NO.1` / `NO.1-1` / `NO.1-2` / `Fur1` / `Metal`
（不是贴图名，也不代表"第几套 UV"）。**判据**：逐槽把 UV 包围盒算出来比 ——

```
Choker  : NO.1   u 0.033~0.107   ；NO.1-1 u 0.055~0.122   ⇒ 区间**互相重叠**
Suit    : NO.1   u 0.037~0.969   ；NO.1-2 u 0.037~0.957   ⇒ 几乎完全重合
```
⇒ 它们只是**同一套 UV 上的不同材质实例** ⇒ **按"件"归组**（与素材作者自己写的上色脚本一致），
用 `NO.*` → 哨兵 `"__PIECE__"`（归到该件的 mainkey），`Fur*` → `FUR`、`Metal*` → `METAL`。

★ **但"按材质拆件"仍然要做**（导出器每网格只写**材质槽 0**），而且**要跳过 0 面槽**
（本素材 `Suit` 的槽 2 就是 0 面；拆件逻辑里"该槽没有面就 continue"天然跳过，不用特判）。

## E. ★★ 部位**空了** ⇒ 导出**直接中止**；用**通用**的"隐形载体"兜底

去掉兔尾后 `wst` 一个网格都没有，导出预检报 **`f_wst040_0010.mod3: 没有网格 (NoMeshesInCollection)`**
并中止整条流水线。正文早写过：**不能发空 mod3，也不能删 mod3（游戏会回落到原版模型）**。

**做法（`Y1` 里加一段通用的空部位兜底，不特判某个部位）**：
```
对每个部位：若集合里没有任何 MESH：
  取 Body_base 的某一小块（按 z 带选，如骨盆 z∈[0.00,0.10]）
  → 绕**该批顶点的质心**缩到 0.9 倍（质心在身体内部 ⇒ 每点往里挪 10% ⇒ 严格在体内）
  → 权重沿用那批身体顶点（只保留**本部位骨架里存在**的骨名）
  → 材质取 MAT_OF[部位] 的第一个键（保证它在本部位的 mrl3 里存在、且贴图已随包发出）
  → 挂本部位骨架 + 进本部位集合
验收：算载体每个顶点到身体表面的**有符号距离**，要求全为负（本版 −2.92 ~ −13.65 mm ✓）
```
★ **每出一个新变体都要跑一次导出预检** —— 这类"某个开关把某部位清空"的错误只在**那个开关组合**下出现。

## F. ★★ 姿态下的穿模判据：**配对法**；"有符号最近距离"会被**最近特征跳变**污染

v4（去手套）要量"屈指时手指会不会顶出袖子"。**两个判据并排看**：

| 判据 | 静止 | 屈指 45°（16 根指骨各弯 45°） |
|---|---|---|
| 到皮肤表面的**有符号最近距离** | 陷入 20（0.36%），最深 −4.9 mm | 陷入 **229**（4.10%），最深 **−15.6 mm** |
| **配对法**（静止时给每个衣物顶点配一个最近的皮肤顶点，之后**一直用这一对**，量配对距离的变化） | Δ 全 0（**零点自检通过**） | 中位 +0.000 / p1 −3.36 / **min −6.80 mm** |

**读法**：静止时袖子间隙中位 **+5.7 mm**，屈指后局部收窄 **6.8 mm** ⇒ 最坏只剩 **1 mm 级**净穿入，
**不是**那个 −15.6 mm（弯曲时"最近点"从这根指跳到邻指/指节，读数是假的）。

**三条可移植的规矩**：
1. **姿态下的穿模一律用配对法**（正文 §"贴身衣物的自适应间隙"里那条）；
   有符号最近距离只在**静止、低曲率**时可当参考。
2. **配对法必须做零点自检**：把 `SP_now/BP_now` 传成静止值，Δ 必须恒为 0 —— 不通过就是代码错。
3. 想改善时**先看权重残差**：本版 `Z32` 把袖子按"最近**面**的重心插值"对齐，中位/p90 的 L1 差已是 **0.000**、
   但 **max 还有 0.289** ⇒ 这 0.29 在 45° 屈曲下就是几毫米。
   ⇒ 若要再收，把口径换成"最近皮肤**顶点**"（配对点与衣物逐位同权重）。

## G. 链条取点的两个"静默出错"（`seg_nodes`）

`seg_nodes` 的取点规则是"该顶点的**链组权重和 > 非链组权重和**"。两处会**静默**给假值：

| 症状 | 根因 | 修法 |
|---|---|---|
| 折线**退化成 0 长度**（弧长 0.0000） | 兔尾的顶点大量是 `{Hip_Root_Tail.001:0.4, Hips:0.6}` —— **主导组是链组、但权重和更小** ⇒ 两个段组都收不到点 | 该链改用 `chain_tip`（根 = 源骨 head、尖 = 几何 p95 的**直线轴**） |
| **往复折线**（节点飘在几何外） | 段组是"散开的小片"（颈饰 11 段 = 上圈 + 下垂两簇）⇒ 最近邻游走排出往复 | 同上；或用 **弧长/弦长 > 2.5** 判 |

**做法**：把判据写进建链代码自动报 ——
```
弧长 < 0.1mm            ⇒ 打 "!! 折线退化成 0 长度（段组收不到点）⇒ 改用 chain_tip"
弧长/弦长 > 2.5         ⇒ 打 "!! 往复折线（节点会飘在几何外）⇒ 改用 chain_tip"
```
★ 与"段组编号不沿链"是**两条不同**的坑：那条要 `order_segs_geo` 按几何排序，这条要换成直线轴。

## H. 交接材料里的"已探明"要复核：本版三条

| 交接材料说 | 实测 |
|---|---|
| 兔耳 `Head_Root_Headband.*` "6 段 = 每耳 3 段" | **右 4 段 / 左 2 段**（按质心 x 符号分完就是 4+2）⇒ 节点数按实际段数取 |

沿线的走 `chain_tip`/`seg_nodes`，绕圈的**必须拆成弧**。
