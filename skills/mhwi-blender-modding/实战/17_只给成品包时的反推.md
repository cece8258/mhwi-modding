# 第十七次实战：只给成品包时的反推工作流（一次外部求助）

> 场景与前面十六次都不同：**没有工程文件、没有工作 blend**，只有 8 个成品 zip（v15~v22）。
> 所以整条链是"**从二进制反推 → 定位根因 → 就地打补丁 → 重新出整包**"，
> 而且中途拿到源模型（`外部求助.fbx`）后，把"猜"换成了"逐顶点对拍"。
> 交付：`外部求助_pl024_0000_v23.zip`（30 条目 / 15.1 MB）+ `诊断与修复说明.md`。

## 0. 交付物与结论一句话

**★ 内裤走动撕裂的根因不是"VRChat 骨架注定会撕"，而是权重转移那一步把源骨架的 `Hips`（骨盆）骨整个丢掉了。**
源 FBX 内裤中缝 = `Hips 1.00`（全网格 Hips 占 76.6%），mod3 里 `MhBone_013` 权重 = **0.000**，
那 909 份骨盆权重被两条大腿接管（腿骨放大 **9 倍**）⇒ 中缝 104 对"同一点"一半挂左腿一半挂右腿 ⇒ 迈步裂开。
修完离线指标：重复顶点对 45° 分离 **2.41 → 0.05 mm**，邻点对 **7.48 → 0.90 mm**，皮肤 6.82 → 1.88 mm。

## A. ★★ 没有工程时的通用工作流（本次最大收获）

| 步 | 做什么 | 本次用到的工具 |
|---|---|---|
| 1 | **先把成品全解析成数据**：mod3（骨表/网格/顶点/权重/面）+ ctc（链/节点/矩阵/骨号/角度上限），落 JSON/npy | `m3b.py`、`ctc2.py` |
| 2 | **拿本机语料对照"我这个写法正不正常"**（这一条常常一步到位） | `scan_ref3.py` / `ref_waist.py` / `ref_ctc.py` |
| 3 | 需要"症状复现"时**自己写 LBS 模拟器**（不必有 Blender）：给骨头一个姿态 → 顶点按权重混合 → 量几何量变化 | `eval_src.py` / `final_eval.py` |
| 4 | 有源模型时：**建精确顶点对应**（三角形数配对 + Umeyama），然后**逐骨做"质量缺口扫描"** | `src_xform.py` / `scan_all.py` |
| 5 | 补丁**只改必须改的字段**，出整包，再做字节级验收 | `v23_build.py` / `verify23.py` |

**关键心态**：没有工程时，"症状 → 判据 → 反推"顺序不能乱；**先造对照（参考语料 / 源模型），再谈修法**。
本次两步对照（71 个参考 mod 的髋带锚定率、源 FBX 的逐顶点权重）各自单独就足以定案。

## B. ★★ 根因判据：三步定位"权重转移丢了盆骨"

1. **量"重复顶点对"**（中缝上静止间距 < 0.05 mm 的重复点 = 视觉上同一点）在迈步姿态下的分离。
   - 用 KD-tree **取 k ≥ 4 并排除自身**：`k=2` 时 `ii[v,1]` 常常就是 v 自己，会把真重合对整批漏掉
     （我第一版因此把撕裂量低估 5 倍：2.41 mm → 误读成"只有几个点动"）。
2. **横向对照语料**：`<模组管理器>\Mods` 里 71 个第三方 `body.mod3`，
   口径 = "髋/裆带（髋关节高度 ±6~12、|x| < 0.4·|大腿 x|）内非腿骨权重占比"：
   **中位 0.843、最小 0.630、71/71 ≥ 0.5**；本次 mod = 0.277（皮肤）/ 0.211（内裤）⇒ **在参考区间之外**。
   （过滤：排除材质名含 hair/cloth/outline/uv\d/vfx 的网格、排除 >4 万顶点的非人物网格、每目录取一份。）
3. **逐骨质量缺口扫描**（有源模型时）：`scan_all.py` 输出把 25 个网格扫一遍，
   结果是**只有两处缺口**：皮肤 `Hips 0.097→0.000`、内裤 `Hips 0.770→0.000`，其余骨相关系数全 **1.0000**。
   ⇒ 根因从"可能是任何一种刷法问题"收敛到"**只错在这一条骨上**"。

## C. ★★ 修法：按源权重回写，而不是"灌锚定函数"

- 用户 v18 试过"给内裤中缝灌 `fn13` 锚定函数" → 实测"完全没用、还更奇怪"（他的锚定函数 Y 项还写反了）。
  **启发式的锚定函数不知道"该给多少"**；源里有答案就该抄答案。
- 映射表（相关系数 1.0000 反推，不要按名字猜）：
  `Hips→fn13 / UpperLeg_L→fn14 / UpperLeg_R→fn18 / Butt_L→fn74 / Butt_R→fn76`。
- 公式：`α = clamp((Hips_src − 0.02)/0.12, 0, 1)`；`新 = 混合((1−α)·原权重, α·源权重)`，取最大的 wc 个后归一化。
  **在 Hips 0.02~0.14 之间淡入**，避免在皮肤上出现台阶。
- ★ **内裤与它底下的皮肤必须一起改**：同一槽的皮肤髋带往往也丢了 Hips；静止时间隙只有 **0.42 mm**，
  只改一边立刻变成"内裤顶穿皮肤"。一起改后实测"内裤→最近皮肤顶点"距离 45° 时中位 0.470 → **0.425 mm（变好）**。
- 槽位不够时（本例内裤 `weightDynamics=3` 只放 3 个影响）：取源的前 3 大影响即可
  （源内裤 538 个顶点用 3 个、仅 14 个用 4 个，第 4 个都很小）。

## D. ★★ ctc 节点矩阵 ≡ 骨段方向（把"物理一动就发散"变成机制）

把 ctc 每个节点矩阵第 0 行与 mod3 骨表里 `head[k+1] − head[k]` 的方向求夹角：

```
body / wst / leg / arm 全部 61 条链、242 个节点：误差 中位 0.0000、max 0.0000
```

⇒ **ctc 里的段方向是从骨位算出来并逐位冻结的；节点矩阵没有平移分量（位置完全来自骨表）。**
所以：

> **改带链的物理骨（fn≥150）的位置 h，必须"骨位 + 该链全部节点矩阵"一起改。** 只改一边 → 求解器里
> "位置说往东、方向说往北"互相较劲 → 发散（正是用户 v20 看到的"裙子飞起来、和头发缠成一团"）。

反向结论同样有用：**只回退不带 ctc 链的纯蒙皮辅助骨是安全的**（本例 `body fn74/76`、链根 `fn150`）。
判据：从 ctc 节点 @72 的 u16 取该槽的物理骨集合，取差集 —— 不在集合里的骨随便改。

**顺带答掉一个插件问题**：`MHWI-PartPhysics` 的判据是"**这根骨有没有 ctc controller**"，不是"是不是 fn≥150"。
本例 body 日志只报 201~238（= `colFlag≠0` 的链），而 ctc 里的骨号集合是 151~246 + 420~442；
差集就是 `colFlag=0` 的链 ⇒ 不在任何链里的辅助骨只能纯蒙皮跟随。

## E. ★ 源 FBX 要**自己解**，别用 Blender 导入器（被自己的工具骗了一轮）

用 `blender -b -P` 导入源 FBX 后读出"源模型权重也没归一化"（Σw 中位 0.101、min 0.000），
差点写成"源骨架本身就这样"。**实际是导入器的问题**，两个坑同时存在：

1. **FBX 7700 的数组属性是 zlib 压缩的**：属性格式是 `ArrayLength u32, Encoding u32, CompressedLength u32` + 数据
   （极易读成"长度/数据长/编码"）。`Encoding==1` ⇒ 后面是 zlib deflate。Blender 4.2 不解压 ⇒ 只读到一小部分权重。
   自己 `zlib.decompress` 之后 **Σw = 1.0000（每个顶点精确）**。
2. **骨骼与网格落在两个坐标系**（armature 矩阵带 0.01 缩放 + 轴换）⇒ 看起来"骨在另一个地方"。

自解要点（`fbxparse.py`）：头 27 字节 + u32 version；**version ≥ 7500 时节点头的三个字段是 u64**；
连接方向 **`Model(骨) → Cluster`**（骨是子、cluster 是父 —— 我第一版写反，`clus2bone` 直接 = 0）；
`PolygonVertexIndex` 最后一个索引是**取反编码**（`~i`）。

**有源模型后最值钱的一步**：按**三角形数**配对源网格 ↔ 目标网格，按第 i 个三角形（无旋转/无翻绕序）
建立精确顶点对应，Umeyama 拟合相似变换并报残差 —— 本例 **残差 4e-5 单位、旋转=单位阵、scale 1.458**。
有了对应才能做 B.3 的逐骨缺口扫描，也才能做 C 的按源回写。

## F. ★ 量测坑（都是本次真踩的）

| 坑 | 现象 | 正解 |
|---|---|---|
| LBS 模拟器忘乘权重 | 分离量与**姿态角无关**（20°/45° 都是 16 mm），两个 99% 同权的点也"裂开" | 写 `acc += w*q`。**读数与自变量无关 ⇒ 先怀疑代码** |
| KD-tree `k=2` 返回自身 | 重复顶点的真配对在 `ii[v,0]` 而非 `ii[v,1]`，真重合对被整批漏掉 | 取 k≥4 并显式排除 `u == v` |
| 只量"平均权重" | 平均下来中缝是 40/39（看着很均衡），看不出问题 | 要量**同一点上两侧权重差**（重复顶点对）与**跨 x=0 的硬阶跃**（|x|=1.5 处已 86% 单侧） |
| 拿参考语料不剔污染 | 我自己的测试包（pl040_0010）在语料里，"最大拉伸 4.98"明显高于其他人 | 先按目录名/`installSource` 剔掉自己导出的包 |
| "和参考做法一样"≠"没问题" | 源作者自己也把腰以下 100% 绑裙链；参考 mod 里也有 10/81 这么做 | 参考统计要说"分布"，别把中位数当"唯一正解" |

## G. 交付纪律（只给成品时更要注意）

- **单变量**：本次只出 v23（只动 body.mod3 权重），`ctc`/`ccl`/`mrl3`/`tex` 一个都不碰
  ⇒ 若 #1 好了，功劳只可能来自这一处。**没有实机验证的猜测（改 damping/colFlag）不打包**，只写进说明当"下一步 A/B"。
- **字节级验收**（`verify23.py`）：文件数一致、长度不变、**改动字节 100% 落在权重(4 B)/骨号(4 B)字段内**、
  全部网格 `Σw = 1023`（10-bit 量化后精确）、骨下标无越界、其它 28 个文件 md5 相同、zip 内 29 文件与工作区逐字节一致。
