## A. ★★ 交接材料里的"坑"也必须实测 —— 本轮第一条被**否证**
提示词把这套的一个形态键列为"必须处理的坑"：
* 提示词说：`腰部褶边` 的形态键 `forceOn` 键值 = 1.0 ⇒ 预览看到的是"打开"后的形状，
  按 basis 建件会**静默丢一个形状**，要求改采求值网格。
* 实测（10 秒只读探针）：键值确实是 1.0，但**该键块与 `Basis` 的逐顶点最大差 = 0.000000 m**、
  `animation_data = None` ⇒ 是**空键**；采 basis 与采求值网格**逐位相同**。
  提示词自己给的"验收 reference"（basis 口径 z +0.385~+0.753）也正是实测值 —— **它自己就证明没有差别**。

⇒ **规矩**：拿到"会静默出错"的警告，先写一个**只读的 10 秒探针**把它变成一个数字，再决定改不改代码。
改动可以保留为防御性写法（本版仍走求值网格），但**结论要写成"实测不存在该风险"**。
★ 反向也要记住：同一条提示词的**另两条坑实测确实成立**（见 B、C），所以不能一概不信 —— 差别只能靠量。
（顺带：`第6套` 的 `E_Usamimi` 兔耳有 **`←→` = 0.717** 的非 0 键值、`D_Tights` 也有几个非 0 键 ——
**非 0 不等于有形状差**，量过再定。）

## B. ★★ 段组的作者编号**不沿链** ⇒ 建链前必须按几何排序
`Y1_构建.py` 里已固化成 `order_segs_geo()`：**从离链根 bone head 最近的段组出发做最近邻游走**。
第5套 实测的错序（照名字序号排 ⇒ **锯齿折线** ⇒ 节点飘在网格外面，**且不报错**）：

| 链 | 作者原序 | 几何实序 |
|---|---|---|
| `arm_tentacle_1_L/R`（3 段） | 根, .001, .002 | 根, **.002, .001** |
| `arm_tentacle_2_L/R`（8 段） | 根, .001 … .007 | 根, **.007, .006 … .001**（整条逆序） |
| `arm_tentacle_3_L/R`（5 段） | 根, .001 … .004 | 根, **.004, .003, .002, .001** |
| `RT_Hair_Twin_L/R`（6 段） | .001, .002, .003, .004, .005, .007 | .001, **.007**, .002, .003, .004, .005 |
| `RT_Hair_Ribbon_L/R`（10 段） | .001 … .010 | .001, **.009, .002, .010, .003, .006, .004, .007, .008, .005**（蝴蝶结是折返的） |

**判据**：排序函数要把"原序 ≠ 实序"的链**打印出来**（第5套 里 5 组链全都打印了，一眼看出不正常）。
**单段组链不要用 `seg_nodes`** —— 折线会退化成"质心正上方 3cm 的短桩"、整片挂到 tip 上＝刚性，走 `chain_tip`。

## D. ★★ 新建链的节点 `colShape` 必须**显式写 257**
`Y4b_物理ctc.py` 的节点模板是"从**该文件的第一条链**抄的"：`body.ctc` 的第一条恰好是 257
（所以双马尾/缎带链正常），而 `wst.ctc` 的第一条是 第1套 的旧裙链、**`colShape=258`**
⇒ 抄出来的 4 条腰部褶边链**整条零反应**（用户实机原话："跑起来一点没动"）。
**判据被独立物证确认**：用户认可过的 第4套 成品（裙摆会动）里 **14 条链全部 257**。
⇒ 建节点时 `struct.pack_into("<H", nd, 70, 257)` **显式覆盖**（节点 112 字节；骨号在 +72、`colShape` 在 +70）。
**验收**：把成品 `.ctc` 解出来打一张"链 → 节点骨号 + colShape"的表，**每一条都必须是 257**。

## E. ★★ 姿态驱动的穿模：判据要看权重差的**尾部**，不要只看中位数
用户反馈"站立时 `紧身衣` 稳定穿模、小腹露出"（以及"`足リング` 内侧陷进大腿"）。
我第一轮判成"源包是别的角色的身体"（**错**——该角色 与 该角色 是**同一作者、身体一模一样**、
Blender 里也不穿模）；第二轮改用**最近顶点**量权重差、得到"中位 0.029 ⇒ 几乎一致"（**也错**）。
换成**最近面的重心插值**后：`紧身衣` 的 L1 差 **p90 0.870 / max 1.589**、`足リング` **中位 0.849 / p90 1.121**
⇒ 不是"几乎一致"，是**差一整根骨**。用户点明的机理也对：**MHW 的站姿会自然挺胯、双腿岔开**
⇒ 腿骨一转，胯部皮肤与衣物**相对错动可达 1 cm 量级**，1~2 mm 的几何余量根本挡不住。

**两条修法（按件类型分工）**：
1. **软的贴身件 ⇒ 权重转移**（新增 `Z32_衣物权重对齐身体.py`）：BVH 最近面 + 重心坐标，
   把**皮肤权重抄给衣物** ⇒ 逐顶点同一套权重 ⇒ **任何姿态下都不会相对错动**。
   实测 `紧身衣`/`足リング`/`アンダーブラ`/`チョーカー`/`ゴムクラゲ`/`首`/`胸贴`/`足アクセ`
   的 L1 差**全部 → 0.000**（最大残差 0.016）。
   **★ 描边壳**要按"最近源顶点"抄源件**转移后**的权重（否则壳与本体以不同权重形变、黑边会错位）。
   **★ 顺序**：必须在所有改身体权重的步骤之后 —— `Y11 → Z26 → Z27 → Z31 → Z33 → Z28 → Z32`。
2. **硬的环/带类 ⇒ 查"面片弦切"**：`足リング` 的权重与皮肤完全一致（L1 0.000），
   但**面片中段切进肉里** —— 504 顶点的粗环绕大腿一圈、**弦高 1~3 mm**，
   三个顶点都在皮肤外、面片却穿进去。⇒ 穿模判据必须把**面心（或边中点）**也算进去：
   `need = max(target − d_面心)` 再分给该面的三个顶点；这类粗环的目标间隙提到 **+1.5mm**。

## F. ★★ 身体侧的"提胯拉扯 / 裆底敞开"：分界高度是**曲线** + 平滑带
用户反馈：待机"左右切换重心、提胯"时另一条腿的**大腿上部被明显拉扯**；直立时**裆底最下面被拉向两侧敞开**；
且"**上一个模组就有、本模组完全一致**"⇒ 从基壳继承的**身体侧**问题（不是衣物/素材）。

实测（纯 python 跑预览 JSON 即可，不需要渲染）：
* 先排除"被两条腿同时拉"：全网格 `Upper_leg.L` 与 `Upper_leg.R` 同时 >0.2 的顶点 **= 0** ⇒ 左右分派干净。
* **大腿上部**：同一条腿、同一 2cm 高度环内 `Hips` 的 **sd = 0.354、极差 0.96**（z≈0.69）⇒ 圈内错开 = 撕扯。
* **裆底**：中线有一条 **2mm 的硬边界**（`z=0.639` 处 `Hips=0.46`、`z=0.641` 处 **`Hips=1.00`**）。

修法（新增 `Z33_修胯与裆部权重.py`）：取 `pool = Hips + Upper_leg.L + Upper_leg.R`，
按 `t = smoothstep((z − (zc(|x|) − HW)) / (2·HW))` 重分配（`Hips = pool·t`、腿 = `pool·(1−t)`，腿内按原比例）。
**其余骨骼（`Butt.L/R` 臀部抖动、`Lower_leg`、`Spine`）一个都不动**；pool 守恒 ⇒ 总权重不变
⇒ 对"腿权重本来就小"的顶点是**恒等变换**（第5套 只改 889~1567 / 16517 个顶点）。

**★★ 分界高度 `zc` 是随 |x| 变化的曲线，不能按高度一刀切。** 骨盆下缘本身就是曲线 ——
**中线最低（裆底 ≈0.655）、两侧最高（髋 ≈0.705）**。照"只随高度"平铺会把**本该跟骨盆的会阴**拉到腿上
（我第一版就犯了这个，改动顶点 1507 反而更糟）。参数：`ZC_MID=0.655 / ZC_SIDE=0.705 / ZC_W=0.05 / HW=0.035`。

**验收**（都能纯 python 从预览 JSON 算）：
① 同一侧 + 同一高度环内的权重 **sd**（圆柱部位本就该只随高度变化）；
② 沿 z 扫描找**硬跳**（相邻 1~2mm 的圈之间权重突变）。
读数：带内 sd 中位 **0.151 → 0.065**；两侧 **0.354 → 0.127**；裆底剖面从 2mm 硬跳 → **70mm 平滑上升**；
`body.mod3` 尺寸**不变**（影响数没变 ⇒ 没引入新风险）。

## G. ★★ 光照异常先做 **CB 44 字段对拍**，别猜系数
用户反馈"阴凉 / 阳光未直射时亮度正常，但**阳光直射时变成一团白光**"。
把我们的材质与**用户满意的基壳材质**（body `__1` 身体）**逐字段对拍 CB 的 44 个字段**：
**只有两个字段不同** —— `fBaseMapFactor` 0.30 vs 0.40、`fEmissiveMapFactor` 2.35 vs 2.00；
其余 42 个（含 `fSpecular`、`fEmissiveBlendColor`=0 且 blend=0、`fAddColor*` alpha=0、雪参数）**全同**。
**选旋钮的判据 = "这个字段只影响被光照到的那部分吗"**：
* `fBaseMapFactor` / `fSpecular` ⇒ 只在被直射时起作用 ⇒ "只有直射过曝"就该动这两个
  （`Base 0.30→0.10`、`Spec 1.0→0.30`；自发光占比 88.7%→96%，**阴凉处差 <1%**）
* `fEmissiveMapFactor` ⇒ 阴凉处也在起作用 ⇒ 动它会把"本来正常的亮度"一起改掉（留作下一档）

## I. 源贴图的权威路径 = **预览工程里 image datablock 的 `filepath`**
多配色源包里常有**同名不同内容**的两份（`resolved/` vs `tex/`），靠名字猜会拿错。
做法：写一个 10 秒只读探针打印每个源材质的 `node → TEX_IMAGE → image.filepath + size + 是否存在`。
第5套 实测：素材 用的是 `cloth8\**resolved**\`（**不是**同名的 `tex\`），头发用 某头发素材 的 **Cream** 配色。
★ 换配色 = 只改 `Y2` 的 `SRC` 里那个源 PNG 名并重跑（贴图差分：材质名与几何都不动）。

## J. ★ 同一个材质名在不同部位可以指向不同贴图
第5套 四个部位共用一套名字 `__5~__12`，但 **`__6` 在 body/arm/wst = 布半透明、在 `leg` = 宝石**；
`__7` 同理（クラゲ vs メタル）。⇒ **量亮度、改指向、写 `PLAN` 时都必须带部位过滤**
（`X8` 的 `JOBS` 已按部位分组），否则掩码会把两套不相干的 UV 并起来、读数无意义。

## K. 顺带的三条
* **贴图差分做颜色对齐**：用户要"统一头发与耳朵的颜色"⇒ 按耳/尾**自己的 UV** 采样 该角色 的 `Hair.png`
  得中位 RGB (228,197,176)；12 套 某头发素材 配色按**头发自己的 UV** 采样后算距离
  ⇒ **Gold 12.0 最近**（Cream 37.5）⇒ 用户的判断被实测确认。
  **换完要"从 zip 里独立解码"复核**（拼合法 DDS → texconv → 读像素：与 Gold 差 0.18、与 Cream 差 15.0）。
* **`X1` 继承来的有符号距离符号是反的**（写成 `sgn = −dot(q−loc, nrm)` 却把读数标成"陷入"）——
  第5套 已改正为 `+dot`（正 = 在外）。**两处读数对不上时先怀疑符号**。
* **"要不要保留原版耳朵/尾巴"逐版不同**：第1套~4 删、**第5套 保留**（用户要求）、**第6套 又要删**
