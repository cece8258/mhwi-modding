## A. ★★★ 换素材第一件事：**逐条骨链**打"head 距离 + 骨方向夹角"表（只看 Hips 会被骗死）

本工程素材工程里有个"看起来完全正常"的骨架：`OPAL_Armature` 205 骨，`Hips` 与 该角色 **逐位相同
（0.0000 m）**，顶点组里还带着 该角色 真身骨 `Wrist_support.*`/`Elbow_support.*` ⇒ **Hips 对齐这一条
± `X1` 的自动对拍都判它"同源、不用配准"**。实测**只比 Hips 是不够的**：

| 骨 | head 距离 | **骨方向夹角** |
|---|---|---|
| Hips / Spine / Chest / Neck / Head / Shoulder.L / 整条腿 | **0.0000 m** | **0.0°** |
| `Upper_arm.L` | 0.0000（**肩关节重合**） | **45.0°** |
| `Lower_arm.L` | **0.1515 m** | 45.0° |
| `Hand.L` | **0.2870 m** | 45.0° |

⇒ **素材的衣服是按"手臂 45° 下垂"（A-pose）做的，而 该角色 的身体/骨架是 T-pose** ——
躯干/头/肩/腿逐位相同，**只有手臂链整体差 45°**。后果**只出现在绑到那条链的件上**：
袖子、披肩在游戏里**多转 45°**（甩到手臂后面/离开肩膀），而裙（绑骨盆）、上衣/束带（绑躯干）、
头发（绑头）**全对** —— **这个"错件的分布"本身就是最强的定位线索**。

**三条便宜判据（不用配对参照就能下手）**：

1. **`Body_base` 里"主导组 = Hand.L"的顶点质心 z**：本例 **1.0015**（= 与肩同高）⇒ 手臂水平 = **T-pose**；
   A-pose 会落在大约 z≈0.7。
2. **MHWI 骨架的指纹**：`MhBone_006/007/008`（上臂/前臂/手）的 head **全在同一个 z、只沿 x 排开**
   ⇒ 游戏骨架就是 T-pose。
3. **件到"水平手臂轴"的半径**（轴 = `Shoulder.L.head → Hand.L.head`）：`套装件. Top 3` **中位 17.8 cm
   / p90 31.7 cm** ⇒ 它**不可能**是包在水平手臂上的袖子，而是挂在"下垂手臂"位置上的垂布。

**"整条链 = 绕肩一个刚体旋转"的验证**：取该侧 `Upper_arm` 的 A-pose 方向与 T-pose 方向求最小旋转
（本例 **44.973°**，左右各一个），用它把 A-pose 的链上各骨 head 搬过去 ⇒ **40 根差异骨的残差全部 <3 mm**
⇒ 可以放心用"一个旋转 + 按权重混合"来转换（见 B）。

**教训**：**Hips 相同 ≠ 骨架姿态相同**。对拍脚本要**同时打 head 距离与方向夹角、并按链分组看**
（本工程的自动对拍只报了"head 距离 max 0.3659，全在手指远节"，把手臂这条链的 45° 夹角藏了过去）。

## B. ★★★ A-pose 素材 × T-pose 骨架：转换要"整链搬"，**按逐点权重做会把网格撕开**

把 A-pose 的件搬到 T-pose 骨架，教科书做法是按权重做 bind-pose 转换：
`v' = v + t·(R(v−p)+p−v)`（`t` = 该顶点在"手臂链组"上的权重和；`R` 绕肩、`p` = 肩关节）。
**`t` 怎么取，决定成败**：

* ★★ 作者的权重常常是**近似二值**的（本例披肩：`t=0` 的顶点 **31%**、`t=1` 的 **28%**，中间只有 ~40% 过渡）
  ⇒ 在权重突变的那条边上，两个端点的位移差 = `Δt · |R(w)−w|`，**一条 2 mm 的边被拉到 35 mm（20.6 倍）**，
  两端 t=0.38 / 0.70 ⇒ 游戏里就是"**静止时从后背穿出一条白条、随手臂甩、跑动更长、一直伸到手肘**"。
* 我先试了"沿网格 Laplacian 平滑 `t` 场"（α=0.5、**40 轮**）：最大拉伸 **20.6 → 6.7 倍** ⇒ **不够**。
  原因：这类件**本来就不该被剪切**（它是刚性挂在肩/手臂交界处的），平滑只是把"撕开"变成"慢慢扭"。

**正确做法（`Y1` 的 `NO_ARM_FOLLOW`）：不转换 + 把该链权重并入同侧父骨**

```
对"挂在肩/背/腰上、又有一截盖住手臂"的件：
  把它的**手臂链权重整体并入同侧 `Shoulder.L`(5) / `Shoulder.R`(9)**（权重总量不变、只改归属）
  ⇒ 几何**不做姿态转换**（t 自然为 0）⇒ 既撕不开、也不再被手臂甩
```
复量：`套装件. Top 2` 的 `MhBone_006/010`(**Upper_arm**) **归零**（顶点组 10 → 8），
改由 `Chest 31.3% + Shoulder.L/R 41.8% + Breast 25.8%` 驱动 ✓。

**★★ 这已经是同一条教训第三次踩**（第六次实战 C「外挂件必须限定骨集合为躯干/肩/颈、排除手臂/前臂/手与腿」
→ 本轮的 `Z32 TARGETS`（见 D）→ 本节）⇒ 固化一条**规律**：
**凡是"挂在肩/背/腰上、又有一截盖住手臂"的件，都不要让手臂骨参与**；
真需要跟手臂的（比如合体的袖子）才用姿态转换，且要先量它的权重场是不是二值。

**判据**：转换前后**最大单边拉伸倍数** `max(|L₁−L₀|/L₀)`，**<1.2 才算没撕**。
本例平滑后各件：Top 1 **1.02** / Harness 1 1.11 / Harness 2 1.00 ✓；袖（Top 3）7.09→**1.83** ✗
—— 用户当时说"**袖子的上半段好像绑歪了**"，根因就是这同一个撕裂（所以那条"绑歪"不是权重错，是转换撕的）。

## D. ★★ `Z32`（衣物权重对齐身体）的"最近体表"**只对贴着身体的件成立**

`Z32` 是按"**最近的体表点**"给衣物转移权重的。悬垂件的几何最近点**不是它的挂点**：

| 件 | 实测结果 | 后果 |
|---|---|---|
| `OPAL_3. Wings` | **79.1% 的权重落到 `MhBone_006/010`(Upper_arm)** | 翅膀被两条**手臂**拽着走 |
| `套装件. Top 3`（袖） | 下摆那截拿到 `MhBone_013`(**Hips**) **15.7%**（2503 个主导点、横跨 x ±0.487） | 袖口钉在骨盆上、上段跟手臂 ⇒ 抬手把袖子从胯扯到手臂 |

原因：**手臂自然下垂时，袖子末端正好落在骨盆高度、翅膀外缘正好贴着上臂**（而在 T-pose 的骨架里
手臂是水平的 ⇒ 几何与骨的关系更错位）。

**修法**：把**悬垂件（袖 / 披肩 / 翅膀 / 飘带 / 尾巴）从 `Z32` 的 `TARGETS` 里去掉**，
保留作者的分组（`Y1` 按名字映射的那一版）；只留**贴着身体**的（束带 / 紧身衣 / 袜 / 腿环 / 帽子）。
★ 与第六次实战 C「限定骨集合」是同一条，只是更省事：**整件不列**。
★ 诊断手法（很好用）：**逐件量"每个骨号的 Σw + 主导顶点数 + 空间跨度"** ——
`Wings` 那一行 `Upper_arm 39.9%/39.2%、主导 7739/7604 点` 一眼就看出来不对劲。

## E. ★★ `follow` / `t0` 的实质：**斜坡 × 链条权重在高度上的分布**

`Y1` 里的跟腿是这样算的：
```
tt = (z_top − z) / (z_top − z_bot)              # 0 在顶端、1 在底端
sv = 0 if tt ≤ t0 else min(follow, follow·(tt−t0)/(1−t0))
把 sv 那部分权重从链骨让给 Upper_leg.L/R（按 x 分左右）
```
⇒ 它是**按高度从 `t0` 线性升到 `follow`** 的斜坡。**同样的 `follow/t0`，效果完全取决于
"链条权重在高度上的分布"**：

| | 链骨 | **腿骨** | 骨盆 | 说明 |
|---|---|---|---|---|
| `第9套` 的裙 | 0.447 | **0.250** | 0.303 | 链条权重**集中在摆边** ⇒ `t0=0.45` 就吃满（0.447×0.55 ≈ 0.25 ✓ 算式吻合） |
| `第11套` 的裙（改前） | 0.826 | **0.104** | 0.070 | 链条权重**铺满整条裙** ⇒ 上部吃不到斜坡 |
| `第11套` 的裙（改后） | 0.687 | **0.243** ✓ | 0.070 | **`t0` 0.45 → 0.10**（`follow` 保持用户验收过的 0.55 不动） |

**诊断**：逐件量"Σw 里 链骨 / 腿骨 / 骨盆 的占比" + "**下半 30% 的腿骨占比**"。
**验收口径**：**腿骨占比对齐参照工程**（本例 0.243 vs 0.250 ✓），不要用"腿皮露出率"（见 F.2）。

**★ 参照工程怎么造**（用户明确要求"优先参考之前做过的模组"）：**把参照工程的 `Y1` 重跑一份工作 blend**

然后在**同一套判据脚本**下与自己的工作 blend 比 —— 比"翻别人/自己旧的成品 mod3 反解权重"省事一个量级。

## F. ★★ 判据纪律：本轮三个"指标无效"的实例（共同点是"先看基线与对照"）

1. **"顶点到最近骨的距离"判"绑错位"** ⇒ **所有件都报 80~100%**（衣物的骨本就在身体内部、
   裙摆在半径 20~30 cm 外）⇒ **指标无效**，不能用它下任何结论（同类：第十一次的"镜像均值"）。
2. **"腿皮露出率"（射线法）判 `follow` 改动** ⇒ 改前 **40.53%** / 改后 **40.53%**
   （参照工程是 31.76%）⇒ **分辨不出**：读数被"**设计上本来就露**"的部分（裙腰开口、腿内侧、小腿）主导。
   ⇒ 只能**如实报"这次没用它下结论"**，改用 E 的"腿骨占比"。★ 顺便：参照工程与自己的**静止基线**
   差 8.7 个百分点（40.5 vs 31.8）是**结构差**（裙子形状/覆盖），不是跟腿差。
3. **"有符号距离"判件与身体的关系** ⇒ `Headband 97.86% / Ribbon 71.06% / Top 2 8.85%`（最深 −22.7 mm）
   全是**假信号**。Top 2 那 524 个"深点"**全部落在 z 0.987~1.014**（斜方肌/颈根那一段），
   `P − 最近体表点` 的 Δz 均值 **+4.2 mm**、而最近体表的法线 z 分量 **−0.363（朝下）**
   ⇒ 它们是**悬在斜方肌上方**、被朝下的体表法线误判成"陷入" ⇒ **不做穿模外推**
   （判据 = 看"`P−loc` 的方向与 `loc` 的法线方向有没有物理意义"）。

**共同教训**：`测不出已知现象时，结论只能是"未知"`；**先看对照与基线**，再谈"改进/恶化"。

## G. ★ 探索工具的三个小坑

* **生成器只能消费一次**：探针里写 `legg = ("MhBone_%03d" % f for f in (14,15,...))` 然后 `b in legg`
  ⇒ **恒为 False**（第一次 `in` 就把生成器耗尽了）⇒ 候选选到 **0 个**，白跑一轮。（写成集合 `{...}`）
* **mod3 的链头与节点是分区存放的**：`80` 起是 `chainCount × 80` 的**链头区**，之后才是**节点区**
  （按链序、每个 112 字节）；按"每条链头后跟它的节点"读会 `struct.error`。
  自检：`80 + chainCount×80 + Σ(nodeCount)×112 == 文件长度`。
* **"把顶点压回体内"必须迭代**：压回去之后**最近面会跳**（同第十二次 F），
  单次只把 +29.6 mm 压到 +8.1 mm，迭代 8 轮才到 −3 mm。

## I. 本轮的"取舍不是 bug"清单（交付说明要写清，别让用户当成 bug）

* **半透明件按不透明渲染**：`3._ Transparent` 是真半透明源图（`alpha<0.5` 占 23.9%），
  而 MHW 的 `PL_Mt` **没有混合模式** ⇒ 摆边/翅膀/飘带会比原设计"实"（同 `第4套` 的 `_trans` 蕾丝）。
* **白件大面积满亮**：白布料 UV 覆盖区亮度 0.926，乘 `EmiF 2.25` 后大面积过曝（浅花纹会被压平）——
  亮布料 + 伪发光的必然（与 `第9套` 同一档）。
* **黑裙是"深炭黑"（≈ sRGB 66）不是纯黑** = 伪发光配方下 `(Base+EmiF) × 黑贴图` 的结果，
  与 `第9套` 的 `blkscale=0.30` 同档。

## J. 两个"方向相反"的路径坑（本轮白跑两轮）

* **`robocopy` 在 Git Bash 里必须 `MSYS_NO_PATHCONV=1`** —— 否则 `/E` 被 MSYS 吃成 `E:/`，
  robocopy 报"无效参数 #3"而**一个文件都不拷**（而且 `| tail` 会把退出码盖成 0，看着像成功）。
* **`Z9_出一版.sh` 反过来绝不能带** `MSYS_NO_PATHCONV` —— 它里面的 `P="/d/blender project/…"`
  是**靠 MSYS 转换**才能被 Windows 版 Blender 解析的；禁了就会
  `FileNotFoundError: '/d/blender project/…/_X3_preview.json'`。
* 同一台机器、同一条流水线，**两个方向相反的坑** ⇒ 记住结论：**给 Shell 脚本用正斜杠路径时不要禁转换；
  给 Windows 原生程序传参数时（尤其带 `/X` 开关）要禁转换**。
