## A. ★★★ 「跟腿」= **按 x 分侧**给腿骨权重 ⇒ 横跨 x≈0 的布片必被两条腿各拽一半

**症状**（用户原话）："你现在旗袍物理使用的应该是跟腿，这不行，**跑步的时候旗袍左右两半直接交错拉伸了**。"

**机理（一算就清楚）**：`Y1` 的 `FOLLOW` 把让出的权重按
`uu = clip(x / 0.12, -1, 1)` 分给 `Upper_leg.L/R`：`wl = sv*(0.5+0.5*uu)`、`wr = sv*(0.5-0.5*uu)`。
旗袍的**一片前后片横跨 x≈0**（实测方位 θ **−40°~+30°**）⇒ 中缝处 `uu≈0` ⇒ **一半给左腿、一半给右腿**
⇒ 迈腿时**同一片布被两条腿各拽一半** = 用户看到的"左右两半交错拉伸"。

**★ 有两条来源，两条都要断（只断一条没用）**：

| 来源 | 它怎么把腿骨权重贴上去的 | 断法 |
|---|---|---|
| `Y1` 的 `FOLLOW` | 显式按 x 分侧给 `Upper_leg.L/R` | `FOLLOW = 0`（默认关） |
| `Z32`（贴身衣物对齐皮肤） | 旗袍下摆**最近的皮肤就是大腿** ⇒ 非链骨那部分换成大腿权重 | 把 `Cloth` **移出 `TARGETS`** |

**判据（可复算）**：`_probe_腿骨占比.py` —— 在**带链骨权重**的顶点上算 `Upper_leg.L/R` 占总权重的比例。
修前 **0.1392**（`p50 0.138 / p90 0.312`），修后 **0.0000**（3855 个顶点全 0）。
★ 参照：`第9套` 某套装 = 0.250（用户验收过那档）—— 但**目标不是凑 0.25**，而是"这片布不该被腿分尸"。

**替代方案（= 用户要的"头发式"）**：**纯链驱动 + 顶端 `Hips`**。作者原本的列组权重走链
（链根骨挂在 `MhBone_013`）⇒ 顶端"跟胯"、下半段"当头发处理" ✓ 而且**一点腿骨权重都没有**，
从原理上不可能再左右交叉。

## B. ★★★ 一件衣服用**多条独立链** ⇒ 相位漂移 ⇒ 拉扯、甚至左右交叉 ⇒ **一片布一条链**

**症状**：① 第一轮"左右两半交错拉伸"（当时归因于 A，但 A 修掉后）② 用户第二轮：
"**下摆还是能够明显地看出是左右两半，不像一个整体** …… 前进时左右摆动 ⇒ **向左向右剧烈拉伸**，
有时候**左边向右、右边向左就会交叠**"。

**根因**：一、二轮是"前后各 3 条 = 6 条链"（左列 / 中线 / 右列）。这 6 条链是**互相独立**的竖条，
走路时各自的相位/振幅不同 ⇒ 相邻列之间被拉扯（"不像一个整体"），相位差大到一定程度就**交叉**。

**修法（一句话）**：**一片布用一条链**。前片 1 条、后片 1 条（各 **5 节点**），
把该片**全部 18 个列组**塞进这条链的 `segs`，u 只由**高度**定（`anchor="Hips"` 直线轴的投影）⇒
**同一高度的左右两侧必然同步** ✓。

**★ 关键认知：链数 ≠ 覆盖度。** 第一轮曾以为"只做两条中线"就只剩 30% 覆盖 —— 那是因为
**两侧列没被分给任何链**（走 `AUX → Hips` 变刚性）。把列组**全塞进**同一片的那条链，
**2 条链照样覆盖 97%**。

**复核判据（`Y8c`，比"root 占比单调"更有用的一栏）**：

| | 每条链的**链权重和** 中位 | 带权顶点 |
|---|---|---|
| 6 条链（每列一条） | 0.32 ~ 0.59 | 714 / 1244 / … |
| **2 条链（每片一条）** | **1.000** | **1820 / 2035** |

⇒ **链权重和 = 1.000 才是"这片布完全由模拟驱动"**；0.3~0.6 说明一半以上还在跟躯干骨走。

## C. ★★ `hair` 档（damp 0.055 / trans 0.620）是**尾巴/头发**的参数 —— 长裙用它会**余摆**

用户第一轮说"前后的布料都应该使用**类似头发**的物理" ⇒ 我把旗袍链换成了 `hair` 档。
第二轮实机："下摆在人物前进时**左右摆动**（剧烈）"。
`hair` 档 `damping 0.055 / transForce 0.620`（尾巴/头发要"余摆长、拖尾多"）⇒ 侧向摆动衰减不掉；
`skirt` 档 `0.120 / 0.350` 才是给长裙调过的（`第4套` 起沿用）⇒ 换回长裙档。

★ **"不跟腿"是权重层面的事，与物理档无关** —— 换档不会把腿放回来（腿骨占比仍 0.0000）。
★ 顺序建议：**先把权重改对（A/B），再用物理档调"观感"（C）**，否则两个变量混在一起难归因。

## D. ★★ 「相交对」≠「看得见穿模」—— 拿它当"要不要抬高"的判据会翻车

第一轮实测 `Hat` × 某头发素材 头发 **Δ=0 时 925 对三角面相交**（`BVHTree.overlap`），据此抬 **+20mm**。
用户第二轮："**帽子是浮空的**" ✗ —— 那 925 对**全在帽子的内壳里**（从外面根本看不见），
抬起来只在头上留了一道缝。第二轮改回 0（作者原高度）⇒ 第三轮用户仍说"还是偏高，可以**往下 5mm**"
⇒ 第三轮 **−5mm**（`HAT_SHIFT = -0.005`，负值 = 往下）。

**教训**：**"几何相交"与"视觉上看得见穿模"是两件事**。判据要用"**可见外壳**上的相交"或干脆**实机判**
（游戏里的头/发型与素材工程的预览并不完全一致）。同族坑：`顶点在体积内` 也别用（68% 的头发顶点都在帽子体积里）。

## E. ★★ 用户手改的 blend：**先量再信**，也别直接当数据源

用户要求"用我改过的 `第12套/1/第12套素材工程.blend`"。**量下来两条**：

1. 他的改动 = **某头发素材 整体沿 +Y（往后）纯平移 `0.0195949 m`**（顶点数、局部 bbox 与旧版逐位一致）
   ⇒ `Bang→脸` 最近距离 **0.0290 → 0.0119 m**（`p10 0.0082`）。**纯平移 ⇒ 可以提取成常量**。
2. ★ 但**同一个文件里 `某旗袍套装` 的 13 件父级变换全坏了**：`mwScale` 从 `0.01` 变成 `1.0`、
   世界坐标 ≈ **×100** 且轴序被换（`Cloth` 的 z `0.148~1.073` → `−10.05~+11.39`），
   而且 `第12套/1/` 里**没有 `Texture/`**（贴图路径全断）。
   ⇒ **它不能当 MH 的数据源**（某头发素材 那 6 件是好的）。

**做法**：数据仍取自完好的原版素材工程，把"发际修正"作为**常量** `KA_DY` 施加在 `X1` 采集端
（并给 `X1` 加了 **⑦b 发际贴合度**：`Bang/Hairline/Aho → 脸` 的最近距离分位 ⇒ 以后每轮都能自证）。
**量测脚本**：`_probe_两版素材对比.py`（世界 bbox + 刘海距离）、`_probe_父级与矩阵.py`（父级/matrix 逐件对拍）。
★ **已固化进 skill**：`scripts/探针_素材对拍与小件贴合.py`（对拍 = 逐件父级/matrix/bbox；贴合 = 小件到宿主的最近距离 + 扫位移），本工程里的同源版本是 `_probe_两版素材对比.py` / `_probe_父级与矩阵.py` / `_probe_符咒贴合.py`。

★ 顺带一条纪律：**用户说"用这个文件"时，先跑这两个探针对拍**，比事后返工便宜得多。

## F. ★★ 挪一个**主体**时，**贴在它上面的小件**必须一起挪

用户第三轮："**头发上贴的符咒(`ACC_Paper`)浮空了**"。
`ACC_Paper`（78 顶点）是**贴在头发上的符咒**；上一轮只把头发后移 19.6 mm、**没挪它** ⇒ 它留在原地。

实测（`_probe_符咒贴合.py`，沿 Y 双向扫位移）：

| 状态 | 符咒↔某头发素材 头发 最近距离（中位） |
|---|---|
| 素材帧（作者摆放） | **2.44 mm** ✓ 贴着的 |
| 只挪头发的 in-game 状态 | **19.70 mm** ✗ = 用户看到的浮空量 |
| 沿 Y 扫 −20…+30 mm | **最小就在 Δy = 0**（往前往后都更远） |

⇒ 答案不是"往哪边挪"，而是**跟着头发一起挪**（`X1` 的 `KA_RIDE`）。成品几何复量 **3.37 mm**
（= 2.44 × 1.379583 换算）✓。
**通用判据**：小件是否贴住主体 = **"到该件表面的最近距离"**；挪主体前先记下这个数，挪完复量。

`某旗袍套装` 的 `A_Black&Blue` 配色，**21 个 `.mat` 逐个 grep `_BaseColor` ⇒ 全部 = 白 (1,1,1)**。
⇒ 本版**不烘 tint**（贴图原样），只有两个例外：两个 **matcap**（`Mat_*Pearl`，`_BaseColor=(0,0,0)` + 无 albedo
⇒ 平涂银灰）与一个**纯色**（`Mat_AccVillus = (0.6698,0,0)` 暗红，用户定"照原样"）。
⇒ **5 个材质键**（MH_CLOTH / MH_ACC / MH_PEARL / MH_VILLUS / HAIR）。

**烘焙按 alpha 结构分派**（同一套工程里三种口径，判据 = "该 alpha 区间的 RGB 有没有内容"）：

## H. ★ `tFurMap` 是**活引用** —— 它能挂住几十 MB 的死贴图

## I. ★ 流程 / 工具（这一轮踩到的）

1. ★ **陈旧报告陷阱**：`robocopy` 把 `第9套` 的 **35 个旧报告**一起拷来、**文件名与本版同名**
   ⇒ 差点把旧 某套装 读数当新结果（`_Y8c_链骨权重.txt`）。⇒ 拷完立刻把旧报告挪进 `_旧报告/`（或删），
   **读任何报告前先看 mtime / 内容里的版本名**。
2. ★ **补丁脚本一律"先 `ast.parse` 再落盘"**：本轮靠它拦住两处会把脚本写坏的补丁
   （嵌套双引号；三重嵌套少一个右括号）。
3. ★ **报告行引用的变量必须在它之前定义**：`QP_PRESET` 定义在链规格区（第 510 行）、
   而 `[开关]` 报告行在 459 行 ⇒ `NameError`、Y1 早退、整轮白跑（`grep -q SAVED` 哨兵抓住了）。
4. ★ **Bash 命令串会被解一层转义**（`\\` → `\`），而 **`Write`/`Edit` 是逐字写入** ⇒
   写"要落到文件里的反斜杠"时多写一倍，或干脆用正斜杠 / `chr(92)` 绕开。
5. ★ **`bash script.sh | tail` 的退出码是 `tail` 的** ⇒ 管道会把脚本的失败**吞掉**
   （本轮有一次 bash 语法错误发生在最后一步，`exit 0` 让"完成"看起来还在跑）。
   判完成要看脚本自己的 `=== [版本] 完成 ===` 行。
6. ★ 删件（鞋/袖/袜）后 `arm`/`leg` 都空 ⇒ **3 顶点占位件**（第13次 C）第二次实战验证 ✓
   （离体表 −39.5~−54.2 mm，实机未见露出）。
