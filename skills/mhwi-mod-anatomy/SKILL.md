### 2.2 mip 偏移表与长度自检（含 65 张分叉的完整归因）

- 偏移表从 **184** 开始，每级 8 字节 `(绝对偏移 u32, 0 u32)`；`mip0偏移 == 184 + 8*mips`（【普查】2349/2349）。
- 每级字节数 = `ceil(w/4/2^i) * ceil(h/4/2^i) * 块字节`（BC7/BC5/BC6H=16、BC1/BC4=8）。
- **全量逐张验算**（【普查】§6）：严格通过 **2284/2349**；偏移表与块对齐算法不吻合 **65**；**只看文件长度**吻合块对齐累加 **2349/2349**；偏移表**完全无法解释**的 **0**。
- **65 张的关键事实**：**65/65 的 payload 长度精确等于块对齐累加值——没有一个字节是坏的**，有问题的只是**偏移表本身**；这 65 张被两条备用规则**全部复现、零残留**（【普查】6.1）：

| 备用规则 | 张数 | format |
|---|---:|---|
| **A：逐级 `w*h`，尺寸折半下限钳到 4，不做块向上取整**（= 官方插件自己的算法） | **10** | 31 |
| **B：块对齐尺寸，但每级最少占 16 字节**（<4×4 也按 4×4 记） | **55** | 23(54) + 22(1) |
| 无法归因 | **0** | — |

- 规则 A 就是 `…\MHW_Model_Editor\modules\tex\tex_function.py` 第 265–274 行的算法：`mipOffset += curWidth * curHeight * multi`（**没有** `ceil` 到 4 的倍数），`curWidth = max(curWidth//2, maxWidth)`；尺寸一路整除 4 时两种算法等价，一旦经过 125/62/31/15/7 这类非 4 倍数的级（500²/1080²/600²/2000²/4000²）就分叉。规则 B 的 54 张 `format 23` + 1 张 `format 22` 正是 v1 记的「`参考包N\...\RMT.tex` 前 10 级按 BC1、最后 3 级各占 16 字节」的**通用形式**——那条观察现在被 54 张同类样本证实（【普查】6.1、【集2】2.1）。
- **实用规则**：自己写 mip 表用**块对齐**算法、尺寸取 **4 的倍数**（4096/2048/1024）——此时两种算法结果完全一致，最安全（【普查】§9）。
- **容器公式的独立交叉验证（走 `.dds` 侧车）**（【集1】4.7）：`.tex − .dds = 184 + 8×mips − DDS头长`，三组算例全对：`152 = 184+96−128`（legacy 128B 头）、`132 = 184+96−148`（DX10 148B 头）、`140 = 184+104−148`（4096²/13 级）。同一批文件里 legacy 头与 DX10 头并存。

### 2.3 角色 × 格式交叉表（**权威表 = 【普查】槽级口径**）

**方法（本轮相对旧报告的关键能力升级）**：解析全部 **564 个 `.mrl3`**（0 失败）的材质项与资源项，用官方字典 `master_material_dict.json`（113 个 mmtr 条目）把 `resHash >> 12` 反查成资源名（`tAlbedoMap__disclosure` / `tNormalMap__disclosure` / `tRMTMap__disclosure` / `tEmissiveMap__disclosure` / `tColorMaskMap__disclosure` …），`resValue` 是 1-based 贴图槽下标，槽里就是贴图路径——**角色不依赖文件名，是材质表里的真实引用关系**（【普查】§4）。字典位置：`…\MHW_Model_Editor\modules\mrl3\dict\master_material_dict.json`（v1 §10 记的"字典不存在"已作废，见 §10）。

**权威表：仅第三方 + MD5 去重 + 仅被 mrl3 实际引用**（【普查】§4）：

| 角色 | n | 22 BC1 | 23 BC1_SRGB | 26 BC5 | 28 BC6H | **30 BC7** | **31 BC7_SRGB** | 30 vs 31 |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| **albedo** | 663 | 2 | 8 | 0 | 0 | 5 | **648** | **648 vs 5（99.2% sRGB）** |
| **emissive** | 619 | 1 | 3 | 0 | 0 | 6 | **609** | **609 vs 6（99.0% sRGB）** |
| **normal** | 267 | 36 | 0 | **197** | 0 | 28 | 6 | 6 vs 28（17.6% sRGB） |
| **rmt** | 126 | 5 | 5 | 1 | 3 | **79** | 33 | 33 vs 79（29.5% sRGB） |
| **mask** | 18 | 0 | 1 | 0 | 0 | **15** | 2 | 2 vs 15（11.8% sRGB） |

> 同一张贴图可被多个槽引用（"albedo + emissive 同图"的伪发光配方实测 **900** 张，是主流写法，不是异常）。全量口径（含我们的测试包）对照：albedo 1141 → 1097×31；normal 451 → 327×26；rmt 255 → 166×30。
> **读法**（【普查】4.1）：**albedo** `31` 压倒性（99.2%），`30` 只占 0.8% 且其中大半是我们自己的包（§2.6）；**emissive** 同样 `31` 为主（主流做法就是 emissive = albedo 同一张图）；**normal** `26 BC5` 为主、`22 BC1` 其次，**用 BC7 时选 30 而不是 31**（法线是方向数据，不能做 sRGB 解码）；**rmt** `30` 为主（70.5%）但有 29.5% 的作者误用 `31`；**mask** 样本少、分歧大，自绘 CM/CMM 用线性 `30` 更合理。
> **旧报告的数字**（保留作"同方向样本"，不再是权威值）：【集1】486 张 MD5 去重（文件名分类）albedo 31：271/272、normal 26：110/137、RMT 30：51/58、掩码 30：11/13（【集1】2.3/2.4）；【集2】367 张 31→233(63.5%)、26→63、30→62（【集2】2.2）；【精读】`参考包A` 颜色全 31、`参考包B` 31×18 全颜色类 / 22×8 全法线 / 30×12 全数据类（【精读】1.1/1.2）。三份旧报告的口径（按文件名）与普查（按材质槽）**方向完全一致、可以互证**；但**数值以普查为准**：文件名分类的后缀命中率只有 **1/3**（【集1】4.3 = 146/486 = 30%；【集2】2.4 = 112/367 = 31%），普查实测出现 **331 种不同尾串**，`_N`/`_P`/`OpenGL`/`Normal_P` 这类不带 `NM` 的尾串实测格式几乎全是 `26 BC5`（【普查】3.1）。

**产线结论**（普查槽级 + 旧三报告四方一致）：

```
颜色 / albedo / emissive  → BC7_UNORM_SRGB → format = 31, @17 = 1
法线                      → BC5_UNORM      → format = 26, @17 = 0
RMT（线性数据）            → BC7_UNORM 线性 → format = 30, @17 = 1
自绘 CM/CMM 掩码          → BC7_UNORM 线性 → format = 30, @17 = 1
```

### 2.4 两条必须记住的边界

1. **"30 对掩码/RMT 合法"**：RMT 与自制的 CM/CMM 掩码就该是 **30**（线性）。给它们打 31（sRGB）是**真正的约定违反**——游戏会做 gamma 解码，粗糙度/金属度整体偏离（【集1】2.7）。反向错误也确实存在：**33 张 RMT 被误标 31**（槽级口径；【集1】记的 7 张是一个子集：`参考包F` 2 张、`参考包G`、`参考包H`、`参考包I`、`参考包J`、`参考包E`、`参考包E` 各 1 张）（【普查】4.1、【集1】2.7）。
2. **"albedo 用 30"的第三方反例只有 5 张**（槽级去重口径），逐条列出（【普查】5.2）：`1096\...\acc005_BML.tex`（1024²，只被 albedo 引用）；`1175\...\Chiffon_nyarutoru\GrayRMT.tex`（2048²，albedo+emissive+rmt）；`1187\...\参考包G\hairNM.tex`（4096²，albedo+emissive+normal）；`1218\...\参考包B\Brown.tex` 与 `Red.tex`（各 1024²，albedo+emissive）。注意 `GrayRMT`/`hairNM` **同时被 albedo 槽引用**——它们是"作者把数据图/法线图兼作颜色图"造成的分类噪声，不是"作者有意把颜色图写成线性"。**判据**：拿不准角色时去解 mip0 像素，别信文件名（§2.5、§4）；v1 记的【集1】那张 `Tex_Fur_Mask.tex`（纯色 (151,151,255)、100% 同色）也是同一类误分类（【集1】2.5）。

### 2.7 两处头部字段更正（最高优先级）

#### 更正 1：`u32@124` 是 **`(W<<16)|(W>>1)`**，不是 `(H<<16)|0x800`

v1 抄【集1】的公式 `(H << 16) | 0x800` **不成立**。普查全量实测（【普查】6.2）：

| 宽度 | 实测 `u32@124` | **`(W<<16)\|(W>>1)`** | 旧公式 `(H<<16)\|0x800` |
|---:|---:|---:|---:|
| 4096 | 268437504 | **268437504** | 268437504 ✓（偶然） |
| 2048 | 134218752 | **134218752** | 134219776 ✗ |
| 1024 | 67109376 | **67109376** | 67110912 ✗ |
| 512 | 33554688 | **33554688** | 33556480 ✗ |
| 256 | 16777344 | **16777344** | 16779264 ✗ |
| 128 | 8388672 | **8388672** | 8390656 ✗ |

- **吻合率**：`(W<<16)|(W>>1)` = **2338/2349**；`(H<<16)|(W>>1)` = 2326/2349 —— 本语料 **13 张非方形贴图全部 = `(W<<16)|(W>>1)`**，所以可以确证是**宽度**而不是高度（【普查】6.2）。**第二份独立实测**（【翻绿】§1）：本工程 `milfy\1` 的 **39/39** 张全部满足 `@124 == @136 == @148 == (W<<16)|(W//2)`（2048→`0x08000400`、4096→`0x10000800`、512→`0x02000100`、128→`0x00800040`、16→`0x00100008`），与普查完全一致、再次否定 `(H<<16)|0x800` —— **两个互相独立的样本集（不同工程、不同批次）给出同一结论**。
- **旧公式为什么能骗到人**：它只在 `W == 4096` 时偶然成立（因为 `0x800 == 4096/2`），而旧报告列出的那张对照表里 **`2048→134218752` 本身就与它矛盾**（`(2048<<16)|0x800 = 134219776`）——**数据是对的、公式是错的**，两行放在一起就是自证；来源很可能是"同一个下标的误用"，正是 v1 §2.1 自己记下的教训。**源码级解释**：`tex_function.py` 第 247–249 行 `width2 = width // 2`，`if isRaw or formatName == "R8G8UNORM": width2 = width`；`file_tex.py` 第 118–121 行把它按 `(width2, width)` 两个 u16 写三遍 ⇒ `@31/@34/@37` 同值（【普查】6.2）。
- **11 张例外**（= 2349 − 2338，与吻合数完全对上）：

  | 类别 | 张数 | 实测 `@31` | 归因 |
  |---|---:|---:|---|
  | `(W<<16)\|W` | **8** | 1024² → `67109888`；8×8 → `524296`；256² → `16777472` | 插件在 **raw / `R8G8UNORM` 分支**下 `width2 = width`（`acc006_BML/NM/RMT`、`gm018_*_EM`、`NoImage_EM`、`vfx\1901\ice\hit\NM/RMT`）——**推断**，来自源码分支 |
  | 残留 4096 宽头 | **3** | `268437504` = `(4096<<16)\|2048` | 写头时**没更新 `@31/@34/@37`**（我们自己的 `1249\Body_Base.tex`(2048²)、`1249`/`1251` 的 `ribbon_black.tex`(1024²)） |

  → **可执行判据**：改尺寸/改格式后必须**同时重写 `@31/@34/@37`**；这三处一旦残留，自检脚本应当直接报错（v1 的 `@124 == (H<<16)|0x800` 自检会把正确文件判错、把错的判对）。

#### 更正 2：`u32@17` **与 sRGB 语义锁步**，写 31 就必须写 1

- **实测**：`@17`（字节 68）在 format ∈ {**28, 30, 31**} 时恒为 **1**，在 {**22, 23, 26**} 时恒为 **0**，**2345/2349 吻合**（4 张例外）（【普查】5.1、7.2）。`@68` 与 format 同向这条 v1 已记（【集1】722/722 零例外），普查把它从"冗余校验位"升级为**全量确认的规则**。
- **明确回答**：**写 format 31（BC7_UNORM_SRGB）时必须同时写 `@17 = 1`**；写 26/22/23 时写 `@17 = 0`；写 30/28 时写 `@17 = 1`（BC7_UNORM / BC6H 在 MHW 头里也带这一位）。**所以 `@9 = 31` 而 `@17 = 0` 的文件是自相矛盾的**——普查语料里这种组合几乎不存在（4/2349 例外），一旦在自己的产物里看到它，先怀疑写头脚本漏了字段，而不是"作者就这么写"。
- 意义：说明 `31` 不只是一个枚举值，**作者/工具是有意识地把它当"sRGB 图"在写**，游戏侧极可能真的按这一位做 gamma（此推断未实机验证）。
- ⚠️ **与插件源码的关系**：`file_tex.py` 的 `write()`（第 93–122 行）里 `@17` 落在固定 `b'\xFF' * 32` 段内，即**官方读入-写出路径会把它写成常量**，而普查实测它随 format 变 —— 说明**主流作者用的不是这个插件的写出路径**（更可能是随包分发的 `MHWTexConverter_by_Jodo.exe`，§3.1），或该位由 DDS 转换工具写入。**结论取实测：`@17` 必须与 format 锁步。**

### 2.8 法线图的"色彩空间被多做一次"——比翻绿严重一个量级（【翻绿】§3.4）

**实测（本工程 `milfy\1` 的 `该套装的贴图目录\Hair_Normal.tex`，4096² BC5、13 级 mip）**：成品解出的 R/G 均值 **54.15 / 54.06**，而源 PNG（Unity/VRChat 原包 `Nomal.png`，MD5 `3f39a1bd…` 三方一致）是 **127.06 / 127.04**（std R 4.73、G 1.98，G 落在 120–135 的像素占 98.8%）——**这张图被多做了一次 sRGB→线性**：

| 模型 | 平均 \|差\| R / G | 误差 ≤2 LSB 的像素占比 R / G | 判定 |
|---|---|---|---|
| **照原样（raw）** | 72.92 / 72.99 | **0.0000 / 0.0000** | ✗ |
| **`srgb→linear(源图)`** | **0.176 / 0.139** | **0.9961 / 0.9994** | ✅ **就是它** |
| `linear→srgb(源图)` | 133.05 / 133.15 | 0.0000 / 0.0000 | ✗ |

**后果可直接算成角度**：tangent-space 法线的 R/G 本来就该被**当线性值直接读**（`nx = R/127.5 − 1`）：

| 版本 | mean nx | mean ny | \|nxy\| |
|---|---|---|---|
| 现状（被线性化、未翻绿） | −0.5753 | −0.5760 | **0.8141** |
| 只翻绿（`试验包20`） | −0.5753 | **+0.5760** | **0.8141** |
| 修回缩放 + 翻绿（`试验包21`） | **−0.0038** | **+0.0034** | **0.0051** |

正常法线图（平面区域法线 = `(0,0,1)`）的 `nx,ny` 均值应 ≈ 0；现状 **0.814 ⇒ 整张头发表面被整体歪了 54°**，
表现为"不管从哪个角度看都糊着一层固定错误明暗"，而不是"凹凸方向反了"那种轻微症状。

- **要点 1**：**法线图必须 raw 存，任何 gamma 变换都会让整面法线偏斜。** 这一条同时适用于我们的转换链与"抄别人图"。
- **要点 2**：**"歪了多少度"是可直接计算的**——把 BC5 解成 `nx,ny` 求均值即可，**比看渲染可靠得多**（渲染还得先解决 §8.3#1 的标定问题）。这是本 skill 里少见的"有闭式判据"的项。
- **要点 3（别过度归因）**：同一批转换、同一套脚本产出的**另外 4 张 BC5 法线图全部是 raw**，6 张 BC7 颜色图（`Hair_AshBeige`/`Hair_Acc`/`Face`/`Body_Base`/`UV1_Skyblue`/`Stockings`）**也全部是 raw** ⇒ **这是一张图的一次性手滑（典型来源：导出时误加 `-srgbi`），不是流水线系统性错误。** 判据：发现问题后**必须把同批产物全量审计一遍**，否则会把"单点事故"误判成"系统性缺陷"（或反过来漏掉系统性缺陷）。
- 溯源链可信度：`06_头发_TwinTail\...\Nomal.png`（Unity 原包）→ `04_贴图转换\待转tex\Hair_Normal.png` → `04_贴图转换\成品\Hair_Normal.png` **MD5 完全相同**；且解码由 numpy BC5 解码器与 `texconv` **两个独立解码器**互证（R/G 通道逐像素 max diff = 0）。

### 2.9 "绿通道统计"是空判据——一次被数学证伪的验证路线（【翻绿】§3.3）

任务给定的前提是"Unity 用 OpenGL(+Y)、MHWI/DX 用 (−Y)，所以 Unity 法线图必须翻绿"。本次尝试用通道统计去验证它，**结论是这条路在数学上不可能成立**：

| | mean R | mean G | std G | 以 127.5 为中心的偏度 | 直方图 120–135 占比 |
|---|---|---|---|---|---|
| 现状（未翻） | 54.145 | **54.055** | 1.857 | −1.001 | 0.0000 |
| 翻绿后（`255−G`） | 54.145 | **200.945** | 1.857 | **+1.001** | 0.0000 |

`G → 255−G` 是一个**对合变换**：`mean G` 的镜像是 `255−mean G`，而 **`|mean G − 127.5|` 完全不变**（实测 73.4450 → 73.4450）；`std` 不变、直方图形状不变，**只有反对称统计量的符号会翻转**。孤立的一个符号不携带信息，除非有"外部参照"告诉你是哪一种。

- ⇒ **"翻绿有没有必要/有没有翻对"无法用通道统计判定**，只能回到**素材来源**与**游戏内 A/B**。（这是本 skill 里唯一一条被**证明**为空判据的路线，所以单独成节。）
- 用"能不能区分假设"来筛判据：能区分的是**相关系数**——"同一素材已翻绿"应满足 `corr(R_cand, R_ours) ≈ 1` **且** `corr(G_cand, 255−G_ours) ≈ 1`。用它扫全工程名字含 hair/normal/nm 的 `.tex`（845 个候选 → BC5 成功解码 **553** 张 → 同尺寸 4096² 可做相关的 **109** 张），最高 `corr(G, 255−G_ours)` 只有 **0.0053**、`corrR` 全在 ±0.002 内 ⇒ **工程里不存在这张法线图的翻绿副本，它从来没被翻过。**
- ⚠️ **但"从来没有翻过"只等于"没有反例"，不等于"证明了必须翻"。** 本次**既没能证实也没能证伪** `Unity(+Y) vs MHWI(−Y)` 这条前提；翻绿是按该前提执行的（§10）。
- **可移植的一句话**：**先证明你的判据能区分两个假设，再去量。** 一个对"翻前/翻后"取值相同的统计量，量一万张也是零信息——和数据量无关，和变换的对合性有关。

    7: "R8G8B8A8UNORM", 9: "R8G8B8A8UNORMSRGB", 19: "R8G8UNORM",

```

- **这解决了 v1 的悬案**：`23 = BC1_UNORM_SRGB`（DXGI 72）、`28 = BC6H_UF16`（DXGI 95）。报告里写的 `BC1_UNORM_SRGB` / `BC6H_UF16` 是 DXGI 正式名，插件字典用无下划线缩写，**同一个值**。

## 4. mrl3：材质项 / 资源项 / 贴图表

### 4.1 结构（实测字节偏移）

```

### 4.2 三条最容易走弯路的规则

1. **CB 的 key 是 master 字典里 `resourceDict` 的 key（= `resHash >> 12`），不是资源项的 `typeID`**（【集2】3.1）。普查把这条规则用到极致：`resHash >> 12` + `master_material_dict.json`（113 个 mmtr 条目）⇒ **槽级角色判定**，这是 §2.3 权威表的数据基础（【普查】§4）。
2. 反面教训：CB 的磁盘 `typeID` 实测恒为 `(resHash & 0xFFF00000) | 0xDCDC0`（在 **42 个不同资源**上验证，低 20 位 `0xDCDC0` 是常量），**拿它去查 `property_dict` 必定失败**；报告作者"为此绕了三轮弯路，改成用字典 key 后立刻全通"（【集2】3.1）。
3. **`resValue` 有两种语义**：对贴图资源 = **贴图槽 1-based 索引**；对 CB 资源 = **该材质块内部的字节偏移**（【集2】3.1；同一条规则被本工程独立复用于 `C32_精简成品包.py` 的活槽判定链）。

### 4.6 材质名：mod3 与 mrl3 的接口

从 **152 个 mod3** 里正则提取材质名（ASCII 明文），全场只有 **26 个不同名字**，且高度集中在两族（【集2】3.6）：`Ch_Pl_Standard_Mt__<n>` 与 `Ch_Skin_Mt__<n>`，编号只落在少数几个值上（1–22、78、98–100、7、16）。最高频：`Ch_Skin_Mt__7`(25 个 mod3)、`Ch_Pl_Standard_Mt__16`(24)、`Ch_Pl_Standard_Mt`(24)、`Ch_Pl_Standard_Mt__3`(13)。**这就是"借壳"的直接证据**：作者不自创材质名，而是复用壳 mrl3 里已存在的名字改贴图指向——因为 **mod3 是按名字 hash 去 mrl3 找材质的**（【集2】3.6）。

### 4.7 ★★ 材质名哈希 = `crc32(name) ^ 0xFFFFFFFF`（A 级，实测 2738/2738）

§4.6 说"mod3 是按名字 hash 去 mrl3 找材质"，但**没给公式**。本工程独立实测
（`本项目调研记录\epv与描边_调研.md` §5）：拿官方字典 `various_hash_dict.json` 的全部
**2738 条**"名字→哈希"用 `crc32(name) ^ 0xFFFFFFFF` 复算，**2738/2738 全部命中**。

**三个直接用途**：

1. **字典里查不到的名字也能用** —— 想给模型加一个语料里没有的材质名（如描边用的 `Outline_Black`），
   按公式算哈希、**复用该部位 mrl3 里的一条"死条目"**（只改它的 `nameHash`）即可生效
   （已在游戏里验证）。
2. **可以反过来校验"活槽"**，不必依赖字典完备性。
3. ⚠ **反面**：`crc32(name)` **不带** `^ 0xFFFFFFFF` 是错的 —— 拿错公式会让"活材质"被误判成死材质，
   它的贴图槽会被当成"无人引用"而移走（实测 `Outline_Black`：错算 869338960、正确 3425628335，
   两者恰好互反）。

### 5.3 「抄系数必须连数据一起抄」——本项目最重要的一条换算

**参考包 `参考包A` 的配方**（【精读】2.1，18 个 `PL_Mt` 中 15 个完全相同）：`Base=(1,1,1,1)`、`Emissive=albedo 同图`、**`EmiF=(8,8,8)`**、`Metalic=Roughness=Specular=1.0`、`Translucency=0.0`、`bUseCMM=0`、`bBaseColorEmissive=0`。

**而它的贴图数据只有我们的一半亮**（【精读】1.4，取 `alpha>250` 共同区域逐亮度档实测）：Face 的分档比值 **六档全部 ≈0.52、与亮度无关** ⇒ 是**线性缩放**，不是 γ 变换（线性模型残差 3.89/255，而 sRGB↔线性模型残差 4.74，**反而更差**）；Body ≈0.53（残差 0.97）。**所以换算关系是**：

```
参考包等效发光 = 8.0 × 0.52 ≈ 4.16
我方数据 ×1.0  ⇒ 目标 EmiF ≈ 4.0（不是 8.0）
```

- **抄图不抄系数 ⇒ 整体偏暗；抄系数不抄图 ⇒ 整体偏亮。** 两者必须成对（【精读】5.1）。
- 推荐落地：只动系数、不动贴图 —— 脸/身体/头发/兽耳统一 `Base=1.0 / EmiF=4.0`，保持 `Specular=Metalic=Roughness=1.0`（【精读】5.1 / 5.2）。
- `参考包B` 的侧证：参考包给脸/头发/衣服全都加了 **`Outline_Red`/`Outline_Brown`/`Outline` 描边壳网格**（body 里 `Outline_Brown` 占 32,114 顶点、arm 14,969、leg 8,339），每个壳有自己的材质和 albedo——二次元描边的标准做法（【精读】4.6）。
- **⚠️ 不要硬套配方**：同一个包的不同部位（body/wst/arm/leg）配方也可能不同，最快最稳的做法是**直接读目标 mrl3 的 CB 值照抄**（【集2】3.5、4.6）。`参考包A` 的 leg 用 `Base=0.4/EmiF=1.5` 而脸/身体用 `1.0/8.0` 就是同包内不一致的实例（【精读】2.2）。

### 5.4 路径前缀规则（别写错）

- 自己模组的贴图：**相对 `nativePC` 的路径、不带 `nativePC\`、不带扩展名**（`pl\<作者E>\参考包A\Face`、`pl\<作者F>\参考包B\参考包B_Body_A_BML`）（【精读】4.1、【集2】4.1）。
- 游戏自带图：**必须写全 `Assets\default_tex\...`，不能加自己模组的前缀**（【精读】4.1）。
- **实测教训**：给 `Assets\default_tex\...` 前面多加了一层模组目录，会留下一个"活槽指向不存在文件"的洞（【脚本】`C25_材质指向.py` 注释引 D81 实测）；另外**不要自己编游戏里不存在的贴图名**（例如自造的 `null_black_alpha_BM` 在捐体 mrl3 里出现 **0** 次）。

## 6. 网格 / mod3 侧

### 6.1 结构实测（修正了插件源码的一处误读）

**`meshOffset` 字段就是网格信息表的绝对偏移，不需要再加 `materialCount*128`**——按后者算会得到一个全是乱码的 `blockType`，改回直接用头部 `meshOffset` 后全部字段自洽、并用 AABB 校验通过（【精读】3.1）。网格信息项仍是 80 B：

> **★ 补充（第 15 次实战实测，`第13套`）：两个表的字节偏移直接照抄这两条，别自己数**
> —— 头部前 12 字节是 `magic u32@0 / version u16@4 / boneCount u16@6 / meshCount u16@8 /
> materialCount u16@10`；再往后是 `vertexCount@12 / faceCount@16 / unkn@20 / vertexBufferSize u64@24 /
> groupCount@32 / (skip 4)@36 / timestamp u64@40 / boneOffset u64@48 / groupOffset u64@56 /
> **materialOffset u64@64** / **meshOffset u64@72** / vertexOffset@80 / faceOffset@88 / …`。
> ⇒ **`materialOffset` 在字节 64、`meshOffset` 在字节 72**（差 8 就会把网格表读成浮点噪声，
> 症状是"顶点数 65535 / mid 越界"）。材质项 **128 B**（名字是其中的 ASCII 串，用
> `re.search(rb"[ -~]{4,}")` 找，**不要**假设它在固定偏移）；网格项 **80 B**。
> 自检：`materialOffset + materialCount*128 == meshOffset`（实测 16224 + 10×128 = 17504 ✓）。
> 材质表第 0 条恒为 `InvisibleMantlesModEmiFix`（导出器插的）；**同一个材质名被 N 个网格共用时
> 表里只出现一次**（所以"`strings mod3 | grep -c 材质名` = 1"不代表只有一个网格用它，
> 要按 `mid` 下标到材质表里查）。

| 偏移 | 字段 | 说明 |
|---|---|---|
| +0 | shadowFlag (u16) | 本两包全为 **19** |
| **+2** | **vertexCount (u16)** | |
| +4 | groupID (u16) | |
| **+6** | **materialID (u16)** | |
| +8 | lod (u16) | 本两包全为 **65535** |
| +14 | blockSize (u8) / renderMode (u8) | renderMode 全为 **195** |
| +16 | vertexSub (u32) | **指向全局面缓冲的绝对起始顶点号** |
| +20 | vertexOffset (u32) | 相对于头部 `vertexOffset` |
| +24 | blockType (u32) | → 顶点格式名（如 `IASkin4wt1UVColor` / `IASkin8wt1UVColor`） |
| +28 | beforeFaceCount (u32) | **三角形**数（不是索引数） |
| +32 | faceCount (u32) | **索引**数（= 三角形 × 3） |

**拓扑布局要点**：**顶点缓冲区是所有 mesh 拼接的全局面缓冲**；**面缓冲区放的是每条网格自己的局部索引**（起点 = `faceOffset + beforeFaceCount*2`），面索引**要加上该 mesh 的 `vertexSub`** 才是全局顶点号。已用"索引范围 ≤ vc"自检通过（body mesh0 0~11483 / mesh1 11484~29901）（【精读】3.1）。`renderMode=195` / `shadowFlag=19` / `lod=65535` 在**参考包与我方 34 个网格上完全一致**——**不是差异点**，别去动它（【精读】3.2）。

## 8. 反例与判据陷阱（本项目实际踩过，务必收录）

### 8.1 "直接抄别人的贴图"——UV 能对上也不等于能用

- 参考包 Face 与我方 Face 逐像素相关系数 **0.974**（同一张美术图的不同处理），但参考包的贴图是**同一张图整体 ×0.52 的亮度**（Face 六档比值全 ≈0.52、Body ≈0.53，线性缩放非 γ）⇒ **抄图不抄系数 = 整体偏暗；抄系数不抄图 = 整体偏亮**，两者必须成对（【集1】4.x/【精读】1.4、5.1）。
- 反向教训：我方 `Body_Base.tex`/`Face.tex` 与"游戏里跑通过"的参照文件**逐字段完全一致**（46 个头部 u32、mip 偏移表、文件长度全一样），说明容器没问题——**差别只在图像内容**，查错时要先分开"容器层"和"内容层"两个坐标系（【脚本】`C31` 注释引 D75）。

### 8.2 "用降系数去补偿贴图/色彩空间问题"——本项目往返了三轮（**§2.8 是同一个错误的另一副面孔**）

> **谱系**：8.2 是"用系数去补偿一个颜色空间错误"，§2.8 是"颜色空间错误本身还没被发现"。
> 两者是同一类根因（**色彩空间/格式标志错**）在不同阶段的两种表现；共同教训是
> **先把标志与数据修正，再谈系数与观感**，并且**一次只改一个变量**（§8.3#8、§9 步骤 8）。

因果链（【脚本】`C25_材质指向.py` 注释 + `C24_材质贴图.py` 注释）：

| 阶段 | 状态 | 表现 |
|---|---|---|
| 起点 | 亮数据（sRGB 原值）+ **线性标志 30** + EmiF 3.0 | **太白**：sRGB 数据被当线性用 = 整体被抬亮 |
| 第 1 轮 | 为压白度把自发光/基础系数降下来 | 补偿的是**错误的标志** |
| 第 2 轮 | Base 压到 0.4、EmiF 降到 1.5 | **很暗**（贴图对、标志对、但系数还带着补偿残留） |
| 第 3 轮 | 换回参考包的贴图与标志，系数**必须跟着回到 4.0 / 1.0** | 恢复 |
| 根因 | **只是 `.tex` 的 format 标志（30 vs 31）** | 一个字段 |

> **判据**：**任何时候用"降系数"去补偿一个你还没量过的量，就是在制造第二个未知数。** 先修标志/数据，再把系数一次性对齐；不要"一边降系数一边换贴图"（【精读】5.1 原话："不要同时改贴图亮度（那会引入两个变量，重演上次'用降系数补偿错误标志'的坑"）。**本轮普查给这条因果链补上了外部证据**：全语料里"albedo 用 30"的样本有 **20 张去重**，其中 **15 张是我们自己的三个测试包**，第三方只剩 5 张（§2.6）——**这个坑在样本统计里也留下了指纹**。

### 8.4 别改作者配好的形状

为治"袜子与鞋之间的间隙"，本项目给袜子做了**几何外扩/贴身化**（`C4/C4b/C7/C13/C20`，实测把袜筒推到离腿 15mm、后续又收回 2mm……），结果**反而制造了穿模**（红色穿插像素）。**还原成原始形状后穿模消失**（【脚本】`C44_revert_sock.py`：从最早的备份 dump 袜子顶点、写回当前 blend、并把每个形态键同步同一 delta）。

> **判据**：当"修 A 引出 B"时，先做一次**完整回滚验证**——如果回滚后 B 也消失，说明 B 是你的改动引入的，不是原模型的缺陷。

### 8.5 别把作者有意的手法当垃圾清掉

- 脸部的**自定义法线是二次元"平面脸"手法**（朝脸朝向压平），整片清除会让**脸变立体、变白**；正确的度量是**局部起伏**（相邻顶点法线夹角均值：原来 14.78° → C36 后 11.88° → C37 迭代平滑），而**不是**"与几何法线的偏离度"——后者会把作者的风格判成坏点（D96 实测：脸 29.2°、>90° 占 7.52%，而身体/头发/丝带只有 0.01~3°）（【脚本】`C34_法线重算.py`/`C36`/`C37`）。
- `C37` 最终的取舍：掺回 **0.10** 的几何法线。0.30 试过 —— 鼻子周围出现立体阴影，用户反馈"立体感太强，还不如看不到鼻子"。用户的诉求是"鼻子是一个点"（靠**贴图上画的黑点**表现，不要几何起伏）。⇒ **二次元脸的法线是"风格资产"，不是待修的缺陷。**

### 8.6 烘焙 alpha：别把"半透明"当"空白"

- 规则曾经写成"**alpha<250 全填**"，结果把**画在半透明层上的暗色细节一起抹掉**了。实测：脸贴图的"很暗(<60)"像素从 **0.337% 掉到 0.009%**，游戏里**鼻子那个小黑点就没了**。**正确做法：只填 `alpha == 0` 的真空像素**；`0 < alpha < 250` 的软边**保留原 RGB**，只把 alpha 拉平成不透明（【脚本】`C31_贴图烘焙alpha.py`）。
- 参考包是对照组：它**把 alpha 当覆盖蒙版用**——REF Face `alpha=0` 占 **23.00%**、`alpha<250` 占 **26.65%**（Body 21.92%/30.36%、Hair 26.30%/27.13%），而我方成品三张的 alpha **全部 = 255**（【精读】1.4B）。背景：脸贴图 4096² 里 **23.0%** 的像素是 UV 岛外空白（身体 30.9%、头发 28.7%），RGB 白、alpha=0；嘴/鼻这类最小最密的岛在 mip 过滤时会被周围空白"渗"进来，若材质按 RGB×alpha 取就是**白×0=黑**，正好是"嘴鼻处斑驳的暗影"（【脚本】`C31`）。
- **色彩空间同样会伪装成"图案错位"**：把每张贴图与"用户满意的旧 build"同名 `.tex` 解码对比，发现 `Hair` 和 `军装藏青` 在旧 build 里是 **sRGB→线性**（差 5.0 / 0.27），按原样出图差 38.8 / 54.1 —— 这才是"袜子白圈发黑、裙摆白条错位"的真因（同图案不同色彩空间时，深色藏青从近黑变成中灰，白/藏青边界看起来就移位了）。**⇒ 这条与本轮普查的 `@9`/`@17` 是同一类错误：色彩空间写错时，现象会伪装成"图案/几何问题"**（【脚本】`C31`）。

### 8.7 ★★ "作者到底给这件配了哪个材质" —— 权威是**源包的 prefab/slotmap**，不是预览工程

`第6套` 实测：素材 的 **`A_Collar` 与 `Tail.001` 在预览工程里 `data.materials = []`（材质槽是空的）**。
如果只读预览工程，就会得出"这两件没材质"；而源包解包目录里的
**`_extracted\resolved_mats.json → slotmap_prefab`**（Unity prefab 的"对象名 → 材质名"表）写着
`A_Collar → A_White`、`Tail → fur`（`fur` 是**无贴图的平涂色** 0.93/0.90/0.86，只有 `_Color`）。
⇒ **"某件没材质/材质可疑"时第一件事是查源包的 prefab/slotmap**；预览工程的对象材质槽可能是导入时丢的。
（这与 §8.1 同族：**别拿"看起来像"的东西当依据**，要找那个"作者亲手写下的对应关系"。）

### 8.8 ★ 一个"交接给别人的读数"里最容易错的一类：**角度/长度用算术推、而不是拟合**

`第6套` 的交接材料写"丝袜绕踝 ≈ **6.2°** = atan(Δz/Δy)"（总升高/总长）。实测用
**沿脚长分箱取最低 z + 最小二乘**拟合鞋底剖面得 **9.20°**；两者对"鞋底是不是平面"的假设不同 ——
那只袜子的鞋底其实是 **rocker（脚尖 9cm 平垫 + 后跟往上翘的坡）**，不是平面，
算术角度会**转不够**（残差带 10.3mm vs 4.8mm）。
**规矩**：姿态类几何量一律**从剖面拟合**，并且**至少比较两个候选值的残差带**再选；
"atan(Δ总/Δ总)"只在能确认目标面是平面时可用。

## 9. 解剖一个陌生模组的推荐流程（可执行清单）

按这个顺序做，**每一层都能独立证伪**，不要跳步直接改自己的工程。

1. **先确认"这个包不是自己造的"**：看 `info.xml` 的 `installSource`；是安装版模组库时，先剔掉自己的导出测试包再做统计（§2.6、§8.3#6）。
2. **再看目录骨架与部位**（不改任何文件）：`nativePC\pl\f_equip\pl<NNN>_<NNNN>\{body,arm,wst,leg,helm}\mod\` 下是否有成对的 `f_<part><NNN>_<NNNN>.{mod3,mrl3,ctc,ccl}`、`helm` 位是不是 `.evhl`（【集2】4.1）；贴图目录是"作者命名空间"（`pl\<作者>\<作品>\`）、"复用他人目录"（`pl\<公共目录>`/`pl\<作者A>`/`pl\<作者C>`/`pl\<作者D>`）还是"无 `pl` 前缀"（`该角色_X\`、`该角色_X\`、`参考包E\`）（【集1】4.1）；顺手扫一眼 `备份`/`beifen`/`无CMM`/`原版`/`+0.06` 之类命名——有的话**你拿到了作者的迭代史**（【集1】4.5）。
3. **列 `.tex` 的角色与格式**：先按文件名后缀分类，**再用 format 字段交叉验证**（颜色类 31、数据类 30、法线 26/22）（【普查】4.1、【集1】2.4、【集2】2.3）。后缀命中率只有 **1/3**（【集1】4.3 = 146/486 = 30%；【集2】2.4 = 112/367 = 31%），普查实测 **331 种尾串**，所以**后缀只能当提示，不能当判据**；拿不准就解 mip0 像素（§2.5），**有 mrl3 就走槽级判定**（§2.3、§4 开头的方法说明），那才是硬判据。
4. **看容器自检**：`184 + 8×mips + Σ各级字节 == filesize`；**`@31 == @34 == @37 == (W<<16)|(W>>1)`**；**`@17` 与 format 锁步**（{28,30,31}→1，{22,23,26}→0）；`@30 == width`。**任何一条不成立，先怀疑自己的下标算错了**（【集1】2.1、【普查】6.2/7.2）。若长度对而偏移表不对，去查是不是撞上了 §2.2 的规则 A/B。
5. **再看 mrl3 槽位与 CB**：从 mod3 提取材质名（ASCII 明文正则）→ 按 `materialNameHash` 找到材质 → 读资源项 → `resValue-1` 是贴图槽下标 → 槽里的路径就是这张图的真实角色（【集2】4.2）；看到 `default_tex\null_*` 就是"没在用"（【集2】3.3）；要抄系数就**逐字段读 CB**（`fBaseMapFactor@0`、`fEmissiveMapFactor@16`、`fMetalic@28`、`fRoughness@32`、`fSpecular@36`、`fTranslucency@48`、`bBaseColorEmissive@52`、`bUseCMM@68`），**别套配方**（【集2】3.5）。
6. **最后对比 mod3 网格组织**：`meshOffset` 直接用（不要加 `materialCount*128`）；校验"面索引 + `vertexSub` ≤ `vertexCount`"；比 `renderMode`/`shadowFlag`/`lod`（参考包与我方一致，通常不是差异点）；量"唯一位置占比"（脸 95.2% vs 100% 就是硬边/平滑的差别）（【精读】3.1~3.3）。
7. **只有在以上几层都查完、且能写出"根因只有一个"的假设之后，才动自己的工程**；并且**一次只改一个变量**（§8.2）。
8. **动手前：备份 + 压缩域逐字节可回退 + 单变量分包**（【翻绿】§0、§4、§8）。三条都要做到：
   - **双备份**：就地 `.bak`（打包时排除）+ 工程外第二份，并**校验两份备份与上一版发布包内该文件逐字节相同**（同 size、同 MD5）⇒ 才能确认"没改错对象"（本次两份备份 MD5 相同、且与 `试验包19-低亮.zip` 内那张一致）。
   - **改动脚本幂等**：每次都从 `.bak` 重算，重复运行结果一致；新产物**已存在就拒绝覆盖**。
   - **同一个问题拆成多个单变量包**：本次刻意分成 `试验包20-翻绿`（只翻绿）与 `试验包21-色彩空间修复+翻绿`（翻绿 + 修回被误加的 sRGB→线性）两个包，就是为了让游戏内 A/B 能**归因**——一个包同时改两件事，测出差异也说不清是谁的。**同时改两个变量 = 用一次实验换回零个结论。**

### 9.1 我们自己的 `.tex` 写出清单（普查 §9 的直接落地）

### 11.3 权重存储与导出（踩过的坑，逐条都能省一轮）

- **权重数值存在 1/1024 网格上**（实测 1,019 个取值、步长 0.000977）⇒ 两次导出会有 **±1 格量化差异**，**别把量化当改动**。
- **导出侧顶点数 ≠ blend 侧**（本次 16,517 → **18,418**，按 UV/法线接缝拆点）⇒ **逐顶点比对必须用导出侧口径**，否则永远对不上。
- **权重数组步长 = 全网格最大影响数 × 4 B** ⇒ "给顶点加影响"会**改变整个文件大小**（实测 6→4 时精确少 **147,344 B** = `(6−4)×4×18,418`，且**三个头部尺寸字段各自恰好少同样多**）⇒ 用文件大小/尺寸字段可以**反推影响数变化**。
- **导出走求值网格**（`evaluated_get`）⇒ 改了权重，**逐顶点坐标/法线末位也会变** ⇒ **不能说"只改权重 ⇒ 几何逐字节未变"**，只能说"**基础网格数据未改**"。
- **重导出不是字节确定的**：同一 blend 仅改权重，两次导出差 **493 B 浮点末位噪声 + 头部 2 B** ⇒ **一切重导出比对必须用内容级判据**。
- **最小路径 `B6_材质名对齐 → B7_导出mod3` 与整条 `C10` 链对 body.mod3 等价**（实测 3,725,540 B 完全一致）⇒ 实验可放心用最小路径。
- **后台导入必须 `preferences.showConsole=False`**，否则崩（**不是文件损坏**：旧文件同样崩、补上即成功）。
- **`to_mesh()/to_mesh_clear()` 必须作用于同一个 `evaluated_get` 引用**，后台模式建议直接读 `ev.data.vertices`（否则硬崩、无 traceback）。
- **`C10_一键收尾.py` 取 `sys.argv[1]` 当可选源 blend** ⇒ `blender -b X.blend` 会被 `-b` 占位报"源文件不存在"；直接传主工程会 `SameFileError` ⇒ **正确做法 = 复制一份主工程当源**。
- Blender 里 **`Bone.length` / `head→tail` 是导入器占位值**（统一 5 cm、朝向 +Z）⇒ **拿它比骨长会得到"假通过"**；要比就用 **head→head 跨度**。
- **跨产物线共写同一批文件必须约定"谁最后写"**：本次材质线与权重线曾在 `leg.mrl3` 上撞车（**同一个文件装两套内容**）。**外科合并**是把这条约定固化成做法：以**已验收包**为底 → 只替换目标文件 → 条目级核对"**33/33 条目、差异条目恰好 1 个**"。

### 11.4 ★ 操作性判据的设计规则（本轮唯一见效的方法论）

1. **症状是视觉的 ⇒ 判据必须是可见量**，而不是"权重总量/占比"这类代理量。
   实证：`V[g]`（权重总量）**四项全过而实机毫无变化**（十四轮全无感）；换成"**展掌姿势下的皮肤拉伸率**"后**一次对症**（实机确认拉伸消失）。
2. **判据三件套缺一不许上线**：**零点自检**（姿势=静置 ⇒ 拉伸率恰好 1.0、位移恒 0）＋**已知好对照**（另一份实机正常的模组）＋**能分开已知好/已知坏**。
3. **判据必须能失败**：任何"**恰好 0.0 / 恰好 100.0（或空集）**"的读数**一律当 bug**，且必须给出**成因 + 交叉验证**（本规则上线首轮就拦下 8 个异常读数）。
4. **判据必须与"用户眼确认过的现象"同序**：本次分指严重度（中指最重 > 无名 > 小指 > 食指最轻、拇指 0）与用户实机表述一致 ⇒ 判据可信。
5. **先定操作性判据，再谈修法**：**离线判据全过 ≠ 实机可见效果。**

| # | 纪律 | 代价实例 |
|---|---|---|
| 1 | **空对照/自证式对照不算对照** | "我们自己骨架 vs 我们自己导入的骨架 = 0.0000°"——两边同一套数据、同一条通道 ⇒ **那个 0 被保证**（同类第 3 次） |

| 6 | **不许把"推算的偏移"当已知量** | `对齐点 − 步长×顶点数` 推出的偏移被当常量写进解析器 ⇒ 读的全是浮点段；**被"权重和恒定"自检拦下** |

| 8 | **探针/样本先校验有效性** | 探针设了 3 个顶点，其中一个骨名不在该网格顶点组 ⇒ 样本静默变成 2 个 |

4. 沿**最近身体点的法线**外推；
5. **迭代**直到达标。

### 11.11 ★★ 判"这套素材与我们的身体是不是同源"：逐骨对拍（含 ×100 缩放的变体）

换装工程里**最省时间的一步**：把新素材的骨架与目标身体的骨架**逐骨对拍**。

本轮（`第4套` 的素材）实测：新素材骨架 `Armature.1`（261 骨）与身体 `Armature`（222 骨）
有 **33 个同名骨**、**head 距离 max = 0.000000 m** ⇒ **同源**（就是同一副骨架）。

**判读表**：

| 对拍结果 | 结论 | 省掉什么 |
|---|---|---|
| 同名骨 head 差 **< 1e-3 m** | **同源** | **配准与权重转移都可省** —— 顶点组按名字映射即可用；链的根位置可直接用它的骨 head |
| 差**整 100 倍**（且轴模长是 1/100） | **×100 缩放变体** | 只需几何整体 `scale 0.01`（**纯均匀、无旋转无偏移**）；**不要去解相似变换** |
| 差几毫米~几厘米 | 同一世界空间但要微调 | 解一次相似变换（Umeyama），把残差报出来 |
| 差一个量级 / 名字对不上 | **另一套身体** | 只能做权重转移 + 逐件贴合（成本完全不同） |

**做法**：`bpy.ops.import_scene.fbx()`（或直接开 `.blend`）后，打印两边同名骨的
`matrix_world @ head_local` 求最大距离 —— **5 分钟出结论**，比导入后慢慢试快得多。

**两个前提（都踩过）**：

1. 对拍用 **骨 head**，别用骨 `tail` —— 导入器的 tail 是**显示朝向**，不可靠
   （实测同一个文件里 `Skirt_AL` 的 tail 朝下、`Skirt_AR` 的 tail **朝上**）。
2. 骨架自带的 **`*_end` 叶骨**是导入器补的标记，**不该出现在任何顶点组里**；
   权重里若出现 `*_end`，说明"组名 → 骨号"的映射表漏了。
   （反过来说，看到成对的 `Bone` + `Bone_end`，就知道这套素材来自 Unity/VRCat 系工具链。）

**这条判据的另一半价值**：同源 ⇒ 可以**直接拿它的骨 head 当链的根位置**；
不同源 ⇒ 任何"照抄骨位置"的做法都会错，必须从几何实测。
（两者都别忘：**链的方向与长度永远从几何实测**，骨的 tail 不可信。）
**★★ 只比骨 head 是不够的：还要比「骨方向夹角」—— `第11套`（某套装）的实战教训**

`第11套` 的素材骨架 `OPAL_Armature`（205 骨）**`Hips` 与 该角色 逐位相同（0.0000 m）**、同名 65 个、
顶点组里还带着 该角色 真身骨（`Wrist_support.*` / `Elbow_support.*`）⇒ 上面那张表会判它「**同源**」。**但它不是**：

| 骨 | head 距离 | **骨方向夹角** |
|---|---|---|
| Hips / Spine / Chest / Neck / Head / Shoulder.L / 整条腿 | **0.0000 m** | **0.0°** |
| `Upper_arm.L` | 0.0000（**肩关节重合**） | **45.0°** |
| `Lower_arm.L` | **0.1515 m** | 45.0° |
| `Hand.L` | **0.2870 m** | 45.0° |

⇒ **素材的衣服是按「手臂 45° 下垂」（A-pose）做的，而目标是 T-pose**。只比 head 会得出「同源、
不用配准」的结论，然后**绑在那条链上的件（袖子 / 披肩）在游戏里会多转 45°** —— 而绑躯干 / 骨盆 / 头的件全对。
**症状看起来像「某几件绑错了」，实际是整条链差一个旋转**（这个「错件的分布」本身就是最强的定位线索）。

**三条便宜判据（判 T / A pose，不需要配对参照）**：

1. 身体网格里「**主导组 = 手的骨**」的顶点**质心 z**：与**肩同高** ⇒ T-pose；落到 `z≈0.7`（约肩下 30 cm）⇒ A-pose。
   （`第10套` 的 `Body_base` 实测 **1.0015** ⇒ T-pose。）
2. **MHWI 骨架的指纹**：`MhBone_006/007/008`（上臂 / 前臂 / 手）的 head **全在同一个 z、只沿 x 排开**。
3. 件到「**水平手臂轴**」（`Shoulder.head → Hand.head`）的**半径**：`套装件. Top 3` 中位 **17.8 cm**
   ⇒ 不可能是包在水平手臂上的袖子（而是挂在「下垂手臂」位置上的垂布）。

**⇒ 对拍脚本要同时打两个量、并按链分组看**（head 距离 + 方向夹角）；任一条链夹角 >2° 就要做 bind-pose 转换。
★ 转换本身会踩的坑见 `mhwi-blender-modding` **第十三次实战 B**：**权重近似二值的件会被撕开** ——
那时正确做法不是「平滑再转」，而是「**不转换 + 把该链权重并入同侧父骨**」。
